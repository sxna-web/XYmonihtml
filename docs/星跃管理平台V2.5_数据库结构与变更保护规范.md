# 星跃管理平台 V2.5｜数据库结构与变更保护规范

> 状态：强制保护规范 / 设计与核查基线，不代表当前数据库已经符合或已经实施。
> 适用对象：所有 AI、开发人员、自动化代理。
> 正式环境：现有 Cloudflare D1 数据库。实际数据库名称、绑定名称和 schema 必须从当前项目配置及真实环境核对，不得猜测。

## 1. 最高保护原则

1. 现有正式 D1 数据库是唯一既有业务数据来源；不得擅自另建一套替代数据库。
2. 未经用户明确批准，禁止对正式数据库执行 CREATE/DROP/ALTER、表重建、字段删除/重命名、索引/约束删除、数据清空、批量覆盖或不可逆数据修正。
3. 不得因本规范提出某个字段或表，就直接在生产环境创建它。文档中的字段、表名和状态仅为设计示例，必须先与真实 schema 对照。
4. 不得把测试数据库、预览环境或本地 mock 当成生产数据库。
5. 任何迁移必须先说明目的、影响对象、兼容性、数据回填、锁表/性能风险、回滚方式和验证 SQL，等待用户批准。
6. 禁止在未备份、未验证备份可读且未制定回滚方案时执行高风险数据库变更。
7. 不得将真实订阅 URL、节点凭证、卡密、用户隐私、密钥或数据库连接凭证提交到 Git。

## 2. 变更前必须完成的只读核查

必须先检查并保存核查证据：
- 当前 Git 分支、提交 SHA、工作区状态。
- D1 绑定配置、数据库标识和环境区分（不得输出密钥）。
- 所有迁移文件及其执行顺序、迁移记录表（若存在）。
- 当前 schema：表、列、类型、默认值、NOT NULL、主键、唯一约束、外键、索引、触发器（若有）。
- Worker 中所有相关 SQL、事务边界和数据访问路径。
- API 请求/响应字段及前端实际依赖。
- 现有测试、历史兼容逻辑、定时任务和后台作业。

推荐只读检查方向（具体命令需按项目当前 Wrangler/环境配置调整）：
- 列出表和视图；
- 对每张相关表执行 PRAGMA table_info；
- 检查 PRAGMA index_list 和 index_info；
- 检查 PRAGMA foreign_key_list；
- 检查 sqlite_master 中的表、索引、触发器定义；
- 核对迁移历史与仓库迁移文件。

**只读核查也必须确认目标环境，避免误连生产环境。**

## 3. 迁移设计要求

每个数据库变更必须提供：
1. 变更编号、目的和业务依据。
2. 涉及表/字段/索引/约束。
3. 旧 schema 与目标 schema 差异。
4. 现有数据影响及回填规则。
5. 旧 Worker 与新 schema 的兼容策略。
6. 新 Worker 与旧 schema 的兼容策略（如部署窗口需要）。
7. 并发、锁、执行时长和容量风险。
8. 备份位置、备份校验结果及恢复步骤。
9. 回滚脚本或明确说明为何不能直接回滚。
10. 测试环境验证、数据抽样核对和上线后监控计划。

迁移应尽量采用向后兼容的扩展式步骤：先增加兼容能力，再迁移数据，再切换读写，最后在单独批准后考虑清理旧结构。不得把多步风险变更合并成无法定位问题的一次性脚本。

## 4. 数据完整性与并发

- 所有唯一性、归属关系和关键状态转换应由数据库约束与服务端事务共同保护。
- 关键卡密激活、VIP 状态切换、额度扣减、任务领取、归档确认必须防止并发竞态。
- 对可重试操作设计幂等键和唯一约束；重试不得重复发放、重复扣费或重复归档。
- 外键启用状态必须核实；不能仅凭代码中声明了外键就认定约束生效。
- 删除操作需明确级联行为；禁止意外级联删除用户、节点、批次、卡密或审计记录。
- 对重要业务记录优先采用状态失效、软删除或可审计删除；永久清理必须有独立授权和保留政策。
- 时间统一使用服务器可信时间源；时区、精度、宽限期边界和定时任务幂等规则必须明确。

## 5. 备份与恢复

- 备份频率、保留周期、异地副本及 RPO/RTO 由用户确认后配置。
- 备份必须记录开始/结束时间、目标环境、结果、大小/校验信息和错误。
- 不能仅以“备份命令成功”判定备份可用；应进行完整性检查和定期恢复演练。
- 恢复前必须确认目标数据库、备份版本、数据时间点、差异范围和可能丢失的数据。
- 优先恢复到隔离环境验证；禁止未经审批直接覆盖正式库。
- 恢复操作必须记录操作者、审批、来源备份、影响范围、结果和后续核验。

## 6. 敏感数据

- 订阅凭证、节点认证信息、访问令牌等按敏感数据处理。
- 设计静态加密、密钥轮换、最小权限访问和日志脱敏。
- 密钥只存储在受控 Secret/环境配置中，不得写入代码、迁移文件、截图或公开 Git。
- 任何后台查看敏感值的行为应受授权并留下审计记录。
- 数据保留期限、删除请求处理和用户告知必须一致。

## 7. 禁止事项

- 未经批准重建现有表或以新表替代旧表。
- 为方便开发清空、重置或导入覆盖正式数据。
- 将生产数据复制到公开仓库、公开 issue 或普通测试日志。
- 假设迁移脚本从未执行，重复执行非幂等迁移。
- 只改 schema 不检查 Worker SQL、前端字段和历史数据。
- 在没有恢复验证的情况下声称“已有备份，可以放心回滚”。

## 8. 交付格式

每次数据库相关任务必须提交：
- 核查环境与提交 SHA；
- 当前 schema 证据；
- 变更前后差异；
- 迁移脚本路径及校验；
- 备份与恢复证据；
- 测试结果；
- 是否触及生产环境；
- 尚存风险和需要用户批准的事项。

没有用户明确批准，不得执行正式数据库变更。
