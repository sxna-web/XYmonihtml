# 星跃产品品牌区分与双产品协同架构规范

- 批次：第四十批
- 版本标识：V2.5-DEV-B1-BRAND-40
- 日期：2026-11-27
- 状态：产品定位与品牌架构规范；未修改 HTML/Worker/APP 源码；不可部署
- 关联基线：第三十六批统一导航与 RBAC、第三十七批路由治理、第三十八批通知中心、第三十九批通知 API 契约
- 重要原则：星跃管理平台与星跃 Android APP 是两个独立产品，不得将 APP 描述成管理平台的安卓版。

## 1. 用户明确要求

星跃后台和星跃 APP 必须有明显区分，同时保留合理关联。用户不能产生“星跃 APP 就是星跃后台的安卓版本”的认知。必要时可以调整 APP 产品名称。

该要求属于产品定位、品牌架构、信息架构、登录入口、界面文案、发布渠道和权限模型的基础约束，后续 UI、API、APP 改造都必须遵守。

## 2. 建议品牌架构

采用“共同母品牌 + 两个独立产品”的架构：

- 共同品牌：星跃。
- 管理产品：星跃管理平台（网页管理端）。
- 客户端产品：星跃 APP（Android 用户客户端；最终名称待品牌核查和用户确认）。

二者是同一生态下的两个独立产品，不是同一个产品的不同屏幕尺寸或不同操作系统版本。

### 管理平台定位

面向超管、管理员及获授权的运营人员：
- 用户、管理员和 VIP 权益管理。
- 卡密、APP 授权、设备授权和分享管理。
- 节点分组、同步、订阅和转换管理。
- 运营数据、审计、系统配置、版本和通知中心。
- 权限、租户、资源归属和业务生命周期管理。

管理平台是控制面/运营面，不承担 Android 客户端的日常代理连接体验。

### APP 定位

面向实际使用节点/代理服务的终端用户：
- 节点和分组查看、选择、连接、断开。
- 本机连接状态、流量/运行状态（以真实客户端能力为准）。
- 通过管理员身份 ID 或 APP 卡密获取被授权的节点分组。
- 本机配置、设备管理、授权状态、基础帮助和客户端更新。
- 不展示后台运营管理菜单，不让普通 APP 用户误以为自己进入了管理员后台。

APP 是独立客户端/使用端，不是管理平台的 Android 版；不能把后台网页简单套壳作为 APP 的产品定义。

## 3. 两个产品的关系边界

共同点：
- 使用统一的“星跃”生态识别。
- 共享必要的用户/管理员身份关联、授权关系、卡密和节点分享数据。
- 使用受控 API、明确的数据契约和统一的安全审计。
- 在各自产品中清晰说明对方的存在和作用。

必须分开：
- 产品名称、图标、启动页、主导航、应用商店/下载页介绍。
- 用户主要任务、信息架构、操作流程和界面语言。
- APP 客户端账号/授权体验与后台管理员登录/管理体验。
- 产品版本号、发布记录、更新节奏和故障诊断入口。
- 权限模型：APP entitlement 不等于后台管理员权限；后台 VIP 到期不应自动使已激活 APP entitlement 失效。
- APP 不应暴露后台管理 API 或后台管理入口；后台不能把 APP 用户界面当作管理功能的替代品。

关联方式必须通过业务能力实现，而不是靠复制对方界面：
1. 管理平台创建和维护可分享节点分组。
2. 管理平台为对应 APP 卡密配置授权分组。
3. APP 用户通过管理员身份 ID 获取免费分组，或通过 APP 卡密获取对应卡密分组。
4. APP 只获取当前用户被授权的数据，服务端校验 owner、entitlement、卡密状态和资源范围。
5. APP 分组撤销/改型后的 24 小时本地清理规则继续执行：服务端 tombstone/generation → APP 增量同步 → 本地清理 → cleanup acknowledgement。

## 4. 名称方案（暂定，不直接改正式名称）

当前建议优先评估：
- 管理端：星跃管理平台（保持）。
- APP：星跃连接（候选名 A）。

其他候选：
- 星跃网络（候选名 B）。
- 星跃通（候选名 C）。
- 星跃 APP（候选名 D，作为暂时的开发代称，不建议长期作为最终品牌名）。

名称评价原则：
- 能让用户一眼理解它是独立的连接/代理客户端。
- 不包含“后台、管理、控制台、管理版”等管理端语义。
- 与星跃母品牌保持可识别的关联。
- 不暗示未经证实的加速、安全、匿名或服务质量承诺。
- 需在正式采用前核查商标、应用市场重名、域名/下载入口冲突和第三方源码许可；本批未做商标或市场检索。
- 未经用户明确确认，不修改 APK applicationId、包名、签名、versionCode、versionName、应用市场标识或已有数据迁移规则。

## 5. UI/文案强制规则

管理平台：
- 标题统一使用“星跃管理平台”或经用户确认的后台品牌。
- 主导航突出管理任务；桌面保留独立 APP 管理分组。
- APP 管理分组管理的是授权、卡密、分组分享、设备和客户端版本，不是把 APP 用户界面嵌进后台。
- 手机端 APP 一级入口进入“APP 管理工作台”，仍然属于管理端功能。
- 管理平台下载/接入 APP 的入口使用明确说明：“面向终端用户的独立客户端”，避免“后台安卓版”等表述。

Android APP：
- 启动页、登录页、主界面、设置页均以客户端身份呈现。
- 主任务围绕连接、节点、分组和本机状态。
- 不使用“后台首页”“管理平台首页”“管理员控制台”等主界面命名。
- 不把后台侧栏、管理表格、VIP 运营统计照搬到 APP。
- APP 内可以有“授权来源/管理员信息”说明，但不得因此把整个 APP 定位为后台子页面。

共同入口：
- 管理平台可提供“客户端说明/获取客户端”入口。
- APP 可提供“授权来源/管理方信息”入口。
- 两边互相跳转时必须明确告诉用户即将打开的是另一个独立产品；不可静默伪装成同一个产品页面。

## 6. 版本与发布区分

系统和 APP 继续独立版本编号：
- 管理平台系统：SemVer，例如 V2.5.0、V2.6.0。
- Android APP：versionCode 单调递增整数 + versionName，例如 6.00.50。
- 发布页面分别显示产品名、产品图标、版本、发布日期、变更摘要和兼容性。
- APP 第三方源码来源、许可、授权服务器、设备限制、远程停用、SDK/API 依赖和更新控制权审计完成前，不宣称 APP 完全自主可控。
- 管理平台升级不代表 APP 自动升级；APP 升级也不代表后台升级。兼容性通过独立 manifest/API contract 声明。

## 7. 权限和通知边界

- APP 用户通知与后台管理员通知按 recipient、tenant、owner 和能力隔离。
- APP 的连接/授权/设备通知在 APP 内呈现；需要管理员处理的事件可向后台对应管理员生成摘要通知。
- 后台管理通知不应全部推送给 APP 终端用户。
- APP 客户端不能凭管理员 ID 或卡密本身访问后台管理能力。
- 后台页面隐藏按钮不等于授权；所有 APP 和后台 API 均由 Worker 重新验证会话、资源归属、entitlement 和 action capability。
- VIP 管理权限、APP entitlement、APP 设备绑定、卡密有效期分别建模，不混用一个状态字段。

## 8. 设计验收场景

1. 新用户只看到 APP 下载页时，能理解这是连接/代理客户端，而不是后台管理软件。
2. 管理员登录后台时，能理解自己正在管理用户、卡密、授权和分组，而不是使用 APP。
3. APP 用户通过管理员 ID/卡密取得分组后，只能看到被授权的客户端数据。
4. 后台管理员更改分组后，APP 通过同步机制更新，不需要打开后台页面。
5. APP 用户在客户端内无法通过改 URL 或伪造参数进入后台管理 API。
6. 两个产品的版本、更新、故障和通知不会混为同一个发布实体。
7. 后台 APP 管理分组仍保留；手机后台的 APP 一级入口进入管理工作台，不改变 Android APP 本身的信息架构。
8. 在所有下载介绍、启动页、关于页面和帮助文档中，不出现“星跃后台安卓版”或类似误导文案。
