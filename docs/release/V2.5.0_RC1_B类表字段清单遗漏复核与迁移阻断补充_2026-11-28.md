# V2.5.0 RC1 B 类表字段清单遗漏复核与迁移阻断补充

- 日期：2026-11-28
- 分支：`release/v2.5.0-rc1-converge`
- 范围：22 张 B 类 Worker SQL 引用表的第一轮反例检查
- 结论：发现字段清单存在明确漏项；不得据现有清单生成建表 SQL。

## 1. 明确发现的字段漏项

以下不是推测，而是当前 Worker 源码中可定位的 SQL 明确引用：

| 表 | 现有清单列 | 源码明确引用但清单缺少的列 | 证据位置 |
|---|---|---|---|
| `admin_audit` | `action`, `detail` | `id`, `created_at` | Worker 第 5156 行：`SELECT id, action, detail, created_at ... ORDER BY id` |
| `node_sync_logs` | `trigger_kind`, `duration_ms`, `missing_nodes` | `source_id`, `source_name`, `status`, `total_nodes`, `added_nodes`, `updated_nodes`, `error_message`, `created_at` | Worker 第 1071-1074 行 INSERT；第 4905-4911 行 SELECT |
| `admin_audit_events` | 当前清单列出业务审计字段 | SQL 还依赖 `id` 排序，并以 `SELECT *` 暴露整行 | Worker 第 2213-2215 行 |

以上证明当前 B 类字段数组不是完整字段清单。尤其 `admin_audit` 和 `node_sync_logs` 已出现直接可验证的漏列，因此此前“字段名词法命中”只能作为线索，不能作为字段完整性验收。

## 2. 逐语句证据摘录

### admin_audit

- 写入：Worker 第 5146 行，`INSERT INTO admin_audit(action, detail)`。
- 读取：Worker 第 5156 行，`SELECT id, action, detail, created_at FROM admin_audit ORDER BY id DESC LIMIT ?`。
- 最低可确认字段集合：`id`、`action`、`detail`、`created_at`。
- 字段类型、主键/自增属性、默认值和索引仍未知，不能据此推断 DDL。

### node_sync_logs

- 写入：Worker 第 1071-1074 行，插入 `source_id`、`source_name`、`status`、`total_nodes`、`added_nodes`、`updated_nodes`、`error_message`、`trigger_kind`、`duration_ms`、`missing_nodes`。
- 读取：Worker 第 4905-4911 行还读取 `id`、上述字段及 `created_at`。
- 最低可确认字段集合：`id`、`source_id`、`source_name`、`status`、`total_nodes`、`added_nodes`、`updated_nodes`、`error_message`、`trigger_kind`、`duration_ms`、`missing_nodes`、`created_at`。
- 字段类型、默认值、索引及约束仍未知。

### admin_audit_events

- 写入由 `auditStmt` 等 SQL 显式列出业务字段。
- 读取接口使用 `SELECT * ... ORDER BY id DESC`，因此 `id` 是实际排序依赖；完整输出列还需以原始 CREATE TABLE 或真实 schema snapshot 确认。
- 不得把 `SELECT *` 当作字段清单证据。

## 3. SQL 参数绑定核对状态

本轮没有把简单的问号数量扫描冒充为参数绑定验收。Worker 存在模板字符串、条件 SQL、展开数组、`FENCE_SQL`、动态 WHERE/ORDER BY 和多语句 batch；要证明参数绑定正确，必须按每个 prepare 表达式与对应 `.bind(...)` 建立语句级关联，并检查条件分支。

当前明确待核项：
1. 所有静态和模板 SQL 的占位符计数与 bind 参数数量/顺序；
2. 动态 SQL 的每个分支与 `binds` 数组来源；
3. `FENCE_SQL` 与 `fenceBinds(lease)` 的参数展开位置；
4. `db.batch()` 内每条 statement 是否各自完成绑定，审计语句是否与业务语句保持预期原子性；
5. `ON CONFLICT` 依赖的唯一索引/约束是否存在于实际 schema；
6. 所有字段对既有 D1 schema 是否兼容。

## 4. 本地迁移验证器边界

RC1 workflow 的 SQLite verifier 测试只运行于 disposable local SQLite fixture。工具 README 明确禁止将其视为生产迁移执行器；它不访问 Cloudflare、Wrangler、D1、Secrets 或生产 binding。25 项本地测试通过，只代表隔离验证器自身的回归测试通过，不代表 Worker SQL 与生产 D1 schema 兼容。

## 5. 处理决定

- 保持 `/api/super/migrate` fail closed。
- 后台数据库页继续只读表名检查，不显示泛化“数据库已就绪”。
- 不补猜字段类型，不生成生产 CREATE TABLE，不执行 ALTER/CREATE。
- 下一步按 22 张表逐项建立 SQL 路由—表别名—字段—bind 参数矩阵；优先完成 `admin_audit`、`node_sync_logs`、`admin_audit_events`。
- 在真实 D1 schema snapshot 获得用户明确授权前，生产数据库迁移继续阻断。

## 6. 发布判断

当前 RC1 CI 的 bundle、Cron、静态门禁、隔离 SQLite verifier、授权适配器和 Worker handler 测试均已通过。但本报告发现 B 类字段清单本身有漏项，故数据库结构验收未通过。RC1 仍是内部候选，不是生产可部署版本。
