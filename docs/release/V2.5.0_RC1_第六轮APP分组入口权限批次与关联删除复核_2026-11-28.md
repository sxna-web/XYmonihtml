## 1. 发现的问题

### 1.1 APP 管理写入没有统一使用 scopeGuard

用户态 APP 分组的创建、修改、删除、来源关联和设备成员关联部分路径直接调用 `.run()`。入口虽然先调用 `requireScope`，但检查与写入之间存在撤销协助权限的时间窗口；这几条写入没有像其他 userBatch 路径一样，在同一个 D1 batch 中再次验证协助授权仍有效。

APP 入口链接新增和删除也存在相同缺口：新增 helper 直接 INSERT 后再 best-effort 写审计；删除则直接执行 DELETE。

### 1.2 APP 分组来源移除缺少资源归属验证及有效 VIP 动作分类

`DELETE /api/user/app-groups/:id/sources/:sourceId` 原先没有先验证分组属于当前管理员，SQL 也没有最终 group-owner predicate。并且 authorization adapter 没有把来源移除分类为配置变更动作，正式 VIP 过期用户可能通过普通 manage scope 执行该配置修改。

## 2. 修复内容

### 2.1 用户 APP 分组写入统一改用 userBatch

以下路径现统一通过 `userBatch(db, ctx, stmts)` 执行，协助会话的 scopeGuard 与业务语句同批提交：

- 创建 APP 分组
- 修改 APP 分组
- 删除 APP 分组及其来源/成员关系
- 添加分组来源
- 移除分组来源
- 添加指定设备成员

主要业务写入均保留 owner predicate。来源移除现在先验证分组归属，最终 DELETE 也通过 EXISTS 再次限制 `app_groups.id + admin_user_id`。

### 2.2 分组删除顺序改为安全的原子级联

分组删除现按以下顺序放入同一个 D1 batch：

1. 先执行 owner + formalCutoff 断言；历史删除不符合范围时整批失败。
2. 删除该组来源关联（仍要求该组属于当前管理员）。
3. 删除该组设备成员（仍要求该组属于当前管理员）。
4. 最后删除分组主记录，并再次带 owner + formalCutoff 条件。
5. 写入审计记录。
6. userBatch 最后追加协助 scopeGuard。

这样避免先删除主组后，子记录清理语句因主组不存在而无法执行；也避免历史 cutoff 不满足时先删掉子记录。

### 2.3 APP 入口链接也纳入 scopeGuard

- `addAppLink` 的入口 INSERT 与审计 INSERT 现在通过 userBatch 同批执行。
- 用户删除入口链接也通过 userBatch 执行，并保留 admin_user_id + formalCutoff 最终条件。
- 该 helper 也被超管路由使用；本人直接超管会按既有规则不追加协助 scopeGuard。

### 2.4 来源关联移除改为有效 VIP 配置动作

`worker-auth-adapter.mjs` 将 `DELETE /api/user/app-groups/:id/sources/:sourceId` 归类为 `associate`：
- 必须有有效 VIP 才能修改配置；
- 协助会话仍须满足管理入口的 manage scope 检查；
- 正式 VIP 到期后的历史删除权限不再被误用于来源关联配置修改。
