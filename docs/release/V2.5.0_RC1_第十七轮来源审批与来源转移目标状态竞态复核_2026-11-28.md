## 1. 发现的问题

### 1.1 来源审核

approve/reject 路径先读取 source_approvals 状态，再按 source_id 更新。并发审核可能让旧请求覆盖新审核结果；拒绝路径还会同时停用 subscription_sources，需要审核状态和副作用写入保持原子。

### 1.2 来源分配

来源分配路径先读取来源、目标用户 active 状态和当前归属，再执行 ownership upsert。目标用户在预读后被停用/删除时，旧请求仍可能继续分配；来源也需要在最终 batch 再确认存在。

## 2. 已实施修复

- approve/reject 同一批次首条断言确认 `source_approvals.source_id + 原 status` 仍匹配。
- 审核 UPDATE 增加 `WHERE source_id = ? AND status = ?` compare-and-swap。
- reject 的来源停用和审计仍与审核状态更新同批次；状态竞争返回 409 `SOURCE_APPROVAL_CHANGED`。
- source assign batch 新增来源存在断言，以及目标用户仍为 active 的断言。
- 既有 source_ownership 前态断言、ownership upsert 和审计继续保留在同一批次。

## 3. 测试与静态回归

新增两项 Worker handler 测试：
- 来源审核必须在同批次重查原审核状态、执行状态更新并写审计。
- 来源分配必须在同批次重查来源存在和目标用户 active。

静态回归新增 source approval compare-and-swap 与 source assignment target/source guard 检查。
