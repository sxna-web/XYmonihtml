## 1. 发现的问题

APP 卡密生成流程原先先查询管理员名下总记录数和未激活库存数，再逐条 INSERT。虽然单次批量上限为 300、总记录上限为 20000、未激活库存上限为 5000，但这两个容量查询发生在写入 batch 之前。

两个并发生成请求可能同时读取到相同的剩余容量，并分别通过预检查，之后各自插入，最终突破库存或总记录上限。这是典型的 check-then-write 并发窗口。

## 2. 修复

保留原有预查询，继续提供友好的即时错误提示；同时将两个容量断言加入实际写入的同一个 `userBatch`：

1. 总记录数断言：
   `COUNT(app_cards for admin_user_id) + requested_count <= APP_CARD_TOTAL_MAX`
2. 未激活库存断言：
   `COUNT(normal + unactivated + unused cards for admin_user_id) + requested_count <= APP_CARD_STOCK_MAX`

断言在卡密 INSERT 和审计 INSERT 之前执行，并与用户协助 scopeGuard 同一批提交。若批次内断言失败，整批回滚并返回 HTTP 409、`APP_CARD_CAPACITY_CHANGED`，不会返回虚假的生成成功。

原有约束保留：
- 单次生成不超过 300 张；
- 未激活库存最多 5000 张；
- 总记录最多 20000 条；
- 每张卡密的天数范围仍为 1–3650 天。

## 3. 自动回归

新增 Worker handler tests：
- 正常生成时，确认总记录与未激活库存两条断言均在同批写入。
- 模拟容量断言失败，确认返回 409 `APP_CARD_CAPACITY_CHANGED`，且没有执行卡密 INSERT。

更新静态回归脚本，要求 APP 卡密路由必须同时包含两个 in-batch 容量断言和容量冲突错误处理。

## 4. 限制与结论

本轮修复把容量条件放入同批写入，以消除应用层预检查和插入之间的竞态；CI 使用的是 mock Worker handler 与隔离测试，并没有对真实 Cloudflare D1 做并发压测。最终数据库锁定/事务行为仍需在非生产隔离 D1 环境验证。

本轮没有修改卡密设备数、到期、失活、恢复或多卡密聚合规则。APP 多卡密分组聚合和客户端同步仍是未完成项目。
