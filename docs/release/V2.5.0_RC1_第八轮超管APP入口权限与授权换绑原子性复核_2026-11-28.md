## 1. 发现的问题

超管 APP 入口/权限/授权路由仍有旧式非原子写入：

- 删除 APP 入口：先 SELECT，再独立 DELETE，无同批次存在性断言及审计。
- 修改 APP 权限：先独立 upsert，再 best-effort 写审计；两者不在同一个 D1 batch。
- APP entitlement 设备换绑：先读设备 ID，再独立 UPDATE，审计另行 best-effort 写入；并发换绑时没有旧设备 ID 条件，可能覆盖刚刚发生的换绑。
- 权限更新在请求未提供 `free_group_enabled` 时，若继续把预读值作为更新值写回，会覆盖并发请求刚更新的开关。

## 2. 已实施修复

### 2.1 超管删除 APP 入口

- 保留入口快照。
- 同一 D1 batch 内执行存在性断言、DELETE、审计 INSERT。
- DELETE 未命中时返回 409。

### 2.2 超管修改 APP 权限

- 同一 D1 batch 内断言目标 APP 用户存在、执行 upsert、写审计。
- `free_group_enabled` 未在请求中提供时，UPSERT 使用 SQL CASE 保留数据库写入时的当前值，不再把预读旧值覆盖回去。
- 请求显式提供时才更新该开关。

### 2.3 超管换绑 APP entitlement

- 在写入前生成目标设备 token，避免密钥/签名失败发生在设备 ID 已变更之后。
- 同一 batch 内断言 entitlement 仍匹配预读的旧 `device_id`，UPDATE 也使用 `WHERE id = ? AND device_id = ?` 比较并交换条件，再写入审计。
- 如果并发换绑已先改变旧设备 ID，本次 batch 断言失败，不覆盖新绑定。

### 2.4 回归测试

新增 Worker handler 集成测试，覆盖：
- 超管权限更新同批次包含 app_users 存在性断言、upsert 与审计，并在未传 free-group 开关时保留数据库当前值。
- 超管 entitlement 换绑使用旧 device ID CAS 条件，并在同批次写审计。
- 超管 APP 入口删除在同批次完成断言、删除与审计。

静态回归脚本还检查超管 APP 入口/权限/换绑路由不得出现独立 `.run()` 写入，要求三类写操作使用 batch 和审计。
