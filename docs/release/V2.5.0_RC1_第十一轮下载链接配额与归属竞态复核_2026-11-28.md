## 1. 发现的问题

### 1.1 下载链接 20 条上限存在并发超额风险

`addDownload` 原先先查询当前数量，再独立 INSERT。并发请求可能同时读到不足 20 条，随后都插入，突破每个 scope + 管理员维度的 20 条上限。插入也没有与业务操作同批次的 `admin_audit_events` 记录。

### 1.2 用户删除下载链接存在 owner TOCTOU

用户删除前 SELECT 使用了 `id + admin_user_id`，但最终 DELETE 只使用 `id`。如果检查后资源归属发生变化，旧请求仍可能删除不再属于当前管理员的链接。

### 1.3 超管删除缺少存在性断言和审计

超管删除下载链接直接执行 DELETE，无预读快照、同批次存在性断言或审计事件。

## 2. 已实施修复

### 2.1 新增下载链接配额保护

- 保留预读 COUNT 以提供友好错误。
- 最终配额断言放入同一个 `userBatch`，再执行 INSERT 与审计。
- admin scope 同批次确认目标管理员仍存在。
- 使用当前数据库配置重新计算 scope + admin 的链接数量是否小于 20。
- 若并发请求已用完最后一个名额，返回 409 `DOWNLOAD_LIMIT_CHANGED`，不会插入超额记录。
- 普通管理员和超管新增共用该 helper。

### 2.2 用户删除下载链接保留 owner 条件

- 同批次断言 `id + admin_user_id` 仍匹配。
- 最终 DELETE 也使用 `WHERE id = ? AND admin_user_id = ?`。
- 同批次写入审计；未命中返回 409。

### 2.3 超管删除下载链接纳入原子审计

- 先读取删除前快照。
- 同一 D1 batch 中断言记录仍存在、执行 DELETE、写审计。
- 不再直接独立 `.run()` 删除。

## 3. 回归测试

新增 Worker handler 集成测试：
- 用户新增下载链接时，配额断言、INSERT、审计必须在同一 batch。
- 模拟并发消耗最后名额时返回 409，且没有 INSERT。
- 用户删除最终 SQL 必须保留 owner predicate 并写审计。
- 超管删除必须同批次完成存在性断言、DELETE 和审计。

静态回归增加检查：addDownload、userDownloadsRoute、superDownloadsRoute 不得绕过 batch；必须保留数量断言、owner predicate 和审计。
