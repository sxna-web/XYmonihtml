## 一、本轮实现

### 1. 后台逐卡密分组配置 UI

修改 `releases/v2.5.0-rc1/index.html`：

- 卡密列表每张卡增加“配置分组”入口。
- 配置窗口按分组 ID 展示当前管理员自己的 `mode='card'` 分组和该卡密已关联分组。
- 不提供免费分组选择；免费分组仍由管理员身份免费授权链路提供，不按多张卡密重复配置。
- 已停用分组不能重新分配；若历史上已关联，则需主动取消勾选后才能保存移除，未保存不会改变原配置。
- 卡密状态不是 normal/used、手动禁用或已过期时，界面只读。
- PUT 请求携带客户端 `Idempotency-Key`；同一卡密、相同选择在网络结果不确定时复用同一请求编号，选择变化才生成新编号。
- 保存成功与列表刷新失败分别提示，避免服务端已成功但刷新失败时误导用户重复操作。

### 2. Protocol66 Worker 正式路由接入

修改 `backend/worker/V2.5-DEV-B1-CORE-AUTH-49/Worker.js`，引入 Protocol66 handler/service/D1 adapter：

- `GET /api/user/app-cards/:cardId/groups`
- `PUT /api/user/app-cards/:cardId/groups`

路由位于既有用户 Session、Origin、scope、APP 管理权限门禁之后；用户身份只取服务端 session，不信任请求体身份字段。
- GET 允许有权限的本人/委托只读会话查看。
- PUT 继续经过既有 `authorizeAppManagementRequest` 的 `associate` 动作判定：有效正式 VIP、7 天体验 VIP、符合规则的直接超管可写；过期 VIP 不可新增/修改；委托会话必须有当前有效 operate/manage scope。
- D1 最终 batch 再次核验有效正式/体验 VIP（直接超管由服务端布尔上下文明确豁免）、卡密归属/状态/手动禁用/到期、卡密分组 owner/mode/enabled、映射 CAS 版本、委托 scope 和审计写入。
- 增加 schema readiness 检查。两张映射表未同时存在时，接口明确返回 HTTP 503 `CARD_GROUP_SCHEMA_NOT_READY`，不会尝试自动建表或写入；不影响其他卡密接口。
- 保持空分组配置有效；卡密分组与免费分组分开。

### 3. 防止现有分组操作破坏映射历史

发现现有 `userAppGroupsRoute` 对分组执行物理 DELETE，且允许直接切换 mode。若启用映射表和历史保护触发器，旧路径会撞上数据库触发器并可能给用户返回内部错误。

本轮增加向前兼容保护：
- 有 active 卡密映射的 card 分组，不允许直接切换到其他 mode，返回 409 `APP_GROUP_HAS_ACTIVE_CARD_MAPPINGS`。
- 任何曾存在映射历史的分组暂不允许物理删除，返回 409 `APP_GROUP_HAS_CARD_MAPPING_HISTORY`。
- 检查映射表元数据/查询失败时返回 503，不冒险执行破坏性写入。
- 没有映射表或该分组没有映射历史时，原有分组行为保持不变。

**限制：** 这只是防止历史映射被破坏的安全闸，不是用户要求的完整 tombstone/generation → APP 增量同步 → 24 小时本地清理 → cleanup ACK。该完整删除生命周期仍需 APP 6.00.48 客户端协议可读后继续实现；在此之前，对曾关联卡密的分组保持保守阻止物理删除。
