## 二、客户端当前实际调用的星跃 API

唯一客户端 API 实现文件：app/src/main/java/io/nekohasekai/sagernet/starjump/StarJumpApi.kt。

静态检索确认当前只有以下四类请求：

1. POST /api/app/redeem，JSON body 仅包含 code 与 device_id。
2. GET /api/app/resolve?code=...。
3. GET /api/app/links?device_id=...&token=...。
4. GET /api/app/version?platform=android&current=60047。

未发现客户端调用：
- GET /api/app/groups
- GET /api/app/free
- GET /api/app/nodes
- Idempotency-Key 请求头
- 分组 generation/tombstone/cleanup ACK 协议

这意味着：当前 APP 6.00.48 并没有真正接入后台免费分组/卡密分组读取链路；本轮后台逐卡密配置 UI 和 Worker 写入路由不能单独让 APP 用户看到分组。

## 三、客户端激活与网络行为

- StarJumpApi.open() 使用 HttpURLConnection；连接超时 10 秒、读取超时 15 秒。
- 没有 GET 有限重试、没有 POST 同设备安全重试、没有处理 Retry-After，也没有明确的 429/503 分类提示。
- ActivationActivity.doActivate() 直接启动后台 Thread；未发现点击后禁用激活按钮的并发保护。
- redeem() 仅解析 JSON 的 error 字段；网络异常显示通用网络错误。
- links() 在 HTTP 错误或异常时直接返回空列表，用户难以区分“确实没有链接”和“网络/服务异常”。
- 当前客户端没有发送 Idempotency-Key。后端已实现同设备同卡密、有效授权的安全重放，因此可在不强迫旧客户端升级协议的情况下缓解激活响应丢失；但 APP UI 仍应增加重复点击保护和有限网络重试。
- 激活成功后，客户端只保存单个 token、expires_at、admin_user_id；再次激活会覆盖旧值，无法本地表达多张有效卡密对应的多份 entitlement。
- device_id 存在 SharedPreferences。Android backup rules 当前只 include 数据库文件，不 include shared preferences；静态规则下该 token/device id 不在配置的备份清单内。

## 四、当前固定分组与后台功能不匹配

- ReferenceSubscription.kt 创建五个固定内置组：星跃节点 01 至 星跃节点 05。
- Slot 01 仍使用固定 Paste.gg Raw 地址；Slot 02–05 是 PASTE_GG_URL_SLOT_02 等占位符。
- AutoNodeStartup.kt 启动时刷新这些固定内置组；失败时保留本地节点。
- ProxyGroup 本地 Room 模型只有 starJumpBuiltIn 布尔标记，没有管理员 ID、卡密 ID、远端 group ID、generation、tombstone、ACK 等字段。
- 现有本地组管理器保护内置组不被普通编辑/删除；这适用于固定内置组，但不足以表达每张卡密动态分组和多个管理员之间的隔离。

## 五、服务端与客户端当前契约差距

当前 Worker 的 appGroupsForDevice()：
- 只选取设备最近一条有效 entitlement（ORDER BY created_at DESC LIMIT 1）。
- 只返回 public/free/assigned 既有模式，不返回新建的 mode='card' 映射。
- 因而无法满足同一设备多张有效卡密分别取得各自卡密分组。
- 有效 entitlement 时只取最近 entitlement 所属管理员的组；不能自然合并多管理员。
- 无有效 entitlement 时读取 app_free_grants；激活成功时通过 INSERT OR IGNORE(device_id,admin_user_id) 建立 grant，这能避免同一管理员多张卡重复创建免费 grant。
- 另有 /api/app/free?admin=... 专用免费节点 API，但 APP 6.00.48 未调用。
- 服务端尚无 tombstone/generation/cleanup ACK；当前禁用/删除分组不能保证 APP 本地缓存按用户规则在 24 小时内清理。

## 六、其他安全与兼容性观察

- StarJumpApi.DEFAULT_BASE 当前写死为 https://starjump-api-staging.synahcoo.workers.dev。是否与本项目获批的目标 Worker URL 完全一致，必须由用户/部署配置核验；不能把源码默认值当作已确认生产地址。
- ActivationActivity.checkUpdate() 当前传入 60047，而 APK 实际 Android versionCode 按构建规则为 355。服务端 releases.version_code 是否使用独立的 60047 序列尚未由真实发布记录证明；需统一约定后再修改，避免 APP 更新检查失效或误触发强制更新。
- network_security_config.xml 允许全局 cleartext HTTP。星跃 API 默认地址是 HTTPS，但在未审查普通订阅/插件兼容性前，不应直接全局关闭 cleartext。
- README 与 LICENSE 明确 GPL-3.0 fork 关系。静态源码扫描不构成完整第三方许可证合规意见。

## 七、下一阶段必须完成的 APP 端主线

建议下一次 APP 大更新采用用户此前提出的 6.00.50 版本方向；当前元数据 VERSION_CODE=71，按既有乘 5 规则下一序号至少应为 72（APK versionCode 360）。正式版本名与版本代码仍需在出包前统一确认。

1. 多卡密授权本地模型：保存多条 entitlement（entitlement_id、admin_user_id、card_id、expires_at、token），不再覆盖单一 token；激活后先落盘再刷新，网络失败保留既有本地节点。
2. 客户端分组读取：增加 /api/app/groups 和 /api/app/free 调用；卡密组按每张有效卡密读取，免费组按管理员 ID 去重一次；不同管理员的数据按 admin ID 隔离。
3. 服务端组合响应：/api/app/groups 合并设备所有有效 entitlement 的卡密组；同一组被多张卡关联时按 group ID 去重并附 card IDs；免费 grant 按 admin/device 唯一；旧字段保持兼容。
4. 本地 Room 迁移：为远端组增加稳定远端 ID、管理员 ID、关联卡密 ID、generation、同步时间与 tombstone 状态；保留当前手动组和五个旧内置组，不做破坏性清空。
5. 安全增量同步：完整校验服务端返回的节点，使用 Room transaction 原子更新；断网/超时/429/503 时保留旧节点；不因空响应或半包覆盖现有节点。
6. 删除与类型变化：服务端 generation/tombstone → APP 增量拉取 → 本地 24 小时内清理 → cleanup ACK；在完整链路完成前，不开放物理删除已映射分组。
7. 网络稳定性：GET 有限重试；激活 POST 同设备同卡密最多一次安全重试；429 按 Retry-After 提示、不循环重试；重复点击禁用；错误提示区分离线、超时、限流、服务端暂不可用。
8. 更新版本检查：统一 APP Android versionCode 与后台 release.version_code 的语义，取消硬编码 60047。
9. 目标 API 地址：通过受控构建配置注入已核验的 API base，不把未知生产 URL 写死进 APK。
