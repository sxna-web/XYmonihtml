## 1. 审计结论：同步 fencing 的关键机制

同步引擎的 `FENCE_SQL` 在 lease 有 `ownerUserId` 时，除 generation、lease owner、token hash、有效期外，还要求 `source_ownership` 中仍存在相同 source_id/user_id。stage、seal、commit 的写入路径均复用该 fencing 条件。

`syncSource` 从来源行的 owner_user_id 或调用选项获取 ownerUserId。因此已分配给用户的手动/Cron 同步，在来源解除归属后，后续 stage/commit fence 应拒绝旧 owner 的写入。该判断来自代码路径审计和 mock/static CI，不代表已在真实 D1 进行并发时序验证。

## 2. 本轮发现与修复

原超管解除分配路径在事务外读取来源 enabled 和当前 owner，批次内仅断言 owner 后删除归属、停用来源并写审计。缺少对来源 enabled 快照的最终检查；删除语句也没有把当前 owner 写入最终 DELETE 条件。

已修复：
- 同一批次先断言来源仍存在且 enabled 与预读快照一致。
- 同一批次断言 source_id 当前仍属于预读的 user_id。
- DELETE 改为 `WHERE source_id = ? AND user_id = ?`，不再只按 source_id 删除。
- 停用改为 `WHERE id = ? AND enabled = ?`，防止覆盖并发启用/停用变更。
- 检查 DELETE 和 UPDATE 的 changes；无实际写入时返回 409 `OWNERSHIP_CHANGED`。
- 来源归属删除、停用、审计仍在同一 D1 batch。
- 原有同步 fencing 规则不变：旧 owner 的 staging/commit 在 ownership 消失后应失效。
