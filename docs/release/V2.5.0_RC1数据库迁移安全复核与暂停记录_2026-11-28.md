# V2.5.0 RC1 数据库迁移安全复核与暂停记录

- 日期：2026-11-28
- 分支：`release/v2.5.0-rc1-converge`
- 范围：RC1 候选 Worker、后台 HTML、仓库 migration tooling
- 状态：已完成静态复核；未连接 Cloudflare；未读取或修改 D1；未读取 Secrets；不可据此宣称生产 schema 已就绪。

## 1. 复核发现

### 1.1 旧 Worker 一键迁移入口存在权限例外

旧版 `/api/super/schema-status` 与 `/api/super/migrate` 特殊分支只判断 `ctx.isSuper`，并明确允许 `ctx.legacy`，即 ADMIN_TOKEN legacy 身份可进入数据库迁移路由；也没有在该分支拒绝 actor/effective identity 不一致的协助会话。

### 1.2 旧迁移执行器不具备生产安全验收条件

- `MIGRATE_STATEMENTS` 逐条 `prepare(sql).run()`，不是一个原子迁移。
- 用宽泛错误文本 `already exists|duplicate column` 判定跳过，无法区分真正已满足与结构冲突。
- 若干 `ALTER TABLE` 使用空 catch，失败不进入错误列表。
- `convert_links` owner 字段的 `addedOwner` 不能准确表达每个字段的实际结构状态。
- 迁移后只复核 `REQUIRED_TABLES` 表名是否存在，不核验字段、类型、NOT NULL、默认值、索引、唯一约束和外键。
- 审计写入失败不会阻止迁移响应报告完成。
- 缺少 migration ID/checksum/dependency ledger、plan hash、并发锁/fencing、postcondition 和中断恢复机制。

### 1.3 仓库迁移文件不是正式 D1 migration

`tools/database_migrations/README.md` 明确标注 LOCAL-ONLY / NOT A PRODUCTION MIGRATION RUNNER。当前 SQL 文件只有：
- `CORE-MIG-001.sql`：本地迁移账本；
- `NTF-001.sql`：本地通知事件表；
- `NTF-002.sql`：本地通知收件箱/偏好/投递表。

这些 SQL 不包含 Worker 旧 `MIGRATE_STATEMENTS` 中的核心业务表，也没有证明与真实 D1 当前结构兼容。不能将它们作为生产初始化脚本。

### 1.4 后台 HTML 原来会直接触发 DDL

数据库按钮原来先读取 `schema-status`，发现缺表后就调用 `POST /api/super/migrate`，仅通过浏览器 confirm 作为确认；页面没有对数据库操作做 Staging 环境限制。登录页的“初始化诊断”虽标注仅 Staging，但不等于数据库按钮也被限制为 Staging。

## 2. RC1 已采取的安全修正

1. 数据库状态与迁移路由现在仅允许本人登录的超级管理员 Session；拒绝 legacy ADMIN_TOKEN 和协助会话。
2. `GET /api/super/schema-status` 仅返回只读表名存在性，并明确返回 `verification=TABLE_NAMES_ONLY`、`required_tables_present`、`migration_enabled=false`；不再返回含义宽泛的 `ready` 字段。
3. `POST /api/super/migrate` 暂时 fail closed，返回 HTTP 503 / `MIGRATION_REVIEW_REQUIRED`；旧的逐条 DDL 迁移实现已从 RC1 Worker 路径移除。
4. 后台数据库按钮改为只读检查，不再调用迁移 POST；页面明确说明 RC1 不执行自动建表。
5. CI 增加静态门禁：数据库迁移拒绝 legacy/assist session、旧 DDL 不存在、状态接口披露检查范围、HTML 不触发 DDL。

### 1.5 Worker SQL 依赖表范围超出当前 schema-status 清单

对 RC1 Worker 的 SQL 语句做静态表名提取，发现除旧迁移清单的 18 张候选表外，还引用以下基础业务表（示例按代码命名列出）：

`admin_audit`、`admin_audit_events`、`admin_user_scopes`、`app_settings`、`app_users`、`node_group_members`、`node_groups`、`node_identity_aliases`、`node_overrides`、`node_records`、`node_sync_logs`、`node_user_metadata`、`source_approvals`、`source_ownership`、`source_quota`、`subscription_sources`、`subscription_sync_state`、`sync_task_manifests`、`sync_task_stage`、`sync_tasks`、`user_manual_nodes`、`user_sessions`。

这些基础表没有在当前 RC1 `MIGRATE_STATEMENTS` 的建表列表中得到完整定义；Worker 的运行代码依赖它们。旧 `schema-status` 只检查 18 张候选扩展表，可能在上述基础表缺失时仍报告 `ready=true`。这进一步证明该接口不能作为全库就绪判定。

本次安全修正将响应字段明确标为 `TABLE_NAMES_ONLY`，并暂停 DDL。下一阶段必须逐表建立完整字段/索引/约束 manifest，并找到可信的原始建库基线或经批准的 schema snapshot，不能根据 SQL 引用自行猜测表结构。

- 旧 RC1 schema-status 仅检查 18 张核心表，未检查另外 22 张 Worker SQL 引用表。

- 自动回归要求两组表名与静态 JSON 清单逐项一致，总计 40 张；不把 B 类 SQL 字段引用线索冒充完整 DDL。
- Push CI Run 46097884870 SUCCESS。该检查仍只读取 sqlite_master 表名，不代表字段级 schema ready。

## 3. 当前边界

- 只读状态接口只核对表名，不是完整 schema 检查。
- Worker 中其它业务 SQL 仍依赖更多既有表/字段；不能仅凭 18 张候选表齐全就认定整个数据库 ready。
- 本轮没有生产 D1 schema snapshot，因此不能安全地生成并执行面向现有数据库的补表/加列 SQL。
- 不能把 local SQLite migration tests 当作 D1 事务、并发或 SQL 兼容性证据。

## 4. 下一阶段数据库实施要求

1. 先建立完整的 Worker SQL table/column/index/constraint inventory。
2. 对照原始 Worker 的基础 schema、版本化 DDL 和所有业务 SQL，生成可审计 schema manifest。
3. 实现只读 inspect：表、列、索引、唯一约束、外键和对象定义摘要。
4. 实现 migration manifest、不可变 checksum、依赖、plan hash、审批、互斥锁/fencing、逐步骤状态与 postcondition。
5. 对同名但结构不一致的对象标记冲突，绝不以“already exists”跳过。
6. 只在经明确授权的隔离 D1 环境执行完整测试；生产 D1 仍需独立审批。
7. 保留手机端一键操作体验，但一键操作必须是“检查 → 计划 → 明确批准 → 执行 → 验证”，不能是未经结构核对的直接 DDL。

## 5. 结论

本轮选择先关闭存在权限和结构验证缺陷的旧一键迁移入口，而不是冒险让用户在正式 D1 上点击“建表”。RC1 的数据库页暂时只读，直到新迁移器及隔离 D1 验收完成。

**结论：数据库迁移仍是正式上线阻断项；当前 RC1 不能作为数据库初始化已完成的 STABLE 版本。**
