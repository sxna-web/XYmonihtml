## 1. 发现的问题

### 1.1 卡密软删除与激活存在竞态

用户删除未激活卡密时，旧逻辑先 SELECT 检查未激活，再独立 UPDATE。若在检查后、更新前另一请求完成激活，旧 DELETE 更新仍只按卡密 ID + 管理员 ID 过滤，可能把已激活卡密标记为 user_deleted。

### 1.2 激活事件不在授权写入事务中

APP 卡密兑换原先在一个 batch 中写卡密状态、授权和免费组资格，但 `app_card_events` 在 batch 成功后另行 best-effort INSERT。事件表写入失败时，兑换成功但卡密事件记录缺失，无法保证完整业务审计链。

### 1.3 兑换前检查需要最终条件复核

兑换前已检查卡密未停用、未使用、状态正常、未过期，但最终 batch 的断言/UPDATE 仍应绑定管理员归属、天数、手动停用状态、未使用状态及有效期，防止检查与写入之间卡密数据被改动。

## 2. 已实施修复

### 2.1 卡密软删除同批次状态断言

- 在同一 userBatch 中先断言卡密仍属于当前管理员、未激活、未使用且 status 不是 used。
- 最终 UPDATE 再重复 owner + 未激活 + 未使用条件。
- 如果状态在预读后发生变化，整批失败并返回 409 `CARD_STATE_CHANGED`，不再覆盖已激活卡密。
- 保留已激活/已使用卡密不可删除、只能停用的原规则。

### 2.2 兑换操作完整原子化

兑换 batch 现在包含：
1. 卡密当前状态断言（管理员归属、days、normal、manual_disabled=0、未激活/未使用、expires_at 仍有效）。
2. 最终条件 UPDATE 卡密为 used。
3. INSERT app_entitlements。
4. INSERT OR IGNORE app_free_grants。
5. INSERT app_card_events 激活事件。

移除 batch 外 best-effort 的激活事件写入。若事件 INSERT 失败，整个兑换 batch 应失败回滚，不留下“已激活但缺少事件”的半完成状态。

### 2.3 回归测试

新增集成测试：
- 兑换成功时，卡密、授权、免费组资格与激活事件必须出现在同一批 D1 batch 中。
- 最终兑换 UPDATE 必须重新检查管理员归属、days、manual_disabled 和 expires_at。
- 模拟卡密删除时状态断言失败，必须返回 409 `CARD_STATE_CHANGED`，且不得执行 UPDATE。

新增静态回归约束：
- 用户 APP 卡密路由不得出现直接 `.run()` 写入。
- 兑换事件必须位于同一个 userBatch 中。
- 兑换批次必须重新检查有效期和手动停用状态。
