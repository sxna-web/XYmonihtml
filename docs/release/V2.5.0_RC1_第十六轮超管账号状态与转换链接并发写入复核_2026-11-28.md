## 1. 本轮发现

### 1.1 超管修改用户状态/角色/密码

原逻辑先读取用户 role/status，随后在 batch 中按 id 更新。如果并发请求在预读后改变目标用户状态，旧请求可能覆盖新状态；最后一个有效超管保护也依赖预读快照，需在最终写入处校验快照未变化。

### 1.2 单条转换链接重新分组

原逻辑先读取旧 group_name，再按 id 更新。并发修改后，旧请求可能覆盖新分组且审计 before 值不再对应实际前态。

### 1.3 单条转换链接撤销

原逻辑先检查 revoked_at，再按 id 更新。并发撤销/状态变化时缺少最终 active-state 条件，重复请求可能产生重复审计。

## 2. 已实施修复

- 超管用户 PUT 在同一批次首条断言中核对目标用户 id + 原 role + 原 status。
- 用户 UPDATE 增加 `WHERE id=? AND role=? AND status=?` 乐观并发条件。
- 若状态快照已变化，返回 409 `USER_STATE_CHANGED`；最后一个有效超管保护仍在同一批次内执行。
- 密码变更仍与会话撤销、审计保持同一批次；停用账号同步撤销会话。
- 转换链接 PATCH 分组增加旧 group_name 断言和最终 UPDATE 条件，归属状态变化返回 409。
- 转换链接 revoke 增加 revoked_at IS NULL 的同批次断言与最终 UPDATE 条件；重复撤销保留幂等成功。

## 3. 测试与静态回归

新增 3 项 handler 测试：
- 超管用户状态/密码更新的快照断言、会话撤销与审计同批次。

- 转换链接撤销的 active-state 断言、状态更新与审计同批次。

静态回归新增检查：用户更新必须保留 role/status compare-and-swap；转换链接重新分组必须检查旧 group_name；撤销必须检查 revoked_at IS NULL。
