## 2. 重点动态 SQL 与 spread 参数复核

### 2.1 同步 fencing / stage / commit

`FENCE_SQL` 固定包含 5 个占位符，`fenceBinds(lease)` 固定返回 5 项：

1. source_id
2. generation
3. lease_owner
4. lease_token_hash
5. 当前时间（lease_expires_at 比较）

已逐条核对下列组合：

| 位置 | SQL 结构 | 参数结构 | 静态组合结果 |
|---|---|---|---|
| `fenceAssert` | FENCE_SQL 5 | spread fenceBinds 5 | 5=5 |
| `stageNodes` | stage 4 + FENCE 5 | task/seq/key/payload 4 + fence 5 | 9=9 |
| 暂存计数更新 | 3 + FENCE 5 | seq/seq/taskId 3 + fence 5 | 8=8 |
| manifest 状态更新 | 4 + FENCE 5 | hash/count/count/taskId 4 + fence 5 | 9=9 |
| node_records set-based upsert | source/task 2 + FENCE 5 | source/task 2 + fence 5 | 7=7 |
| node_identity_aliases upsert | source/task 2 + FENCE 5 | source/task 2 + fence 5 | 7=7 |
| disableMissing 更新 | source 1 + FENCE 5 + task 1 | source 1 + fence 5 + task 1 | 7=7 |
| node_sync_logs 提交日志 | 固定 8 + FENCE 5 | 8 个业务值 + fence 5 | 13=13 |
| committed 状态更新 | 固定 3 + FENCE 5 | 3 个业务值 + fence 5 | 8=8 |

`assertStmt` 与动态 `conditionSql` 的占位符数量由调用者传入的 SQL/数组决定；本轮确认通用函数本身不能独立证明调用点配对，需由各调用点继续维护契约。

### 2.2 列表查询与动态筛选

逐项核对了以下构造路径：

- `buildNodeListQuery`：CTE 原始 binds、三个用户元数据子查询 UID、whereBinds、LIMIT/OFFSET；count 查询不带三个元数据 UID 与分页参数，select 查询使用 `slice(0,-2)` 后重新追加分页参数。
- 订阅来源流量查询：q/name/remark/profile_title 三个 LIKE 参数仅在 q 非空时加入；count 与 rows 共用过滤 binds，rows 另追加 LIMIT/OFFSET。
- APP entitlement 列表：status 过滤可选；count 与 rows 共享 status bind，rows 另加分页参数。
- convert_links 列表：group 过滤可选；count 与 rows 共享 group bind，rows 另加分页参数。
- 超管来源列表：q 为空时无过滤 bind，非空时追加两个 LIKE bind；count/rows 共享过滤参数，rows 另加分页参数。
- VIP 卡密列表：status 过滤可选，分页参数仅追加到 rows 查询。
- 节点生命周期列表：state 为空时空 bind 数组，非空时单个 state bind；SQL where 只替换一次字段名为 `l.state`。
- APP 卡密列表：status/from/to 按条件追加 SQL 和对应 bind；`unactivated` 条件不增加占位符。
- APP 卡密 CSV 导出：status 存在时绑定 adminId+status，否则只绑定 adminId。
- 管理节点列表：source_id/protocol/tier/enabled/q 条件逐个追加参数；count 与 rows 共用 where binds，rows 另追加 limit/offset。
- schema-status：表名占位符数来自 `allTables` 数组长度，并以 `bind(...allTables)` 逐项绑定。

上述动态查询的参数数量结构一致；仍需在隔离 D1/SQLite 兼容测试中使用真实输入组合验证执行结果。

### 2.3 条件分支 SQL

- 订阅源 URL 更新：URL 变化分支 SQL 有 7 个 bind；未变化分支 SQL 有 6 个 bind；代码分别按分支绑定对应参数。URL 变化时审批 INSERT 另行使用 2 或 3 个 bind。
- VIP 卡密激活：当前有效 VIP 续期分支 SQL 为 6 个 bind（旧到期时间 + 新增天数），非有效分支 SQL 为 5 个 bind；两个 bind 数组与 SQL 分支一致。
- 旧管理路由订阅源更新：URL 变化和未变化分支均绑定 6 个参数，差异仅在 SQL 是否将 enabled 设为 0。
- APP 卡密导出和过滤分支已按上一节核对。

## 3. 本轮发现的架构/业务边界（不是 bind 数量错误）

### 3.1 APP 多卡密分组聚合尚未实现

当前 `GET /api/app/nodes`：

- 按 device_id 查询一条最新的有效 entitlement；
- 校验该 entitlement 的 HMAC token；
- 使用该 entitlement 的 admin_user_id 查询管理员所有已分配、已批准、已启用来源的节点；
- 按来源名称形成分组。

该实现没有按 entitlement.card_id 关联卡密配置的 app_groups/app_group_sources，也没有聚合同一设备多个有效卡密的分组；同一管理员免费组去重、不同卡密同名分组序列号显示、多个管理员授权分别隔离也未实现。因此，用户确认的多卡密授权规则不能视为已完成。此项仍是 APP 正式功能验收阻断项。

### 3.2 APP 事件日志不与卡密核销主批次原子绑定

卡密状态更新、entitlement 创建、free grant 写入位于同一个 `userBatch`；随后 `app_card_events` 写入在主批次之后单独执行，并捕获失败。若事件日志写入失败，主授权可能已经成功但事件记录缺失。应在未来迁移/改造时明确审计日志是否必须与业务写入原子一致；本轮不擅自改变历史行为。

### 3.3 仍未获得真实 D1 schema

静态 bind 配对不代表数据库字段真实存在。B 类 22 张表的完整列类型、默认值、NOT NULL、UNIQUE、外键、索引仍需真实目标 schema snapshot 对照；没有 snapshot 前不生成猜测型迁移 SQL。
