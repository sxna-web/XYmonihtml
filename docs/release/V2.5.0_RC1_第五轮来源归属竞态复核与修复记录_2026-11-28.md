## 1. 发现的问题

用户态订阅源接口原先先通过 `loadSourceForCtx` 查询来源及归属，再执行启停、修改、归档。部分最终 SQL 仅使用 `WHERE id = ?`，没有在最终写入时重新约束当前归属。

如果超管在“前置归属检查”与“最终写入”之间将来源重新分配给另一位管理员，旧管理员持有的请求可能继续对来源执行修改或停用。归档操作还可能出现“来源已停用，但 ownership DELETE 因 user_id 不匹配而未删除新归属”的不一致。

这属于读写竞态/TOCTOU 权限问题，不是 bind 参数数量问题。

## 2. 修复范围

### 2.1 新增 sourceOwnerFence

新增统一 helper：

- 普通用户与协助会话：生成同批次内的 `assertStmt`，验证 `source_ownership(source_id, user_id)` 仍然匹配当前 `effectiveId`。
- 同时提供最终 SQL 的相关子查询 predicate，直接限制 `subscription_sources` 最终 UPDATE。
- 只有本人直接登录的超级管理员（`ctx.isSuper && actorId === effectiveId`）保留原有全局管理范围；协助会话不能绕过当前生效用户的来源归属。

### 2.2 三类用户态来源写入全部加 fence

- PATCH `/api/user/sources/:id/enabled`：归属断言、启用审批断言、最终 UPDATE owner predicate 同批执行；启用时最终 SQL 再次要求没有未批准/空状态审批记录。
- PUT `/api/user/sources/:id`：URL 变化与未变化分支均在最终 UPDATE 加 owner predicate；批次前置归属断言与业务写入同批。
- DELETE/归档 `/api/user/sources/:id`：最终停用 UPDATE 加 owner predicate；ownership DELETE 仍限制 source_id + 当前 effectiveId；归属变化时整批回滚并返回 409。

### 2.3 手动同步和 Cron 同步都将来源归属纳入 fencing

- 手动同步重新检查当前 owner 必须等于 `ctx.effectiveId`，本人直接登录超级管理员仍保留全局管理能力。
- 手动同步把确认的 `owner_user_id` 传给同步引擎。
- Cron 来源查询显式选择 `so.user_id AS owner_user_id`。
- `acquireLease` 在创建 task 前再次确认 owner；若已变化，立即释放本次 lease 并停止。
- `FENCE_SQL` 增加 owner 条件；stage、manifest、commit 中所有既有 fencing 检查都会再次核对当前 `source_ownership`。因此来源在抓取过程中被转移时，后续 stage/commit 不能继续写入该来源节点。

## 3. 回归检查

更新 `scripts/rc1_cron_no_source_regression.py`，增加静态门禁：

- sourceOwnerFence 必须存在批内 ownership assertion。
- enabled/update/archive 三条用户态来源变更都必须使用最终 SQL owner predicate。
- 手动同步必须传递 owner_user_id。
- Cron 查询必须带 owner_user_id。
- FENCE_SQL 必须再次验证 source_ownership。

第一次 CI Run #98（`46104062078`）失败原因是旧表名扫描器把注释中的英文短语 “UPDATE to close” 误判为表名 `to`，不是 Worker 编译错误。随后将保留字/误判项加入排除集合，并修正新断言对 scheduled block 的调用顺序。

第二次 CI Run #100（`46104107711`）因新增断言引用尚未赋值的局部变量 `block` 失败；已将断言改为调用 `scheduled_block(source)`。

最终 PR Run #102（`46104155565`）全部通过：

- isolated SQLite verifier tests

## 4. 尚未声称完成的事项

1. 本轮没有构造两个真实并发 D1 会话，执行“转移归属与旧请求同时提交”的压力测试；目前是代码路径修复 + 静态门禁 + 现有 Worker handler 集成测试。
2. 来源 URL 抓取和额度写入发生在同步 stage/commit 前；owner fence 阻断后续节点 stage/commit，但不能据此宣称所有早期 quota/日志副作用都被统一事务包裹。
3. 其他业务表/路由仍需独立检查相同的 read-check-write 竞态，不能把本轮三个来源变更入口的修复泛化为全站所有资源都已完成。
4. 生产 D1 schema、列/索引/约束、真实 D1 batch 行为仍未验证。
5. APP 多卡密分组聚合、管理员免费组去重、同名卡密分组序列号展示、24 小时 tombstone/cleanup acknowledgement 仍未闭环。
