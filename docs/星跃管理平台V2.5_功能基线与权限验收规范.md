## 0. 项目保护总则（最高优先级）

1. 本项目已有正式 Cloudflare D1 数据库和 Worker。不得另起一套无关系统，不得擅自重构替换现有架构。
2. 未经用户明确批准，不得创建、删除、迁移、重建、清空或重命名任何正式 D1 表、字段、索引、外键及约束。
3. 未经用户明确批准，不得部署生产 Worker、修改生产环境变量/密钥、执行破坏性 SQL 或改变线上数据。
4. 修改前必须先核对当前仓库源码、现有 D1 结构、Worker API、前端调用和部署配置；不能根据旧聊天内容推断当前代码状态。
5. 必须先形成影响分析、兼容方案、回滚方案和测试方案，再实施。优先最小范围、向后兼容的修复。
6. 不得删除或弱化已经确认的业务功能。若新规则与旧规则冲突，先列出冲突并请求用户确认，不得自行选择。
7. 不能把静态页面、模拟数据、前端隐藏按钮或未运行的代码说成已实现。每项工作标注：需求设计 / 已编码 / 已测试 / 已部署。
8. 所有权限必须在 Worker 服务端执行；前端隐藏菜单不是安全措施。
9. 所有敏感操作必须有审计记录；订阅凭证、令牌、卡密和密钥不得写入公开文档、普通日志或 Git 历史。
10. 用户主要通过手机操作。交付应尽量提供完整文件、明确路径、可复制内容和简短操作步骤，减少反复试错。

## 1. 身份与角色模型

普通用户等级只有三种：
- **L0：未注册用户**
- **L1：已注册普通用户**
- **L2：VIP 用户**

**超级管理员**为独立最高管理身份，不属于 L0/L1/L2 普通等级。

VIP 管理员不是第四种等级，而是 L2 用户中的管理身份。至少区分：
- 体验 VIP 管理员（体验身份）
- 正式 VIP 管理员（正式身份）

体验与正式 VIP 管理员在有效期内的核心 VIP 管理功能原则上相同。身份类型、会员状态、角色权限必须分开建模，不能把“体验/正式”误当成新的普通用户等级。

## 2. L0 未注册用户规则（已确认）

1. 未注册用户始终可以使用基础订阅转换，不得以强制注册、弹窗、广告、会员引导或人为错误阻断基础转换。
2. 仅当超级管理员明确按用户 ID 限制时，才可禁止该用户基础转换。
3. L0 可提交订阅源、执行基础转换、查看转换结果，并查看/复制自己转换的节点和批次。
4. L0 有默认节点分组；只能访问自己的转换结果、节点和批次。
5. 必须提供注册入口，并如实展示注册用户和 VIP 用户的权益差异。
6. 达到普通频率限流时，应提供额度恢复提示/等待时间，不应永久封禁基础转换；查看和复制已生成结果不因转换限流而禁用。
7. L0 的匿名身份应稳定；注册后如需关联匿名历史，必须通过安全验证和明确关联机制，不能把不同人的匿名数据错误合并。

## 3. 权限执行原则

权限至少分三层：
- 页面权限：前端展示哪些菜单和页面。
- 操作权限：Worker 服务端判断是否允许查看、创建、编辑、删除、复制、分享等动作。
- 数据权限：服务端查询必须校验记录归属、管理员边界、分组/批次/分享关系及状态。

每个敏感 API 必须检查登录身份、等级、管理身份类型、VIP 状态、操作类型、资源归属和资源状态。不得只靠前端隐藏按钮。管理员 A 不得通过猜测或替换 ID 访问管理员 B 的数据。

## 4. VIP 体验与正式身份规则

### 4.1 体验 VIP（已确认部分）

- 体验卡由超级管理员后台生成。
- 激活后体验期为 7 天。
- 有效期内体验 VIP 管理员可使用正式 VIP 管理员的核心管理功能。
- 体验到期后只能查看历史数据；不得新增、编辑或删除历史管理数据。
- “体验到期后能否复制历史数据”此前没有明确确认，必须按第 13 节待确认项处理；未确认前默认严格只读，不开放复制。
- 必须清晰展示体验期、到期状态、正式 VIP 的持续管理权益和正式购买入口。不得虚构倒计时、虚假稀缺或误导用户。

### 4.2 正式 VIP（已确认部分）

- 正式卡密激活后成为正式 VIP 管理员。
- 有效期内拥有完整正式 VIP 管理权限。
- 正式 VIP 到期后仍可查看和删除自己此前的历史数据；不能编辑、创建新的 VIP 管理业务数据或继续修改需要有效 VIP 的分享配置。
- 到期三天后，其个人购卡入口自动切换为公共百度链接。
- 重新成为有效正式 VIP 后，恢复原有业务管理权限、原数据及关联，不得新建空白后台。
- 到期后保留的删除权限只能作用于本人有权管理的历史数据，不得删除其他管理员或系统数据。

### 4.3 体验与正式 VIP 的产品引导

体验期内应让用户真实体验完整核心功能，并明确正式 VIP 的长期价值：
- 持续有效的管理权限；
- 持续管理分组、节点、分享和卡密；
- 正式购卡入口及其归属能力；
- 到期后恢复完整管理操作的能力；
- 正式会员权益和服务说明。

可以配置合理资源安全配额，但不得故意降低核心功能质量或制造虚假限制。营销提醒可配置频率；必要的会员状态通知不能被营销关闭选项屏蔽。

建议提醒节点：激活欢迎、体验中期权益介绍、到期前 2 天、到期前 1 天、到期状态通知。具体频率可配置。

## 5. 卡密生命周期

已确认规则：
1. 体验卡由超管生成，激活后提供 7 天体验 VIP 管理身份。
2. 正式 VIP 管理员过期时，其创建但尚未激活的卡密进入 3 天宽限期；宽限期结束后失活。
3. 已激活卡密不因管理员 VIP 到期而自动失效，按卡密自身有效规则继续使用。
4. 使用失活卡密不能正常激活或使用。
5. 管理员重新成为有效 VIP 后，因管理员到期而失活的卡密自动恢复。
6. 自动恢复只针对明确由管理员到期导致的失活原因（例如 `owner_vip_expired`）；超管手动撤销/封禁/作废、卡密自身过期等原因不得自动恢复。
7. 卡密状态变化必须记录原因、时间、操作者和关联管理员。
8. 到期边界、宽限期和激活/恢复必须使用服务器时间并具备原子性，防止并发激活和竞态。

建议状态模型（需结合现有数据库核查，不能直接据此改表）：
- 状态：unused / active / grace_period / inactive / revoked / expired
- 失效原因：owner_vip_expired / admin_revoked / card_expired

尚未确认：
- 体验 VIP 管理员创建的未激活卡密是否也采用独立 3 天宽限期。
- 同一用户是否严格限制只能领取一次体验卡；此前“一人一次、超管可审批重发”是建议，不是已确认硬规则。

## 6. 购卡入口规则（已确认）

- 每位 VIP 管理员自行从第三方购卡平台获取自己的购卡链接，并在星跃后台填写、保存。
- 该入口用于向其用户展示，维持管理员与用户的购卡来源归属。
- 建议放置在星跃 APP 下载页上方。
- 正式 VIP 管理员到期三天后，自动切换为公共百度链接。
- 管理员重新成为有效 VIP 后，恢复其自己的购卡入口。
- 体验 VIP 可预览正式购卡入口，但体验期间入口配置行为应服从超管配置。
- 第三方平台支付成功不能仅凭跳转链接认定；必须通过可信支付回调或人工核实确认到账。

## 7. 订阅转换、额度和数据归档

### 7.1 转换权限

- L0：基础转换。
- L1：基础转换及经授权的增强功能。
- L2：高级转换。
- 有效体验 VIP 管理员和正式 VIP 管理员均按 L2 的转换等级处理。
- VIP 管理员身份附加管理权限，不是独立用户等级。
- 具体高级功能分级矩阵（多关键词、正则、重命名、排序、多源合并、多目标批量转换等）仍需与现有实现和最终确认的权限矩阵核对，不能把旧建议自动当作已批准规则。
- 高级功能必须服务端鉴权。

### 7.2 转换限流建议（暂定建议值，不是已批准的不可变常量）

| 等级 | 每分钟 | 每小时 | 每天 | 同时任务 | 突发 |
|---|---:|---:|---:|---:|---:|
| L0 | 10 | 60 | 200 | 1 | 3 |
| L1 | 15 | 120 | 500 | 2 | 5 |
| L2 | 20 | 200 | 1000 | 4 | 8 |

这些数字必须结合真实 Worker/D1 负载、监控和用户行为校准。限流采用滚动窗口和服务端原子控制；不能只依赖 Worker 内存计数。重复 request_id 返回已有任务，不重复计费；失败且未实际执行的预占额度应按规则退还。429 响应应包含 Retry-After 或清晰恢复时间。

### 7.3 后台归档（已确认核心要求）

每次成功转换均须形成独立归档，不因订阅 URL 相同而覆盖旧记录。至少保存/关联：
1. 原始订阅源（原始 URL/内容、来源；敏感内容须加密和严格授权）；
2. 解析节点及属性；
3. 节点指纹和来源关系；
4. 转换批次；
5. 过滤规则、转换参数、目标格式；
6. 转换后的新链接；
7. 用户 ID、保存模式、时间和归档状态。

用户选择项准确命名为：**“仅本地保存（不参与用户云端同步）”**。说明必须明确：结果在当前浏览器保存、不参与用户端云端历史同步；平台仍按数据留存规则在管理后台归档。不得宣称服务器不保存或不上传。

后台超管可按用户、ID、URL、批次、时间和保存模式筛选，并按权限查看、复制、编辑（保留原始快照及修改历史）、清理记录。所有敏感查看、复制、编辑和清理操作必须审计。数据保留期限、删除政策及用户告知必须明确。

归档流程必须可恢复、幂等，不能转换成功后悄悄丢档。可采用任务状态/Outbox/重试机制；实际设计须先核对现有系统架构。

## 8. 节点分组和分享规则

分组类型至少区分：
- 普通分组；
- 转换分组；
- 星跃 APP 对接分组；
- 卡密授权分组。

已确认规则：
1. “接入星跃 APP”和“星链接”两类分享仅注册用户可使用。
2. 只有未过期的有效 VIP 管理员可以修改、增减、删除这两类分享。
3. 注册但非有效 VIP 的用户，以及 VIP 已过期管理员，对前两类只能查看，不能修改、增减或删除。
4. 普通链接遵守既定最低权限规则。
5. 星跃 APP 用户可通过 VIP 管理员身份 ID 获取管理员分享的免费节点分组；通过星跃 APP 卡密获取该管理员为该卡密配置的节点分组。
6. 免费分组和卡密分组均必须通过后台专门的星跃 APP 对接分享链接分享，普通网页链接不能替代。
7. 星跃 APP 对接分组（包括免费分组）被管理员删除，或改为其他类型分组时，其本地节点按既定规则在 24 小时内清空。
8. 删除/变更分组前需检查卡密授权、分享关系、正在使用的转换链接；建议使用可恢复删除和版本记录，具体回收站期限需配置并确认。
9. VIP 到期时限制分享管理操作；恢复有效后按原身份恢复。
10. 分组版本修改应保留版本、操作者、时间、节点差异；恢复旧版本应生成新版本而不是覆盖历史。

## 9. 公告、广告与运营中心

超级管理员后台设置独立“公告与广告管理”：
- 可分别针对 L0 未注册、L1 注册、L2/VIP 或全体用户投放；
- 可配置展示位置、起止时间、优先级、启停、跳转地址和频率；
- 可统计曝光、点击、注册成功，必须区分三种指标；
- 广告不得遮挡转换、结果和复制按钮，不得强制跳转，不得阻止 L0 基础转换；
- 广告服务异常不得影响核心转换；
- 必要的会员/数据状态通知与营销提醒分开管理。

## 10. 必须补充的后台保障模块

这些模块是建议纳入完整版本的保障功能，具体实现前要核查现有系统，避免重复建设：

1. **安全中心与操作审计**：登录记录、异常行为、账号冻结、敏感操作确认、数据变更前后对比、超管操作审计。
2. **数据备份与恢复中心**：自动备份、失败提醒、备份校验、恢复前预览、恢复审计。恢复不能未经检查直接覆盖正式数据。
3. **客服工单与申诉**：卡密、会员、转换、节点、分享等问题；按管理员数据边界隔离工单。
4. **订单与购买核对**：购卡来源、订单状态、卡密发放/激活、未到账申诉、重复发放检查；没有可信回调或人工核实不得确认支付成功。
5. **运行监控中心**：Worker、D1、API、转换成功率、失败率、并发、归档失败、定时任务和异常情况。
6. **系统配置中心**：等级额度、体验期限、宽限期、链接规则、广告规则、注册开关、维护模式等；修改前后值必须审计。
7. **数据隐私与凭证保护**：敏感 URL/令牌加密、日志脱敏、最小权限、访问审计、保留期限、删除申请及披露。
8. **维护与版本中心**：平台版本、API 版本、数据库结构版本、更新公告、升级记录、维护模式；升级前核对兼容性。

## 12. 强制验收测试清单

至少覆盖以下场景：
1. L0 可正常基础转换。
2. L0 访问 VIP 管理 API 被服务端拒绝。
3. 有效体验 VIP 可使用核心 VIP 管理功能。
4. 体验 VIP 到期后编辑历史数据被拒绝。
5. 正式 VIP 到期后可删除本人历史数据。
6. 正式 VIP 到期后删除其他管理员数据被拒绝。
7. 正式管理员到期后的未激活卡密按三天宽限处理。
8. 已激活卡密不因管理员到期而失效。
9. 超管撤销卡密不会因管理员恢复而自动恢复。
10. 正式 VIP 恢复后原权限、数据和关联恢复。
11. 星跃 APP 对接分组删除/改型后 24 小时清理规则生效。
12. local_only 记录后台归档但不进入用户云端历史。
13. 相同 request_id 重试不重复创建/扣额度。
14. 归档失败可恢复且不丢失成功结果。
15. 管理员 A 无法读取/修改管理员 B 的数据。
16. 超管敏感删除需要确认并留下审计。
17. 并发激活卡密不会重复激活或重复延长。
18. 宽限期边界和定时任务重复执行具备幂等性。
19. 直接调用 API、伪造身份字段、替换资源 ID 均不能绕过授权。
20. 前端和 Worker 修改不得破坏已有功能及数据库兼容性。

每项验收必须记录：测试环境、输入、操作、预期、实际结果、证据、结论。没有测试证据不得标记通过。

## 13. 待确认事项（不可擅自定为硬规则）

1. 体验 VIP 到期后是否允许复制历史数据。默认严格只读，等待用户确认。
2. 体验 VIP 管理员创建的未激活卡密到期后，是否有独立 3 天宽限期。
3. 同一用户是否限制只领取一次体验卡，及超管重发审批流程。
4. 客服工单哪些身份可提交，以及 VIP 管理员可处理的工单范围。
5. 自动备份频率、保留周期、异地副本和恢复演练周期。
6. L1/L2 高级转换功能逐项授权矩阵和最终限流值。
7. 分组回收站保留期限及永久清理条件。

## 14. 开发阶段顺序

阶段一：只读核查现有仓库、D1、Worker、前端和 API，输出差距与风险清单。
阶段二：身份、VIP 生命周期、卡密及服务端权限。
阶段三：转换、节点解析、归档、链接和数据生命周期。
