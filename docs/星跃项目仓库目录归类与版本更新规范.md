# 星跃项目仓库目录归类与版本更新规范

> 状态：已确认的仓库协作规则
> 生效日期：2026-11-27
> 适用范围：本仓库后续新增文件、源码更新、版本归档和文档维护

## 1. 总原则

1. 后续新增或上传的文件，必须先判断所属模块，再放入对应文件夹；不得长期散放在仓库根目录。
2. 更新已有模块或产品版本时，必须在该模块对应目录内新增/更新，不得把新版本随意放到根目录，也不得覆盖历史原始版本。
3. 原始交付包、历史版本和已确认基线应保留；新版本采用独立版本目录或明确版本文件名，保证可追溯、可对比、可回滚。
4. 文件移动前先核对目标路径、内容和 Git blob；二进制 ZIP/APK 不得使用只支持 UTF-8 文本的接口读取或重写。
5. 不得为了整理目录而修改源码内容、生产 Worker、D1 数据或部署环境。
6. 根目录原则上只保留 AGENTS.md、README.md、必要的仓库级配置文件，以及 docs/ 和各模块目录。

## 2. 目录约定

后续按实际项目内容逐步建立和使用以下目录；没有对应内容时不必空建：

- docs/：需求基线、权限规范、API 规范、数据库保护规范、审计报告、测试记录、发布说明。
- apk/source/：星跃 Android APK 源码及源码版本。
- apk/releases/：APK 发布产物、版本说明和校验信息；不得提交签名私钥。
- backend/worker/：Worker 源码，按正式模块/版本管理；生产部署前必须单独审批。
- backend/d1/：仅保存经过脱敏的 schema、迁移设计和只读核查资料；不得放真实数据库备份或用户数据。
- frontend/admin/：HTML 管理后台源码及版本。
- archives/original/：不可随意修改的原始交付文件、原始源码和历史基线。
- archives/legacy/：已停用或仅供对照的旧版本。
- tests/：自动化测试、测试数据模板和验收证据；禁止放真实用户数据、真实卡密或生产凭证。

现有目录名称若已由用户明确指定（例如 原始StarJump_V1点0_Final-zip-26-11-25-14:56/），应保留，不得擅自改名。

## 3. 版本更新规则

1. 同一产品的每个版本统一放在对应模块目录中，建议采用清晰版本路径，例如 apk/source/6.00.48/、frontend/admin/1.4.61/、backend/worker/版本号或发布批次/。
2. 若交付的是 ZIP，保留原始 ZIP 文件名，并在同一版本目录内放置；不要只解压后丢弃原包。
3. 修复已有版本时，先复制/建立新版本，不覆盖原始基线；记录修改摘要、文件清单、SHA-256（可行时）和测试结果。
4. 只有用户明确要求替换某个当前文件时，才原位更新；更新前读取旧版本并保留可恢复副本或 Git 历史。
5. 不同模块不能混放。例如 APK 源码不能放进 HTML 管理后台目录，Worker 不能放进 APK 版本目录。

## 4. 原始资料保护

- 原始StarJump_V1点0_Final-zip-26-11-25-14:56/ 当前作为原始 V1.0 文件归档目录，后续只读对照；如需修复，另建修订版本目录。
- 6.00.47、6.00.48 等 APK ZIP 在未完成安全、完整的二进制迁移前，保持原路径，不得因目录整理而丢失或损坏。
- 旧版 HTML、Worker、APK 和文档均不得仅因出现新版本而删除。

## 5. 安全与提交检查

每次新增、移动或更新文件前后检查：
- 是否放入正确模块目录；
- 是否误覆盖旧版本；
- 是否包含 API Token、密钥、签名私钥、真实订阅 URL、卡密、用户隐私或生产数据库；
- 是否保留必要的版本号、来源、日期和变更说明；
- 是否只修改了本次授权范围内的文件；
- 是否可以通过 GitHub 重新读取目标文件验证提交结果。

## 6. 例外

如 GitHub 接口不支持安全移动二进制文件，或无法确认文件完整性，应先保留原文件并说明阻塞，不得采用文本编码方式强行迁移。目录规划可以先记录，待有可靠二进制操作方式后再整理。
