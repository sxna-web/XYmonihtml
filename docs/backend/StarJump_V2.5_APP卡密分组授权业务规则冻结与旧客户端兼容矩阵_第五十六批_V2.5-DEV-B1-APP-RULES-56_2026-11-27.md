## 2. 从用户历史要求中确认的业务规则

以下均为用户此前明确表达的业务方向，不是本批自行发明：

1. **APP 用户可绑定多个管理员**：可激活多个不同 VIP 管理员发行的 APP 卡密，并分别取得各管理员授权；管理员身份 ID 与卡密是两种不同绑定入口。
2. **同一 APP 用户与同一管理员仅保留一条绑定关系**；绑定管理员数量不限。不同管理员授权必须隔离，不能把多个管理员的数据混成一个授权。
3. **管理员身份 ID 入口只取得该管理员免费分组**，不得取得该管理员的卡密专属分组。
4. **卡密入口取得两类权益**：
   - 该卡密明确配置的一个或多个 APP 卡密分组（用户明确表示卡密分组数量不限）；
   - 该卡密所属管理员的免费分组（仅当免费分组已开启且满足免费权益条件）。
5. 每位 VIP 管理员默认最多创建一个免费分组；免费分组可以关闭。超管可单个/批量授权管理员免费分组额度。
6. APP 用户首次激活卡密后，与发行管理员建立绑定关系；管理员 VIP 到期不解除已激活绑定，也不自动使已生效卡密/链接失效。
7. 管理员 VIP 到期当天降权；符合条件的未激活卡密进入 3 天宽限，宽限结束后因 `admin_vip_expired` 自动失活；管理员续费后只恢复这类自动失活卡密。人工停用、超管撤销/封禁/作废、卡密自身过期不能被续费自动恢复。
8. 已激活卡密自身有效期与管理员 VIP 生命周期分开处理；卡密自身到期、撤销或人工停用，按卡密自身状态执行，不与管理员 VIP 到期混为一类。
9. APP 对接分组（包括免费分组）被删除或改为其他类型时：服务端立即停止继续下发该失效分组；APP 本地该分组节点须在 24 小时内清理，其他分组不受影响。
10. 管理员变更分享配置后，APP 后续刷新应获取最新服务端配置；APP 专用分享不能用普通网页链接替代。

## 3. 卡密/身份/授权的边界冻结

| 场景 | 可取得的分组 | 是否形成卡密 entitlement | 规则 |
|---|---|---:|---|
| 管理员身份 ID 绑定 | 该管理员免费分组 | 否 | 不能取得卡密专属组 |
| 管理员 A 的卡密激活 | A 为该卡密配置的全部 card 分组 + 符合条件的 A 免费组 | 是 | 不得出现 B 管理员分组 |
| 管理员 A 与 B 分别发行卡密 | A、B 各自授权范围 | 各自独立 | 多管理员可并存，不混合 |
| 同一 APP 用户再次绑定同一管理员 | 不新增第二条同管理员绑定 | 不应重复创建 | 保持该管理员一条绑定关系 |
| 卡密过期 | 卡密授权失效；已获得的管理员免费资格是否永久保留，依已确认的免费 grant 规则单独判断 | 卡密 entitlement 到期 | 不可继续使用卡密专属组 |
| 管理员 VIP 到期，卡密已激活 | 已生效卡密授权不因 VIP 到期自动失效；免费 grant 已取得的资格不因卡密自身到期被回收 | 保持 | 不能因 VIP 到期误撤销已激活卡密 |
| 管理员 VIP 到期，卡密未激活 | 3 天宽限；期满自动失活 | 否 | 续费只恢复 `admin_vip_expired` 原因 |
| 人工停用/超管撤销/封禁 | 立即按撤销状态拒绝 | 失效 | 管理员续费不得恢复 |

**免费权益生命周期说明：** 历史规则明确“免费分组资格来自曾激活该管理员卡密，卡密过期不收回”。这意味着卡密自身过期不能删除已形成的管理员免费 grant。管理员 VIP 到期不影响已激活卡密/已生效链接；本批按“不自动撤销已取得的免费 grant”处理。未来管理员主动关闭免费分组、删除/改型免费分组时，按分组实时变更和 24 小时清理规则执行。

## 4. 分组授权和实时变更规则

### 4.1 分组类型边界

- `card`：只能通过指定卡密授权；卡密绑定关系决定可见范围。
- `free`：通过管理员身份 ID 或符合条件的卡密免费权益获得；不得把 free grant 误当成 card 分组。
- `public`：旧 Worker 的管理员维度可见模式，不等同于“所有卡密均已明确授权”。不得在新卡密模型中默认把管理员全部 public 组加入卡密授权。
- `assigned`：旧 Worker 的设备成员模式，不等同于卡密授权。不得因设备被加入 assigned 就扩大其他管理员/其他卡密权限。
- `normal` 或非 APP 专用类型：不能作为 APP 卡密授权组。

**卡密授权范围：** 只允许显式 card 关联 + 符合条件的管理员 free grant；public/assigned 不自动叠加。若历史某一明确产品流程需要额外叠加，必须有单独明确的业务授权，不得由实现默认扩大。

### 4.2 变更生效

- 管理员新增/移除卡密关联分组后，服务端后续刷新必须按最新配置下发；不得继续下发已撤销组的节点。
- 分组从 card/free 改为其他类型或被删除：服务端立即把该组标为不可授权并产生单调递增的授权 generation/tombstone。
- APP 联网同步时立即停止使用并清除该失效组节点，提交 acknowledgement。
- 离线 APP 无法被服务端即时强制删除，因此必须使用有期限的本地授权租约/缓存有效期，保证在最后一次有效同步后不超过 24 小时停止使用并清除失效组节点；不能把“等用户下次打开”当作 24 小时保证。
- 其他未受影响分组继续工作；不能全量清空所有管理员/所有节点。
- 删除/改型与重新创建同名分组必须使用稳定 group ID + generation，不能仅比较名称。

## 6. 仍需确认的最少业务边界

下列事项在历史用户原话中没有找到足够明确的最终决定，本批不替用户拍板：

1. **同一卡密允许激活的设备数量**：已确认一个 APP 用户可绑定多个不同管理员，且同管理员只有一条绑定关系；但未找到用户明确规定“同一张卡密最多一台设备”或具体设备上限。不能把旧 Worker 的 `device_id` 字段当作业务上限。
2. **空分组卡密能否激活**：已确认卡密必须配置对应分组的产品方向，但没有明确说“未配置分组必须拒绝激活”。若管理员免费组开启，是否允许只取得免费组，需要用户确认。
3. **激活后编辑卡密分组的适用范围**：历史上确认后续刷新读取最新配置；未明确是否追溯影响所有已激活设备，还是仅新激活设备。推荐实时应用到该卡密全部仍有效 entitlement，撤销组立即停止下发并走 24 小时清理，但须用户确认后冻结。
4. **卡密自身过期后，之前获得的管理员免费 grant 是否永久保留**：历史明确卡密过期不收回免费资格；本批按保留 grant 处理，但如果管理员主动关闭/删除免费组则停止继续提供该组。
5. **VIP 到期 3 天宽限的起止时刻**：确认有 3 天宽限，具体以管理员 VIP 到期时间精确计算还是按自然日结束，仍需与现有 Worker 时间实现统一；不得用模糊日期比较。

### 推荐新协议字段（提案，不代表已批准实现）

- 每个授权实例必须可独立识别：`entitlement_id`、`admin_user_id`、`card_id`、`device_id`、`expires_at`。
- 服务端根据 Token/会话验证 entitlement，不信任客户端提交的 admin_user_id/card_id。
- 分组响应携带 `group_id`、`group_type`、`generation`、`enabled`、`lease_expires_at`。
- 增量同步返回变更游标或 generation；撤销/删除/改型返回 tombstone。
- APP 回报 `entitlement_id`、`group_id`、已应用 generation、清理结果、ack 时间。
- 同一设备多管理员授权必须分别请求/缓存/呈现，不能用“最新一条 entitlement”覆盖其他管理员。
- 为兼容旧调用方，旧 API 的既有字段不得无预告删除；新增字段应可选。但旧客户端若无法携带/保存多 entitlement 上下文，不得通过服务端放宽鉴权迁就它。必要时以明确 API 版本区分，并让旧客户端仅保留已验证的旧权限范围。
