## 1. 本批目的与边界

将已由用户明确的卡密、免费组、多管理员、设备数和 VIP 生命周期规则固化为实现约束，避免后续 Worker/HTML/APK 各自解释。本文不是 D1 migration、不是 API 实现，也不代表客户端已兼容。

## 2. 已冻结规则

### 2.1 卡密和分组授权

1. 每张 APP 卡密的卡密分组配置独立；一张卡密可以绑定零个或多个其所属 VIP 管理员名下、启用且类型为 APP card 的分组。
2. 空分组卡密允许激活；空配置不得隐式扩大成该管理员全部分组。其卡密分组结果就是空集合。
3. 卡密分组只能来自该卡密所属管理员，不能跨管理员绑定。
4. 卡密授权只授予卡密明确配置的 card 分组，不得把普通网页分享、普通转换分组或其他管理员的组当作卡密组。
5. 免费组是独立授权来源。卡密是否包含免费组由管理员对该卡密的配置决定；免费组资格必须单独验证，不能因卡密为空组就自动获得，也不能将免费组写成卡密组。
6. 同一 APP 用户同时持有同一管理员多张有效卡密时：每张卡密分别提供自己的卡密组；该管理员的免费组最多聚合一份。
7. 同一用户持有多个管理员的授权时，各管理员范围独立。按管理员 + 分组 ID 去重免费组，不允许把 A 管理员的免费组/卡密组授权给 B 管理员。
8. 同名卡密分组应保留各卡密实例，并显示非敏感卡密序列号后缀，例如“香港节点（序列号-001）”。不得向 APP 返回可兑换的卡密明文。
9. 卡密撤销、人工停用、作废、到期等状态只影响对应卡密 entitlement；不得连带取消同设备其他仍有效卡密或其他管理员的授权。
10. 管理员 VIP 到期不自动使已经激活的 APP 卡密 entitlement 失效；卡密自身生命周期仍按卡密状态执行。

### 2.2 VIP 管理权限

| 管理员状态 | 查看本人历史卡密/配置 | 新建卡密 | 修改卡密分组 | 删除本人历史卡密 |
|---|---:|---:|---:|---:|
| 有效正式 VIP | 是 | 是 | 是 | 按既定删除规则 |
| 有效体验 VIP（7 天） | 是 | 是 | 是 | 按授权范围 |
| 正式 VIP 到期 | 是 | 否 | 否 | 是 |
| 体验 VIP 到期 | 是（只读） | 否 | 否 | 否 |

- 体验管理员到期后严格只读，不得修改历史数据。
- 正式 VIP 到期后可以查看、删除自己此前的历史数据，但不能新增或修改 VIP 管理数据。
- 超级管理员按超管权限管理，但跨管理员操作必须明确目标管理员并审计操作者、目标、对象和变更原因。

### 2.3 设备数

- 默认每张 APP 卡密最多绑定 1 台设备。
- VIP 管理员可自行调整每张卡密设备上限，最高 5 台；超过 5 台须由超级管理员处理。
- 设备占额必须按卡密维度计数，不得用 entitlement 最新记录或 device_id 总数代替。
- 设备槽位释放/解绑审批的完整规则尚未冻结；实现前不得自行释放已占用槽位，也不得擅自制定自动释放期限。

### 2.4 身份 ID 与免费组

- APP 身份 ID 用于取得对应管理员的免费分组，不等价于卡密，也不应产生卡密专属 card 组。
- APP 卡密用于取得该卡密配置的卡密组，并可按该卡密独立配置是否附带免费组。
- 同一管理员多卡密时免费组只聚合一份；不同管理员的免费组分别保留。
- 设备免费授权必须与管理员公开免费分享区分，不能把公开分享接口的可访问性当成设备已获授权的证据。

### 2.5 节点变更同步

- 分组/节点删除或类型变更必须先更新服务端授权 generation/tombstone。
- APP 增量同步收到撤销信息后，须在 24 小时内清理本地对应数据，并发送 cleanup ACK。
- 重复 ACK、乱序同步、旧 generation ACK 不得覆盖新状态；租约/ACK 必须绑定设备与授权范围。
- 当前隔离模块尚未实现完整持久化 tombstone、真实 APK 本地清理和 ACK 传输，不得标记为已完成。

## 3. 授权结果矩阵

| 授权输入 | 可返回的分组 | 禁止行为 |
|---|---|---|
| 仅身份 ID | 对应管理员的免费组 | 返回任何卡密专属组 |
| 单张有效卡密 | 该卡密配置的 card 组；若卡密配置附带免费组，则另加该管理员免费组 | 返回管理员全部 card 组 |
| 同管理员多张有效卡密 | 每张卡密各自 card 组 + 该管理员免费组一份 | 只取 latest entitlement；把卡密组相互覆盖 |
| 多管理员多张有效卡密 | 每个管理员各自的卡密组和免费组，按各自范围去重 | 跨管理员合并授权、错配 owner |
| 空分组有效卡密 | 空 card 组；如单独配置允许，仍可取得免费组 | 自动放宽为管理员全部分组 |
| 某一张卡密撤销/过期 | 只移除该卡密贡献的组 | 影响其他有效卡密或其他管理员 |
| 管理员 VIP 到期但 APP 卡密仍有效 | 按已激活 entitlement 和卡密状态继续授权 | 因管理员 VIP 到期而批量停掉既有 APP 卡密 |

## 4. 服务端必须满足的安全条件

1. 先验证设备身份，再验证每个 entitlement 的 token；不得只凭 device_id 枚举授权。
2. 每个 token 必须精确绑定 entitlement_id + device_id；多卡密请求中的每个 entitlement 独立验证。
3. entitlement 的管理员、卡密、设备、卡密状态必须由服务端记录解析，不能信任客户端传入 admin_user_id、kind、card_id 或序列号。
4. CARD/IDENTITY 类型由可信服务端数据分类；现有 entitlement 表未确认存在通用 kind 字段，不能假设该列存在。
5. CARD entitlement 通过 card_id → card-group mapping → app_groups 建立授权；关联、卡密和分组管理员必须一致，分组必须启用且类型正确。
6. free grant 独立验证，按 admin_user_id + group_id 去重。
7. nodes 必须受当前 entitlement 的允许 group IDs 限制，不能使用管理员所有来源或其他卡密的 group union。
8. 任何关联查询、owner 检查、启用状态、授权版本或数据加载失败均 fail closed。
9. 不能在旧 /api/app/status、/groups、/nodes、/links 上未经 APK 协议确认就强制增加 token gate 或改变响应结构；新协议先隔离并做兼容矩阵。
10. 卡密序列号展示标签必须是服务端派生的非敏感标识；绝不使用 redeem code。

## 5. 已知实现缺口

- 正式 Worker 没有已核实的 app_card_groups 生产关联表/接口。
- 现有 HTML 的卡密分组管理是本地模拟数据，页面权限和服务端 VIP 自主管理入口尚未完成真实闭环。
- Batch 59/60/64/65 是隔离模块；Batch 65 尚无生产 D1 SQL adapter、真实 entitlement resolver/classifier 注册和正式 Worker route。
- 当前旧 APP API 存在 latest-only 读取和 token gate 不一致问题；不能在未验证旧 APK 的前提下直接改协议。
- 6.00.47 源码未发现现有 entitlement API 调用证据；6.00.48 尚未完成可读源码审计。APK 客户端协议状态保持 APK_PENDING。
- 生产 D1 实际 schema、列、索引、约束及数据分布未核实；本仓库 CORE-MIG-001 只是本地 verifier ledger bootstrap，不是生产业务 schema。

## 6. 仍未冻结、不得擅自决定的事项

1. 设备槽位何时释放、是否需要管理员审批、设备丢失/换机如何处理。
2. 卡密分组在卡密激活后修改时，已绑定设备何时生效；需结合 generation/ACK 规则做向前兼容设计。
3. 卡密删除/软删除时，历史 entitlement、审计和关联记录的保留期限。
4. 身份 ID 设备免费授权与管理员公开免费分享之间的历史兼容细节。
5. 旧 APK 是否支持多 entitlement 凭据、token 安全存储和增量清理 ACK；必须取得可读 APK 源码或真实协议证据。

以上事项在取得证据前，保持 fail-closed 或旧版兼容，不引入破坏性行为。

## 7. 测试验收矩阵

- 多卡密同管理员：card groups 各自独立，free groups 一份。
- 多管理员：owner 严格隔离；同名组展示不同安全序列号标签。
- 空卡密组：可激活但不得扩大授权。
- 卡密 A 撤销：卡密 B 与其他管理员授权仍有效。
- 过期、手动禁用、撤销、作废：状态分别验证，不可错误恢复。
- VIP 正式到期/体验到期：读写权限差异覆盖。
- 设备数 1、管理员调到 2–5、超 5 需超管；并发预约不超额。
- token 错误、entitlement 与 device 不匹配、跨管理员、重复 entitlement、恶意映射、owner mismatch：全部拒绝。
- nodes 只返回当前 entitlement 的允许组来源。
- tombstone/generation/24h cleanup/ACK：乱序、重放、过期租约、重复 ACK。
- 旧 API 与 APK 兼容：未升级客户端不获得权限扩大，既有功能不因新增字段失效。
