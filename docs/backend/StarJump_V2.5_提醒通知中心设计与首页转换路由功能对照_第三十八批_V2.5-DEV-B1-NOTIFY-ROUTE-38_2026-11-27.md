- 批次：第三十八批
- 版本标识：`V2.5-DEV-B1-NOTIFY-ROUTE-38`
- 日期：2026-11-27
- 状态：静态源码核查 + 通知中心设计 + 路由归并决策；未修改 HTML/Worker；未执行 D1；不可部署
- 基线：`星跃模拟后台 1.4.61.html`（blob `d046f71caa5af96b0c0978013771cb0a8f101739`）
- 关联：第三十四批 UX 规范、第三十五批首页差距、第三十六批 NAV/RBAC、第三十七批重复入口治理
- 用户特别强调：提醒功能很重要，必须作为正式产品能力规划，而非仅保留一个通知铃铛。

## 1. 本批结论摘要

1. 现有通知中心只是由当前前端状态即时拼出来的通知列表，没有完整的持久化通知记录、已读/未读、确认处理、稍后提醒、用户通知偏好、通知投递记录和跨设备同步。
2. 现有通知源覆盖失败任务、未解决诊断、订阅同步失败、后台 VIP 到期、管理员待审核、新生成未激活卡密；但缺少 APP 授权/设备/卡密生命周期、版本发布、系统迁移、重要安全事件等正式事件类别。
3. 当前通知数量角标代表列表条数，不代表未读数；用户关闭弹窗后通知仍会再次出现，容易造成重复提醒和提醒疲劳。
4. 现有卡密通知描述会包含卡密 code，属于不必要的敏感信息暴露，应改为批次/卡密尾号或数量摘要，完整信息只能在授权页面查看。
5. 首页 `dashboard` 与 `v1-overview` 不是完全相同的页面：前者偏工作台/访客基础体验，后者偏星跃服务运营概览。目标应是一个统一首页工作台，按角色与权限组合模块，而不是粗暴删除其中一页。
6. `convert` 与 `v1-converter` 是不同成熟度/流程的转换界面：前者是较完整的转换工作区，后者是简化的节点粘贴、格式生成体验。目标是统一转换入口和工作区外壳，提供“基础转换 / 高级转换”模式，不应未经功能对照就删掉任一能力。

## 2. 现有提醒能力的静态核查

### 已发现的实现

- `getNotifications()` 在源码约 198 KB 处动态生成通知。
- `renderTopbar()` 在顶栏显示铃铛和角标。
- `openNotifications()` 打开“通知中心”弹窗，点击项目跳转对应页面。
- 当前通知数据由 `visibleTasks()`、`DB.diagnostics`、`tenantSources()`、当前管理员 VIP 状态、待审核管理员、`visibleCards()` 即时拼装。
- VIP 到期另有顶部横幅提醒。
- `toast()` 仅用于短暂操作反馈，不应代替持久通知。
- 页面右侧快捷工具和首页活动/最近操作区不是正式通知收件箱。

### 当前通知类型

| 现有类型 | 触发依据 | 当前目标页面 | 主要问题 |
|---|---|---|---|
| 任务失败 | 可见任务 status=failed | 任务中心 | 无已读/处理状态、仅取部分 |
| 故障诊断 | 当前管理员未解决诊断 | 故障诊断 | 无升级、确认和关闭流程 |
| 订阅同步失败 | 启用订阅源 syncStatus=error | 订阅源管理 | 可能反复重复提醒 |
| VIP 已过期 | 当前管理员 VIP 无效 | 后台 VIP | 已有横幅，可能重复 |
| VIP 即将到期 | 剩余天数 <= 3 | 后台 VIP | 缺少可配置的提前提醒档位 |
| 管理员待审核 | 超管可见 pending 管理员 | 管理员管理 | 需要审核任务和通知状态分离 |
| 新生成卡密未激活 | 生成后三天内未激活 | 卡密管理 | 提醒对象/收件人范围不够明确，且当前描述暴露卡密 code |

### 当前能力缺口

- 无通知持久化实体和唯一事件 ID。
- 无 read/unread、已确认、已处理、已归档状态。
- 无同一事件去重键、频率限制、合并摘要。
- 无通知设置页、类别开关、提醒时间和免打扰。
- 无按接收人、角色、管理员租户和资源归属过滤的完整模型。
- 无通知投递渠道记录和失败重试。
- 无通知中心独立页面，当前仅弹窗，不适合长列表、筛选和历史追溯。
- 无服务端事件生成与权限校验；当前页面是本地模拟系统，不是生产通知能力。

## 3. 通知中心产品结构

### 3.1 三层提醒，不能混为一谈

1. **即时操作反馈（Toast）**：例如“已保存”“复制成功”。持续短暂时间，不进入重要通知计数。
2. **站内通知（Notification Inbox）**：需要用户之后查看或处理的事件，持久保存，支持已读、未读、确认、稍后提醒和跳转。
3. **强制安全/风险提示（Critical Banner / Blocking Dialog）**：高风险且必须知晓的事项，例如账号停用、权限撤销、危险迁移失败。不能只放在普通通知列表里，也不能被普通免打扰屏蔽。

站内通知不能替代业务页面上的状态提示；业务状态也不能仅靠通知传达。

### 3.2 通知中心入口

- 顶栏铃铛：显示未读数量，不显示总通知数量。
- 点击铃铛：打开简洁预览，默认显示未读和高优先级，可一键进入完整通知中心。
- 完整通知中心：独立 route `notifications`，支持全部/未读/待处理/已归档、类别筛选、搜索、时间排序。
- 手机端：全屏或近全屏页面，顶部筛选，列表卡片化，底部/卡片内操作易于单手点击。
- 桌面端：主内容区通知列表，右侧可显示详情/处理说明。
- 首页：只展示最重要的 3-5 条待处理提醒，不能把通知列表完整复制到首页。

### 3.3 每条通知字段

建议数据模型（设计稿，尚未写入 D1）：

| 字段 | 用途 |
|---|---|
| id | 全局唯一通知 ID |
| event_key | 业务事件幂等键，用于去重 |
| recipient_type / recipient_id | 明确接收人或角色 |
| tenant_admin_id | 管理员租户范围 |
| resource_type / resource_id | 关联资源，不在通知文本中泄露秘密 |
| category | vip/app/card/device/node/sync/task/security/system/release |
| severity | info / success / warning / critical |
| title / summary | 短标题与脱敏摘要 |
| action_route / action_label | 允许访问的处理入口 |
| status | unread / read / acknowledged / resolved / archived |
| created_at / updated_at | 创建与更新时间 |
| due_at / remind_at | 截止时间与下次提醒时间 |
| snoozed_until | 用户稍后提醒时间 |
| dedupe_until | 去重窗口 |
| source_event_id | 来源业务事件 |
| metadata_json | 非敏感上下文；严禁放 Token、卡密、密码、完整订阅 URL |

服务端必须根据当前 session 计算 recipient 和 tenant，不能相信前端传入的管理员 ID、资源 ID 或通知路由。

## 4. 通知分类与事件规则

### P0：必须及时提醒

| 类别 | 事件 | 接收人 | 建议级别 | 默认处理入口 |
|---|---|---|---|---|
| 账号安全 | 管理员账号停用、封禁、权限被撤销 | 受影响账号；超管审计 | critical | 我的 / 安全记录 |
| APP 授权 | APP 管理授权新增、撤销、变更 | 对应管理员及被授权人（按规则） | warning | APP 管理 / 授权 |
| APP 设备 | 新设备绑定、设备达到上限、设备解绑/异常 | 对应 APP 用户；有权管理员可查看 | warning | APP 用户 / 设备 |
| 卡密生命周期 | 卡密激活、失效、宽限期将满、被人工撤销 | 卡密所属管理员；必要时用户 | warning | APP 管理 / 卡密 |
| 节点同步 | 同步失败、连续失败、数据异常 | 节点所属管理员 | warning / critical | 节点 / 同步记录 |
| 任务 | 后台任务失败、长时间卡住 | 任务所有者和授权运维角色 | warning | 任务中心 |
| 数据库/系统 | 迁移失败、结构冲突、环境异常 | 超管本人会话 | critical | 数据库 / 故障诊断 |

### P1：需要计划性提醒

| 类别 | 事件 | 建议提醒节奏 | 默认处理入口 |
|---|---|---|---|
| 后台 VIP | 到期前 7 天、3 天、1 天、到期当天 | 每个阶段最多一次；到期后状态变化通知一次 | VIP / 续期 |
| APP 卡密 | 未激活卡密临近 3 天宽限期边界 | 到期前提醒一次；状态变化通知一次 | 卡密详情 |
| APP 版本 | 新版本发布、强制更新策略即将生效 | 发布时通知目标用户；强制策略另发高优先级 | APP 版本 |
| 管理员审核 | 新申请待审核、审核超时 | 超管待办摘要；避免每次刷新重复生成 | 管理员审核 |
| 订阅源 | 长时间未同步、即将过期（若来源提供有效期） | 可配置阈值，按源去重 | 订阅源 |

### P2：一般信息

- 新功能说明、普通版本更新、系统维护公告。
- 转换任务成功摘要（默认可关闭，避免频繁打扰）。
- 统计周期报告和低优先级运营提示。

### 明确不应通知的情况

- 页面每次打开或每次刷新都重新生成同一通知。
- 同一失败状态未发生变化时重复发送多条。
- 无法确认接收人的跨租户事件。
- 用户无权查看的资源详情。
- 单纯 Toast 操作反馈。
- 未经确认的猜测性“在线”“异常”状态。

## 5. 提醒去重、升级与生命周期

### 5.1 去重键

建议按业务对象生成稳定 event_key，例如：
- `task.failed:{task_id}`
- `subscription.sync_failed:{source_id}:{failure_generation}`
- `vip.expiry:{admin_id}:{expiry_date}:{threshold_days}`
- `app.device_bound:{user_id}:{device_id}:{binding_generation}`
- `app.card.grace:{card_id}:{expiry_generation}`

相同 event_key 在同一生命周期内只生成一条通知。若事件恢复后再次失败，应生成新的 failure_generation，而不是永久吞掉后续告警。

### 5.2 状态流转

`unread → read → acknowledged → resolved → archived`

- read：用户打开/查看。
- acknowledged：用户明确知道并接手处理。
- resolved：业务问题已被系统或授权人员解决。
- archived：用户归档历史通知。
- snoozed：只改变下次提醒时间，不改变业务问题状态。
- critical 通知不能因为用户点“已读”就被标记为已解决。

### 5.3 频率与合并

- 同一事件首次出现立即通知。
- 未解决期间不重复推送相同内容；按配置在合理间隔发送摘要或升级提醒。
- 多个同类订阅失败可合并成“3 个订阅源同步失败”，进入详情查看具体源。
- 严重级别升级时重新提醒，例如连续同步失败从 warning 升级 critical。
- 恢复后发送一次恢复通知，并结束该事件提醒周期。

## 6. 提醒偏好与免打扰

用户可按类别配置：
- 站内通知开关。
- 是否在首页显示摘要。
- 是否允许浏览器/系统推送（未来能力，需用户明确授权）。
- 提醒提前量（如 VIP 7/3/1 天）。
- 免打扰时间段与时区。
- 摘要频率（实时/每日摘要）。
- 稍后提醒选项（30 分钟、2 小时、明天、指定时间）。

限制：
- critical 安全通知和必须处理的系统风险不受普通免打扰屏蔽；可以静音声音，但仍要在页面明显显示。
- 免打扰以用户配置时区为准，不能用服务器时区误判。
- 不提供默认短信/邮件发送；若未来接入邮件、推送等外部渠道，需先明确数据用途、用户授权和投递失败处理。
- 访客只接收与本人访客会话相关的必要提示，不展示管理员或其他用户通知。

## 7. 首页与转换页面对照结论

### 7.1 `dashboard` vs `v1-overview`

静态源码对照：
- `dashboard`：访客分支明确展示基础转换、默认节点分组、本人转换记录、注册/VIP 权益；非访客部分是原管理工作台。
- `v1-overview`：展示星跃服务后台概览、在线统计、配额使用、APP 与授权模块、系统维护模块等运营入口。

决定：
- 不把其中一个直接删除。
- 新首页 canonical route 建议统一为 `home`。
- 将 dashboard 的任务工作台能力与 v1-overview 的服务运营摘要拆成可配置模块。
- 按访客/注册/VIP/超管身份、APP entitlement、协助会话权限组合展示模块。
- 访客首页保留基础转换、默认分组、本人批次、注册入口。
- 有权限管理员首页展示待处理提醒、资源概览、APP 工作台摘要、节点/同步状态和最近工作。
- 超管首页可额外展示系统环境、迁移状态、全局待审核和审计摘要。
- `dashboard` 与 `v1-overview` 先作为兼容 alias/旧页面入口，只有新首页覆盖旧功能并通过角色测试后才做 redirect。

### 7.2 `convert` vs `v1-converter`

静态源码对照：
- `convert` 注册到 `renderConv`，提供较完整转换工作区，支持方案/模板/过滤/高级选项等更完整的管理流程。
- `v1-converter` 提供更直接的粘贴节点、选择输出格式、快速生成/解析流程；访客模式有明确限制与自己的默认分组/批次入口。
- `v1-converter` 页面明确说明当前前端不抓取外部订阅、不运行真实 subconverter，真实配置需 Worker/转换内核。
- 两者不能被认定为完全同一页面，也不能把模拟能力误认为真实服务能力。

决定：
- 一级入口统一为 `convert`（canonical route 建议）。
- 页面内提供两个清晰模式：“基础转换”和“高级转换”。
- 访客只进入基础转换模式；注册/VIP 权限决定高级模式中具体能力，不能因为统一入口而扩大权限。
- 保留 `v1-converter` 作为旧 route alias，初期可带 `mode=basic`；`convert` 默认根据用户权限选择合适模式。
- 迁移时保留原页面有价值的快捷生成体验和高级工作区的模板/过滤能力；需要逐个核对表单字段、数据保存、结果格式、导出、限制和错误反馈。

## 8. 通知与导航的关系

- 通知中心是独立业务页面，不塞进 APP 管理、系统管理或“我的”子页面。
- 顶栏铃铛是全局入口；手机端也必须可触达，不得被底部导航遮挡。
- 每条通知 action_route 必须经过服务端能力授权；用户无权访问时展示权限说明，不得泄露资源详情。
- 通知跳转到业务页面后，应保留来源通知 ID，用户完成处理后回到通知中心能看到状态变化。
- APP 相关通知只对拥有对应 APP 用户/卡密/设备资源权限的人可见；超管协助会话默认降权，不自动继承超管全局通知。
- 通知记录必须与操作审计分开：通知可读/归档，审计记录不可被普通用户删除或篡改。

## 9. 安全、隐私与可观测性

- 不在通知标题、摘要、推送 payload、日志中写完整卡密、Token、密码、订阅 URL、设备敏感标识。
- 对象授权必须在 Worker 端按 recipient、tenant_admin_id、resource owner 和 capability 重新验证。
- 通知列表接口必须分页、限流、字段白名单，不能将其他租户通知返回前端后再隐藏。
- 关键事件应在业务事务提交成功后生成通知；失败事件要有明确的 event ID 和恢复生命周期。
- 发送通知失败不能回滚已经成功的业务操作；应写入可重试投递记录。
- 数据库迁移应遵循第三十三批迁移执行器设计：检查 → 计划 → 超管确认 → 执行 → 结构复核；本批没有执行任何 DDL。
- 日志诊断开关应脱敏，禁止记录通知 payload 中的敏感信息。

## 10. 实施阶段与验收

### 阶段 A：通知模型与页面（先开发、后测试）
- 定义通知类别、severity、event_key、recipient、状态机。
- 增加独立通知中心 route 和移动端通知列表。
- 顶栏角标改为未读数。
- 实现已读、全部已读、确认、稍后提醒、归档、跳转。
- 添加通知偏好设置。

### 阶段 B：业务事件接入
- VIP 到期事件。
- APP 卡密生命周期和 3 天宽限期边界提醒。
- APP 用户/设备/授权变化。
- 订阅同步与任务失败。
- 管理员审核、版本发布和系统诊断。
- 逐类验证通知对象、租户隔离和去重。

### 阶段 C：投递与运维
- 站内实时更新/轮询策略。
- 浏览器推送作为可选增强，必须用户授权。
- 投递重试、事件恢复、失败告警。
- 通知留存和归档策略。

### 必测场景
- 同一事件重复刷新/重复执行只生成一条通知。
- 同一事件恢复后再次失败会生成新一轮提醒。
- 管理员 A 永远看不到管理员 B 的资源提醒。
- 普通 VIP、过期 VIP、体验 VIP、APP 管理授权、超管本人、超管协助会话均符合权限矩阵。
- 点击已读不等于解决；稍后提醒不会丢失。
- VIP 7/3/1 天提醒只按配置触发一次。
- 卡密通知不泄露完整 code；设备通知不泄露不必要的设备标识。
- 免打扰不屏蔽关键安全风险。
- 手机端 360×800 / 390×844 / 430×932 可单手查看与处理。
