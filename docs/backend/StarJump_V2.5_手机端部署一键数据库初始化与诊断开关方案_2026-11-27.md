# 星跃 V2.5｜手机端部署、一键数据库初始化与诊断开关操作方案

- 日期：2026-11-27
- 适用项目：星跃管理平台 V2.5（现有 Cloudflare Worker + D1 + HTML 管理后台 + 星跃 APK）
- 性质：部署与运维工作流设计；不是已实现功能声明。
- 安全边界：本方案不授权直接修改生产 Worker、D1、Secrets 或部署环境。

## 1. 用户希望采用的交付方式

后续由 AI 负责准备完整、可部署的文件和清晰的版本包；用户主要通过手机完成上传、部署和后台点击操作，不要求用户手工编写 SQL 或逐条创建数据库表。

目标操作流程：

1. AI 检查现有仓库、Worker、HTML、D1 字段映射和 APK 接口边界。
2. AI 生成完整、相互匹配的 Worker、管理后台文件、迁移脚本、配置说明、测试清单和版本说明。
3. 用户按步骤上传/部署指定文件。
4. 用户登录超管后台，进入“系统维护 → 数据库”。
5. 页面先显示当前 D1 绑定、迁移版本、已存在表/字段、待执行变更和风险摘要。
6. 用户点击“检查数据库”，系统只读检查，不写入。
7. 检查通过后，用户点击“一键初始化/升级数据库”，Worker 在服务端执行已审核、版本化、幂等的迁移。
8. 页面展示每一步成功/失败、执行耗时、迁移编号和可复制错误编号。
9. 用户进入“系统诊断”，按需打开某个模块的诊断开关，复现问题后查看脱敏日志；问题定位后关闭开关。

## 2. 一键数据库管理设计

### 2.1 页面功能

超管后台新增“系统维护 → 数据库”页面，至少包含：

- 当前数据库环境标识（必须明确显示生产/测试，不允许把 staging 误认为生产）。
- Worker 当前版本与数据库 schema 版本。
- 只读数据库检查按钮。
- 表/字段/索引结构摘要。
- 待执行迁移清单与影响范围。
- 一键执行已批准迁移按钮。
- 迁移历史、开始/结束时间、执行结果、错误编号。
- 迁移后复核按钮。
- 下载/复制脱敏检查报告。

### 2.2 安全执行规则

- 浏览器只调用固定的超管维护 API；禁止把任意 SQL 文本从前端传给 Worker 执行。
- 迁移文件随版本发布，使用唯一 migration ID、版本号、校验摘要和明确依赖顺序。
- 建立迁移历史表（例如 `schema_migrations`，正式命名需先做现有 schema diff），记录 migration ID、checksum、执行状态、时间和执行者。
- 每个迁移必须幂等：重复点击不会重复创建数据、重复发卡或重置业务数据。
- 执行前先比较真实 D1 schema；已存在且兼容的表/字段跳过，不覆盖用户数据。
- 只允许新增表、必要字段、索引和明确批准的数据回填；禁止自动 DROP、TRUNCATE、清空、重建正式业务表。
- 对不兼容结构、未知字段、checksum 不一致、迁移历史缺失或环境不明确，必须停止并显示原因，不得强行继续。
- 每个迁移分批执行并记录步骤；失败时保留明确状态，支持安全重试，不得把半完成伪装成成功。
- D1 迁移执行前后都进行 schema 检查；执行后验证关键表、索引、约束和必要数据。
- 对无法事务回滚的 DDL，采用前置检查、单步迁移、迁移后验证和明确的人工恢复说明；不得承诺所有 DDL 都能自动回滚。
- 生产迁移必须由超管登录并二次确认；高风险迁移必须单独列出影响与恢复方案。
- `/api/super/migrate` 当前属于高风险既有接口，不能未经重构、安全审查和用户明确批准直接开放给页面调用。

### 2.3 建议 API（设计目标，尚未实现）

| 方法 | 路径 | 用途 | 权限 |
|---|---|---|---|
| GET | `/api/super/database/status` | 环境、schema 版本、迁移状态 | 超管只读 |
| POST | `/api/super/database/inspect` | 只读检查真实 schema 与迁移差异 | 超管只读操作 |
| GET | `/api/super/database/migrations` | 查看迁移清单与历史 | 超管只读 |
| POST | `/api/super/database/migrations/plan` | 生成待执行计划，不写库 | 超管 |
| POST | `/api/super/database/migrations/apply` | 执行指定已审核迁移集 | 超管 + 二次确认 |
| GET | `/api/super/database/migrations/:id` | 查看单次迁移详情 | 超管只读 |

API 路径仅为目标契约，需先与现有 Worker 路由、权限中间件和 D1 binding 核对，不能当作当前已存在接口。

## 3. 诊断开关与日志设计

### 3.1 开关方式

在“系统维护 → 系统诊断”页面按模块控制开关，界面可显示 0/1：

- `AUTH_DEBUG=0|1`：登录、注册、Session、协助会话。
- `VIP_DEBUG=0|1`：体验/正式 VIP 判定、到期与宽限。
- `CONVERT_DEBUG=0|1`：转换、归档、幂等、限流。
- `SOURCE_SYNC_DEBUG=0|1`：来源同步、任务 fencing、节点差异。
- `APP_DEBUG=0|1`：APP entitlement、分组下发、设备撤销与清理确认。
- `CRON_DEBUG=0|1`：定时维护任务执行、跳过原因、失败重试。
- `DB_DEBUG=0|1`：D1 查询耗时、迁移步骤、约束错误（不得记录敏感 SQL 参数）。

开关默认全部为 0。只开启排查所需模块，避免长期高噪声日志。

### 3.2 开关控制要求

- 诊断开关必须受超管权限保护，并记录操作者、时间、原值、新值和原因。
- 支持自动到期关闭（例如 30 分钟或 2 小时），防止忘记关闭；具体默认时长可在实现时确认。
- 诊断开关不能改变业务权限、跳过授权、放宽限流、绕过错误处理或改变数据。
- 开启/关闭开关本身不能触发数据迁移或重试任务。
- 如果用 Worker 环境变量控制，需说明修改后是否需要重新部署；如果用 D1 诊断配置表控制，必须加超管门禁、缓存失效和审计。优先采用可审计、有 TTL 的受控诊断配置，不把秘密值放进普通配置表。

### 3.3 日志字段与脱敏

每条日志建议包含：

- 时间、环境、Worker 版本、模块、级别。
- request_id / trace_id、操作类型、执行结果、耗时。
- actor 用户 ID（必要时）、目标记录内部 ID。
- 失败阶段、错误码、可定位的错误摘要。
- Cron 任务 ID、迁移 ID、同步 generation（适用时）。

绝不能记录：

- 完整订阅 URL、用户名密码组合、卡密明文、Session/APP Token、Cookie、API Secret、私钥。
- 完整请求 Authorization header。
- 能通过日志直接恢复订阅凭证的加密密钥或完整密文。
- 不必要的用户个人内容。

诊断日志必须有保留期限、查询分页、导出脱敏、访问审计和容量限制；错误不能被 `.catch(() => {})` 静默吞掉。普通业务日志与敏感审计日志分开。

## 4. 与现有 V2.5 风险审计的衔接

数据库一键升级不能绕过下列已发现问题：

- 正式 D1 schema 尚未获得完整只读核对；不能假设 staging 或旧数据库就是生产。
- Worker 内部迁移语句只是源码定义，不等于生产 D1 实际状态。
- `/api/super/migrate` 已列为高风险接口，不能直接调用。
- Cron 维护逻辑可能被来源数量提前 return 阻断；需要独立维护调度与可观测。
- Session Pepper、APP Token、转换加密密钥必须 fail closed，不能用固定默认密钥兜底。
- D1 限流故障不能 fail-open。
- 转换归档幂等、APP generation/撤销墓碑/cleanup ack、VIP 授权类型等结构变更需先完成设计。
- APP 本地缓存清理必须有 APK 联调与确认，不能只靠后台按钮显示成功。

## 5. AI 交付包的固定内容

每次准备可上传版本，至少提供：

1. 完整 Worker 文件（不只给零散代码片段）。
2. 完整管理后台 HTML/静态资源（与 Worker API 契约一致）。
3. 版本化 D1 migrations 文件及迁移顺序清单。
4. `wrangler.toml` / 部署配置模板（不包含真实 Secret）。
5. 环境变量名称、用途、生成方式与配置位置说明；绝不要求把 Secret 发到聊天。
6. 一键数据库初始化/升级操作说明。
7. 诊断开关和日志查看说明。
8. API 契约、权限矩阵、测试案例、回滚/恢复说明。
9. 文件清单、版本号、校验摘要和变更记录。
10. 已知限制与尚未完成项。

所有文件必须互相匹配并先做静态检查/自动化测试；不能让用户上传互不兼容的半成品。

## 6. 版本实施顺序

阶段 A：只读盘点正式 D1 binding、真实 schema、现有 migration 入口和超管权限；不执行写操作。

阶段 B：设计迁移账本、差异检查、迁移计划、分步执行、失败记录与复核 API。

阶段 C：实现系统维护 UI 与受保护 Worker API，在测试 D1 验证重复点击、部分失败、并发点击、schema 不兼容和重试。

阶段 D：实现诊断开关、TTL、脱敏日志、分页检索、导出和审计。

阶段 E：生成完整部署包；用户部署后先点“检查数据库”，确认目标环境和迁移计划，再明确批准执行。

阶段 F：正式环境先做只读检查和备份/恢复准备，再由用户明确批准生产迁移；迁移后复核并保留报告。

## 7. 验收标准

- 用户不需要手工执行大量 SQL。
- 一键操作只运行仓库中已审核、版本化的迁移，不接受任意 SQL。
- 已存在数据保留，重复执行安全。
- 目标 D1 环境标识清楚，误连 staging/production 会被阻止。
- 每个迁移步骤有成功/失败记录，失败不会谎报成功。
- 所有诊断开关默认 0，可按模块临时设为 1，并能自动关闭。
- 日志能定位错误，同时不泄露订阅 URL、卡密、Token 或密钥。
- 诊断功能不能绕过 VIP、超管、设备授权或其他业务安全门禁。
- APK 缓存清理必须有设备端确认，后台不能单方面宣称已清理。
