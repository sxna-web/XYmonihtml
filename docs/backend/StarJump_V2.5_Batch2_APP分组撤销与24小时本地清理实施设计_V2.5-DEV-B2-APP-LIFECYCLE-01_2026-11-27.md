# 星跃管理平台 V2.5｜Batch 2 APP 分组撤销与 24 小时本地清理实施设计

- 版本标识：`V2.5-DEV-B2-APP-LIFECYCLE-01`
- 日期：2026-11-27
- 状态：**DEV 设计稿；不是已实现代码，不可部署**
- 目标：为“APP 对接分组删除/改型后，APK 本地节点 24 小时内清空”建立可审计、可重试、可确认的端到端协议。
- 前置基线：V2.5 功能基线第 8 节、动作级权限门禁矩阵 V1、Worker 第三批安全审计、Batch 1 部署阻断复核。

## 1. 已确认业务要求

1. APP 对接分组（包括免费分组）被管理员删除，或改为普通/其他类型分组后，对应 APK 本地节点必须在 24 小时内清空。
2. 不能只删除后台分组记录；必须让客户端收到撤销信息并完成本地清理。
3. 需要保留分组版本、操作者、时间和节点差异；回滚应创建新版本，不覆盖历史。
4. 删除/改型必须检查关联卡密、分享关系、活跃转换链接；需要可恢复机制时不能直接物理删除。
5. 只有有效 VIP 管理员可管理 APP 对接分组和星链接；普通注册用户/过期管理员只读。
6. 管理员 A 的撤销不能误伤管理员 B 的同一设备/同名分组授权。

## 2. 协议对象与标识

协议中不要只依赖可变的分组名称或 URL。每个 APP 授权资源至少需要稳定标识：

- `owner_user_id`：资源所属管理员；
- `group_id`：稳定分组 ID；
- `generation`：单调递增的授权/内容代次；
- `share_type`：app_free / app_card 等明确类型；
- `revocation_id`：一次撤销操作的唯一 ID；
- `revoked_at`：服务端撤销时间；
- `purge_deadline`：撤销后 24 小时的截止时间；
- `reason`：deleted / type_changed / owner_revoked / entitlement_expired 等枚举；
- `event_status`：pending / delivered / acknowledged / expired / failed。

具体字段是否新建或复用，必须先对照正式 D1 schema，不能直接套用建议字段执行迁移。

## 3. Worker 服务端流程

### 3.1 删除或改型请求

1. 校验 Session；拒绝无效 Bearer 降级匿名。
2. 校验有效 VIP 管理身份。
3. 校验资源 owner，要求 `owner_user_id = ctx.effectiveId`；协助会话还要通过 scope。
4. 在同一事务/原子 batch 中：
   - 锁定并核对当前 group generation；
   - 检查关联卡密、分享关系、活跃转换链接；
   - 追加不可覆盖的 group version / audit 记录；
   - 写入 revocation/tombstone 事件；
   - generation 增加；
   - 标记旧 APP 授权失效；
   - 将物理清理安排到异步维护队列。
5. 若任一步失败，整批回滚；不得出现“分组已删但撤销事件没写入”。
6. API 返回 `revocation_id`、`generation`、`purge_deadline` 和待确认状态，不返回“客户端已清理”。

### 3.2 APK 增量同步

建议增加独立撤销事件读取端点，采用分页游标或 since token：

- 客户端请求必须验证 APP entitlement Token、设备绑定策略和有效授权；
- 响应只返回该设备/用户实际可见的撤销事件；
- 不得因某一个管理员授权更新而覆盖同设备上其他管理员授权；
- 同一事件可重复下发，客户端必须幂等处理；
- 事件响应不得包含订阅 URL、卡密或其他无关敏感信息。

最终 URL、HTTP method、字段名必须与现有 APK 网络层核对后再定，不在本设计稿中伪造既有接口。

### 3.3 客户端清理与确认

APK 收到撤销事件后：

1. 按 `owner_user_id + group_id + generation` 精确定位本地授权缓存；
2. 先停止继续使用旧节点；
3. 删除本地对应节点、订阅缓存和失效授权；
4. 验证目标缓存确实不存在；
5. 上传 `revocation_id + generation + device_id + cleanup_result` 确认；
6. 服务端验证设备绑定与事件归属，再把事件标记为 acknowledged。

设备标识不能仅信任客户端自报的任意 `device_id`。必须沿用并强化已确认的设备注册/密钥证明机制；现有 APK 证据不足，不能臆造设备证明算法。

## 4. 24 小时 SLA 与补偿机制

- `purge_deadline = revoked_at + 24h`，以服务端 UTC 时间计算。
- 客户端在线时，增量同步应尽快清理；离线设备下次启动/联网必须先处理撤销事件，再允许使用对应旧节点。
- 服务端按 deadline 监控未确认事件，重复投递并记录最后投递时间/失败原因。
- deadline 到期仍未 ack：标记 overdue，超管诊断页告警；不能伪造 ack。
- 设备永久离线时，平台无法证明其本地数据已物理清除。产品状态应明确区分“服务端已撤销”“客户端已确认清理”“设备离线/未确认”，不能对用户谎称离线设备已完成清理。
- 24 小时内的硬性保证需要 APK 启动/联网策略和可验证的清理确认共同支持；仅靠 Worker Cron 无法保证离线设备物理删除。

## 5. 多管理员授权隔离

- 同一设备可同时拥有管理员 A、管理员 B 的不同 entitlement。
- 撤销 A 的 group 只删除 A 对应 owner/group/generation 的本地缓存。
- API 不得只返回“最新 entitlement”；应按有效 Token/设备授权集合分别计算。
- 客户端本地缓存主键不得只用 group name 或 group_id（若不同 owner 可碰撞），至少包含 owner 维度。
- 测试必须覆盖 A 撤销不影响 B、A 过期不影响 B、A 恢复不复活已手动撤销事件。

## 6. 数据库影响与迁移门槛

潜在数据能力（不是已批准 schema）：

- 分组版本快照；
- 撤销事件/outbox；
- 设备同步游标；
- 清理确认记录；
- 失败投递/重试元数据。

在读取正式 D1 schema 之前，不指定最终表名、字段、索引或 SQL。禁止执行任何生产迁移。迁移设计必须满足：

- 可重复运行；
- migration ID + checksum；
- 先只读差异检查；
- 不 DROP/TRUNCATE/重建业务表；
- 先增加兼容字段/表，再切换写入，最后才考虑旧字段清理；
- 回滚采用向前修复或恢复旧 Worker，不通过丢弃撤销历史回滚。

## 7. 测试矩阵

| 场景 | 预期 |
|---|---|
| 有效 VIP 删除 APP 组 | 原子写入版本和 tombstone |
| 非 VIP/过期 VIP 删除 | 403，数据库不变 |
| 管理员 A 修改管理员 B 的 group_id | 403/404，不泄露资源 |
| 删除请求重复提交 | 幂等返回同一撤销结果 |
| 同一分组连续改型 | generation 单调增加，旧事件保留 |
| APK 重复收到同一事件 | 幂等清理，不误删其他组 |
| A/B 两个管理员授权同设备 | 撤销 A 不影响 B |
| 客户端清理后 ack | 服务端记录设备、代次、时间和结果 |
| ack 伪造/跨设备/错 owner | 拒绝 |
| 设备 24 小时离线 | 标记未确认/超时告警，不伪造完成 |
| 撤销事件投递失败 | 可重试，审计不静默吞错 |
| Cron 没有来源/空列表 | 撤销维护仍必须执行，不可提前 return 跳过 |
