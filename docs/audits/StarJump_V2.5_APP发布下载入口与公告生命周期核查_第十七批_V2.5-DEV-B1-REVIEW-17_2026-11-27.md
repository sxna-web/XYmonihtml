## 1. 本批结论

候选后台已经具备超管发布 APP 版本、发布公告、配置全局下载链接，以及管理员分别配置个人下载链接的界面和 API。

但当前发布流程偏向“直接生效 + 物理删除”，缺少草稿、审核、灰度、撤回、历史保留和回滚机制。删除最高版本 release 后，版本查询会自动选择剩余记录中 version_code 最高的一条，可能让旧版本重新成为最新版本，形成意外降级/错误更新提示。

公告管理有发布、下架/恢复、删除；公开公告读取按 scope、active 和开始/结束时间过滤。但管理界面没有提供开始/结束时间配置，也没有编辑公告内容的界面，后台只能切换 active 或物理删除。

下载入口管理有全局与管理员个人两种范围，公开下载列表把个人链接排在全局链接之前；但 HTTP 链接仍被接受，管理员状态与链接可见性没有在公开列表查询中统一判定。此前确认的“管理员 VIP 到期后三天自动切换公共百度购卡入口”是购卡入口规则，不能未经确认套用到普通 APP 下载链接。

## 2. 已核实实现

### 2.1 Release 发布与版本选择

Worker：
- `POST /api/super/releases` 校验 version_code 为正整数、version_name 非空、URL 以 HTTPS 开头。
- 写入 platform、version_code、version_name、min_version_code、url、notes、force。
- `GET /api/app/version` 调用 `pickLatestRelease()` 选取该平台最高 version_code 且 active=1 的记录。
- 更新响应包含 update、force、version_code、version_name、url、notes、min_version_code。
- `DELETE /api/super/releases/:id` 直接物理删除 release。

HTML：
- 有发布版本输入项：版本号、版本名、最低版本、HTTPS 下载地址、更新说明、强制更新。
- 列表展示版本、最低版本、强制更新和地址。
- 每条记录只有删除按钮，没有草稿/发布状态切换、撤回、回滚或历史详情。

### 2.2 公告管理

Worker：
- `POST /api/super/announcements` 写入 title、scope、body、level、starts_at、ends_at。
- scope 仅允许 web/app/both。
- `PUT /api/super/announcements/:id` 只更新 active。
- `DELETE /api/super/announcements/:id` 物理删除。
- 公告公开读取只返回 active=1、scope 匹配且当前时间位于 starts_at/ends_at 范围内的公告，最多 20 条。

HTML：
- 提供标题、范围、级别和正文输入及发布按钮。
- 列表展示标题、范围、状态。
- 提供下架/恢复和删除按钮。
- 未发现编辑公告正文/范围/级别、设置定时发布时间/结束时间的后台交互。

### 2.3 全局与管理员个人下载链接

Worker：
- 超管可读取、添加、删除全局下载链接，也可按 admin_user_id 读取/添加管理员链接。
- 管理员接口只能读取、添加、删除自己的链接，读取响应同时包含可用全局/个人链接。
- `listDownloads()` 只筛选 enabled=1，并按管理员个人链接优先、全局链接其次排序。
- `validDownloadUrl()` 同时允许 HTTP 和 HTTPS。
- 单个 scope/管理员最多 20 条链接。

HTML：
- 超管界面提供全局下载链接添加与删除。
- 管理员个人下载链接由独立用户后台接口管理。
- 当前全局列表界面没有编辑标题、URL、排序和启停状态的完整操作。

## 3. 风险与差异

### P1-17-01｜删除最高版本会使旧版本重新成为最新版本

版本选择按 version_code DESC 取 active release。删除接口直接物理删除，后台列表也只提供删除按钮。

若当前最高版本被误删，旧 release 会自动成为 latest；旧客户端可能收到不符合预期的更新响应，已安装较新版本的客户端也可能因 current 与被选中的版本比较而出现不一致行为。

建议：release 使用状态机 draft → staged → active → withdrawn；撤回保留记录，默认禁止物理删除曾经 active 的版本。发布新版本、紧急撤回和恢复均需审计；回滚应创建新的 version_code，不应重新激活旧版本作为“最新版本”。

### P1-17-02｜缺少发布前检查与 APK 完整性元数据

发布 API 仅校验 HTTPS URL 和基础版本字段。未发现以下发布校验：
- SHA-256；
- APK 签名证书指纹；
- 包名/applicationId；
- versionCode 与 APK 实际文件一致性；
- 文件大小；
- 最低支持版本的冲突检查；
- 下载地址可达性与文件类型检查。

建议：发布流程先登记候选包，后台/CI 验证 APK 包名、versionCode、签名证书、SHA-256，再允许 active。APK 客户端下载后必须校验可信签名；仅 HTTPS 不足以证明 APK 未被替换。

### P1-17-03｜发布操作缺少审计/审批闭环证据

本批所追踪的 release POST/DELETE 与公告 POST/PUT/DELETE 路径未看到明确的发布审批状态、操作者确认摘要和前后值版本记录。

建议：发布/撤回/强制更新/公告下架等动作均记录操作者、时间、对象、前后值、理由、请求 ID；对强制更新和生产版本撤回要求二次确认，必要时采用双人审批。

### P1-17-04｜公告后台无法编辑和设置时间窗口

数据库写入支持 starts_at、ends_at，但 HTML 发布表单没有相应输入；管理 API 的 PUT 只支持 active，无法修改正文、范围、级别、时间窗口。

建议：公告编辑应支持草稿、定时发布、自动到期、紧急撤回、版本历史；正文应做长度限制和安全渲染，不能将公告内容直接作为不可信 HTML 注入。

### P1-17-05｜管理员个人下载链接公开返回未检查 VIP 状态

公开下载列表按分享 code/admin ID 解析管理员后调用 listDownloads()，而 listDownloads() 仅依据 enabled 与 scope 查询，没有检查管理员账号是否被封禁、是否被撤销公开分享，或是否需受 VIP 状态影响。

建议：先明确 APP 下载链接在管理员 VIP 到期时的业务规则。特别区分：
- APP 安装包/更新下载入口；
- 管理员普通 APP 介绍/客服入口；
- 管理员自定义购卡入口（已确认：VIP 到期后三天切公共百度链接）。

不能把购卡入口的三天切换规则自动套用到前两类链接。

### P1-17-06｜下载链接允许 HTTP

`validDownloadUrl()` 接受 http:// 和 https://。APP 下载入口在 HTTP 下可能被中间人篡改或劫持。

建议：新链接默认只允许 HTTPS；对旧 HTTP 数据先只读盘点，确认后再迁移，不得未经用户批准直接改写生产链接。

### P2-17-07｜缺少下载链接编辑、排序和软删除恢复

当前后台下载管理可添加/删除，但本批未发现完整编辑、排序、启停、历史恢复能力。误删链接可能无法追溯原 URL。

建议：使用 enabled/status 与 deleted_at 软删除；保留变更历史和排序，支持恢复；对 URL 修改记录前后值。

### P2-17-08｜公告公开读取的范围和时间边界需实测

SQL 使用 scope 匹配、active=1、starts_at <= now、ends_at > now。静态逻辑合理，但需实测：
- starts_at/ends_at 使用何种时区和格式；
- starts_at 恰好等于当前时间；
- ends_at 恰好等于当前时间；
- 空时间值；
- scope=both 的双端展示；
- 结束后是否立即隐藏；
- 时钟偏差和夏令时影响。

### P2-17-09｜全局下载入口的“默认优先级”未提供显式排序策略

listDownloads() 将管理员个人链接全部排在 global 前，再按 sort 排序。全局下载入口无法明确置顶某个下载方式，管理员个人入口也无法在 UI 中配置顺序。

建议：排序规则作为明确字段并在管理 UI 提供排序控制；是否个人链接必须永远优先，应由产品规则确认。

## 5. 修复前置计划（本批不实施）

1. 与已确认的购卡入口规则严格分离，分别定义 APP 下载入口、普通 APP 入口和购卡入口生命周期。
2. 建立 release 状态机、APK 元数据验证、签名证书固定与发布审计。
3. 将物理删除改为撤回/软删除；保留 release 历史，回滚通过新版本发布。
4. 补公告编辑、定时发布、自动到期、版本历史和撤回功能。
5. 补下载链接编辑、排序、启停、软删除和恢复。
6. 对公开下载列表增加明确的管理员账号状态与分享状态判定；VIP 规则只按用户确认的具体入口类型执行。
7. 只读核实真实 D1 schema、现有 release/download_links/announcements 数据，再设计兼容迁移。
8. 完成 APK 源码核验和集成测试后，才能进入 RC。

## 6. 必须补充的测试矩阵

| 场景 | 预期 |
|---|---|
| 发布合法新版本 | 版本校验通过并记录完整审计 |
| version_code 重复或低于当前 active 版本 | 拒绝或走明确回滚审批 |
| 删除/撤回当前最高版本 | 不会静默使旧版本自动成为最新 |
| APK 包名或签名不匹配 | 不允许发布 |
| APK 文件哈希与登记值不一致 | 下载端拒绝安装/升级 |
| 强制更新版本撤回 | 客户端收到明确撤回/替代版本策略 |
| 公告定时发布 | 到开始时间后可见 |
| 公告到期 | 到结束时间自动隐藏 |
| 公告下架后恢复 | 历史内容和操作审计保留 |
| 修改公告正文 | 保存版本历史，避免覆盖丢失 |
| 管理员 VIP 到期 | 只按对应入口的明确规则切换 |
| 购卡入口 VIP 到期满三天 | 自动切公共百度链接 |
| APP 普通下载入口 | 不错误套用购卡入口的到期规则 |
| HTTP 下载链接 | 正式策略拒绝或进入有期限兼容流程 |
| 删除下载链接 | 软删除可追溯、可恢复 |
| 管理员 A 查询管理员 B 链接 | 不得越权读取或修改 |
| 超管撤回/恢复 release | 留存操作者、理由、时间和前后值 |

## 7. 本批边界与结论

- 已完成：读取候选 HTML/Worker，追踪 release、announcement、download_links 的后台表单、事件处理、API 路由与查询逻辑。
- 未完成：真实 D1 schema/数据读取、APK 源码核验、HTTP 集成测试、实际 APK 下载与签名验证。
- 未修改：Worker、HTML、D1、Secrets、Cron、生产部署。
- 发布等级：仅 DEV 静态审计，不是 RC，不可部署。

**结论：** 当前后台有基础发布/公告/下载管理能力，但还没有可靠的正式发布生命周期。最重要的风险是 release 物理删除导致旧版本回退成为 latest、缺 APK 签名/哈希验证、公告编辑与定时能力缺失，以及下载入口类型与 VIP 失效规则需要明确区分。
