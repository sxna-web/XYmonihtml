# V2.5.0 RC1 APP 多卡密与卡密分组授权缺口审计

- 日期：2026-11-28
- 审计分支：`release/v2.5.0-rc1-converge`
- 当前 Worker：`backend/worker/V2.5-DEV-B1-CORE-AUTH-49/Worker.js`
- 性质：代码路径与现有迁移目录审计；未执行生产数据库操作。

## 1. 审计结论

APP 多卡密聚合和“每张卡密配置不同分组”的数据模型尚未实现。当前接口以同一设备最新的一条有效 entitlement 作为唯一管理员授权来源，不能完整满足已确认的多卡密规则。不能仅通过改动一个 SELECT 就宣称完成。

## 2. 当前代码证据

### 2.1 APP 分组读取只取最新一条有效授权
`appGroupsForDevice` 查询：
- `WHERE device_id = ? AND status = 'active' AND datetime(expires_at) > datetime('now')`
- `ORDER BY created_at DESC LIMIT 1`

之后只按该条 entitlement 的 `admin_user_id` 查询管理员分组。

### 2.2 APP 入口链接同样只取最新一条授权
`appLinksForDevice` 使用相同的最新 entitlement 查询，只返回该管理员的链接。

### 2.3 APP 免费组授权有持久记录，但有授权时没有跨管理员统一聚合
激活卡密会在同一批次创建 entitlement，并写入 `app_free_grants(device_id, admin_user_id)`。没有有效 entitlement 时，分组读取会遍历免费授权；但只要存在任意一条有效 entitlement，当前路径就只读取最新 entitlement 对应管理员的分组，没有将其他管理员的有效卡密分组和免费授权统一合并。

### 2.4 当前没有卡密到 APP 分组的映射
现有 Worker 对 `app_group_members` 的使用是 `group_id + device_id`，属于设备分组授权，不是 `card_id + group_id` 卡密分组授权。
`app_entitlements` 保存 `card_id`，但当前 APP 分组查询没有通过 `card_id` 找到该卡密配置的分组。
`app_cards` 当前查询/生成路径也没有提供可供展示的独立序列号字段；不能把随机卡密 code 擅自当成用户要求的序列号显示。

## 3. 必须实现的目标模型

1. 一个设备可以同时拥有同一管理员的多张有效卡密，也可以拥有多个管理员的有效卡密。
2. 每张有效卡密必须只下发其绑定的卡密分组；不能因同管理员而把其他卡密的私有分组全部开放。
3. 同一管理员的免费分组在设备最终结果中只出现一份；跨管理员免费授权按各自管理员范围保留，不可误去重。
4. 同名卡密分组需要在输出显示稳定、可辨识的卡密序列号后缀；分组实体 ID 和管理端原始名称不得被覆盖。
5. 身份 ID 只获取对应管理员免费分组；卡密授权获取该卡密分组及规则允许的免费分组。
6. 过期 entitlement 不再下发卡密分组；免费授权是否保留仍遵循已确认的永久免费资格规则。
7. APP token 必须验证设备持有的有效授权，不能只凭用户可伪造的 device_id 查询聚合结果。

## 4. 实施前置和兼容性要求

- 需要新增经过核对的卡密—分组关联表及 migration；必须确认现有 D1 表名、主键、外键和索引后才能确定最终 DDL。
- 需要新增/调整管理端卡密分组配置 API，并更新 HTML 管理界面；当前只有设备级 `app_group_members` 入口，不足以替代卡密级配置。
- APP 客户端必须能处理多个管理员、多张卡密、同名分组标签；第三方 APK 6.00.47 的接口兼容性尚未验证，不能假定它已支持。
- 多卡密授权令牌策略需要向后兼容：现有 APP 只持有最新兑换返回的 token。聚合读取必须先验证该 token 对应至少一条当前有效 entitlement，再以经过验证的 device identity 聚合该设备其他有效授权；不能无 token 或仅凭 device_id 聚合。
- 设备绑定、设备数限制、解绑审批和设备 ID 可伪造风险必须一并复核。
- 不允许在生产 D1 上试验迁移；迁移 runner 当前只具备本地 verifier ledger bootstrap，不能视为生产 schema migration 已准备完成。

## 5. 当前上线判断

此项属于 APP 核心授权功能阻断项。当前 Worker 仍不能满足多卡密聚合与卡密分组独立授权规则。应先核实完整 D1 schema 与 APK 客户端协议，再实现 migration、管理端配置、Worker 聚合、客户端兼容和回归测试。未完成前不得将 APP 多卡密功能标记为可上线。
