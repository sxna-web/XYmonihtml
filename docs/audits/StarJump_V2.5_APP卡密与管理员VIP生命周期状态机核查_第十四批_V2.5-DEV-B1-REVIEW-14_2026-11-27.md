## 1. 本批结论

候选 Worker 已实现部分管理员 VIP 到期后 APP 卡密失活及续费恢复逻辑，且恢复条件使用明确的 `inactive_reason='admin_vip_expired'`，并排除人工停用、已激活/已使用及自身已过期的卡密。这与已确认业务规则的方向一致。

但发现一个高优先级调度问题：`runVipCardMaintenance()` 被放在定时节点同步流程中；该流程在读取可同步来源后，如果来源列表为空便提前 `return`，VIP 卡密维护任务不会运行。因而卡密状态维护错误地依赖是否存在可同步来源。

此外，VIP 续费判断与卡密批量状态更新分为独立查询和更新，存在并发竞态窗口；维护审计失败会被吞掉。该候选实现不能作为正式版放行依据。

## 2. 已核实的实现

### 2.1 管理员 VIP 有效状态

- `vipStatus()` 从 `admin_vip_activations` 查询当前有效期，并区分是否存在正式 VIP 激活记录。
- `vipActiveNow()` 检查是否存在 `ends_at > datetime('now')` 的激活记录。
- `vipExpiredOverGrace()` 取管理员历史激活记录的 `MAX(ends_at)`，判断该时间是否已过去三天。
- 时间判断使用 SQLite 的 `datetime('now')`，不是浏览器传入时间。

### 2.2 到期三天后停用未激活卡密

`deactivateCardsForAdmin()` 的更新范围为：
- 管理员名下；
- 当前 `status='normal'`；
- `manual_disabled=0`；
- `activated_at IS NULL`；
- `used_at IS NULL`；
- 卡密自身未过期或未设置自身过期时间。

更新结果写入：
- `status='inactive'`；
- `inactive_reason='admin_vip_expired'`；
- `inactive_at=CURRENT_TIMESTAMP`。

### 2.3 管理员恢复 VIP 后恢复卡密

`restoreCardsForAdmin()` 只恢复：
- 同一管理员名下；
- `status='inactive'`；
- `inactive_reason='admin_vip_expired'`；
- `manual_disabled=0`；
- 未激活、未使用；
- 卡密自身仍未过期。

恢复时将状态设为 `normal`，清空 `inactive_reason`，记录 `restored_at`。

这条精确原因筛选是正确方向：不能把所有 inactive 卡密无差别恢复。

### 2.4 人工停用和删除

用户卡密停用接口会设置 `manual_disabled=1`。当卡密原状态为 normal 时，会设为 inactive 并记录 `inactive_reason='manual'`。

删除接口将未激活卡密设为 inactive、`manual_disabled=1`、`inactive_reason='user_deleted'`；已激活/已使用卡密不能通过该删除接口删除。

即使卡密先因管理员 VIP 到期而失活，随后被人工停用，恢复查询也会因 `manual_disabled=1` 而排除它。

### 2.5 已激活卡密

管理员到期失活 SQL 明确要求 `activated_at IS NULL AND used_at IS NULL`。因此已激活/已使用卡密不会被这条管理员 VIP 到期任务停用，符合“已激活卡密按自身有效期继续使用”的业务规则。

## 3. 关键风险与差异

### P1-14-01｜VIP 卡密维护依赖节点同步来源（高优先级）

定时流程先读取可同步来源，随后执行：
- 计算来源列表；
- 若来源列表为空，直接提前返回；
- 只有存在来源时，才调用 `runVipCardMaintenance()`。

因此，当系统没有可同步来源，或查询结果为空时：
- 管理员 VIP 到期满三天后，未激活 APP 卡密不会按时失活；
- 管理员恢复 VIP 后，因管理员到期而失活的卡密也不会及时恢复；
- 卡密生命周期受无关的节点来源配置影响。

建议：将 VIP 卡密维护从节点同步流程中解耦，作为独立、必定执行的定时维护步骤；节点同步是否有来源不应影响会员和卡密状态维护。需核实 Cloudflare Cron 配置和现有任务入口后再实施。

### P1-14-02｜VIP 续费与失活更新存在竞态窗口

当前维护流程先调用 `vipActiveNow()` / `vipExpiredOverGrace()` 查询，再单独执行卡密 UPDATE。卡密 UPDATE 本身没有再次在同一 SQL 中验证管理员 VIP 当前状态。

可能出现：
1. 维护任务读取到管理员 VIP 已到期；
2. 用户同时完成 VIP 续费；
3. 维护任务仍按先前判断执行失活 UPDATE；
4. 卡密暂时进入 inactive，需等待下一轮维护才能恢复。

反向也应检查：恢复判断和卡密自身过期、人工停用的并发变化，必须由 UPDATE 条件再次保护。

建议：把 VIP 状态条件纳入最终 UPDATE 的 SQL 谓词，或通过具备一致性保证的事务/批处理执行；不能只依赖更新前的独立查询。

### P1-14-03｜失效原因模型仍不完整

当前实现主要使用：
- `admin_vip_expired`
- `manual`
- `user_deleted`

未在本批路径中发现独立、统一的超管撤销/封禁/作废原因状态机。当前通过 `manual_disabled` 标志阻止恢复，有一定保护作用，但不能完整表达“谁在何时以何种原因停用”的多来源状态。

建议：正式状态模型应区分管理员 VIP 到期、管理员人工停用、超管撤销/封禁/作废、卡密自身过期、卡密已激活/已使用等原因；恢复只清理由管理员 VIP 到期单独造成的限制，不能清除其他同时存在的停用原因。实施前必须核对现有 D1 字段和历史数据。

### P1-14-04｜维护审计失败会被静默吞掉

维护任务在状态变化后写入旧审计表及新审计事件，但调用链使用 `.catch(() => {})`。如果审计表不存在、字段不兼容或写入失败，卡密状态可能已经变化，而审计记录缺失且没有可靠告警。

建议：状态变更与审计记录应有明确的一致性策略；至少要记录失败计数和诊断事件，不能把关键审计失败无声忽略。是否允许状态更新在审计不可用时继续，需要在正式实现方案中明确。

### P2-14-05｜VIP 到期边界及宽限起点仍需专项测试

当前判断以管理员最新 `ends_at` 为宽限起点，并通过 SQLite 当前时间比较。需测试：
- 到期前一秒；
- 到期时刻；
- 到期后三天前一秒；
- 恰好满三天；
- 满三天后一秒；
- 续费跨越到期边界；
- 多次续费、多个激活记录和时间重叠。

不得仅凭函数静态逻辑认定边界行为已通过。

## 4. 与已确认业务规则对照

| 业务规则 | 候选实现核查 |
|---|---|
| 管理员正式 VIP 到期满三天，未激活卡密失活 | 已有逻辑；但维护任务可能因无同步来源而跳过 |
| 已激活卡密不因管理员 VIP 到期失效 | SQL 排除已激活/已使用记录 |
| 管理员恢复 VIP，只恢复因管理员到期失活的卡密 | 使用 `inactive_reason='admin_vip_expired'` 精确筛选 |
| 人工停用卡密不自动恢复 | `manual_disabled=0` 条件提供保护 |
| 超管撤销/封禁/作废不自动恢复 | 需核实完整超管操作路径及原因写入；当前原因模型不足 |
| 卡密自身过期不恢复 | 恢复和到期失活 SQL 均检查 `expires_at` |
| 状态变化有原因、时间、操作者和关联管理员 | 有部分时间/原因字段；维护审计可能静默失败，原因模型仍不完整 |
