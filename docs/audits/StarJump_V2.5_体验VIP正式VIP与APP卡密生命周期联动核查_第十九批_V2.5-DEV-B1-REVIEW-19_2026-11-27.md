## 1. 本批结论

候选 Worker 已实现管理员 VIP 激活记录、7 天体验记录、正式 VIP 卡密核销、未到期续费叠加、管理员 VIP 到期三天后失活未激活 APP 卡密、恢复 VIP 后恢复指定失活原因卡密等基本机制。

但发现以下需要优先处理的问题：

1. **Cron 提前返回：** 定时任务先查询可同步来源；如果没有来源，直接 return，VIP 卡密维护、节点生命周期和 APP entitlement 维护都不会执行。
2. **体验卡发放失败被静默吞掉：** 注册/超管创建用户成功后，单独调用 grantTrial()，失败会被 catch 忽略；接口仍返回 trial_days=7，用户可能没有实际体验 VIP。
3. **体验卡自动发放不是原子操作：** grantTrial() 先查询是否已有激活记录，再单独 INSERT；并发调用可能重复发放，具体是否被数据库唯一约束阻止，当前无法从候选 Worker 证明。
4. **续费并发竞态：** 两张不同正式 VIP 卡密同时核销时，可能都基于同一个旧到期时间计算续费结束时间，导致两张卡都被消费，但有效期没有正确累计。
5. **体验 VIP 的 APP 卡密宽限规则未获确认：** 当前 APP 卡密维护逻辑对所有管理员 VIP 激活记录取 MAX(ends_at)，没有区分 trial/formal；体验 VIP 创建的未激活 APP 卡密也可能按三天宽限后失活。该业务规则在基线中明确列为待确认。
6. **维护任务错误可能被静默隐藏：** Cron 对多个维护函数使用 catch(() => {})，缺少可靠失败记录和告警。

本批没有执行 API、D1 或 Cron 测试；以上均为静态源码风险判断，不代表生产环境已经发生。

## 2. 已核实的 VIP 状态实现

### 2.1 VIP 状态计算

`vipStatus(db, userId)` 查询 `admin_vip_activations`：
- 当前有效记录要求 starts_at <= 当前服务器时间且 ends_at > 当前服务器时间。
- `until` 取当前有效记录中最大的 ends_at。
- `active` 由 until 是否存在决定。
- `active_formal` 只看当前有效 formal 记录。
- `is_formal` 由历史 formal 记录总数是否大于 0 决定。
- `has_trial` 由历史 trial 记录总数是否大于 0 决定。
- 查询异常时返回 unavailable=true；有效 VIP 管理操作会 fail-closed 返回 503。

说明：`is_formal` 与 `has_trial` 表示历史上是否存在对应激活记录，不等同于“当前有效身份类型”。前端若将其直接当作当前有效状态显示，可能造成误读；应明确字段语义或改用清晰字段名。

### 2.2 体验 VIP 发放

- 新注册用户创建成功后调用 `grantTrial()`。
- 超管创建普通 user 账号后也调用 `grantTrial()`。
- trial 固定 7 天，写入 `admin_vip_activations`，kind='trial'。
- grantTrial() 先查询该用户是否存在任何激活记录；若存在则不再赠送。
- 注册/创建用户和 trial 写入不是同一个原子批次。
- 调用方对 grantTrial() 使用 `.catch(() => {})`，失败不影响账号创建成功响应。
- 注册响应无论 trial 是否真正写入，都会返回 `trial_days: 7`；超管创建普通用户也会返回相同字段。

### 2.3 正式 VIP 卡密核销与续费

- 正式 VIP 卡密由超管生成，status 初始为 unused。
- 用户通过 `POST /api/user/vip/activate` 提交卡密。
- Worker 检查卡密状态、天数范围，并读取当前 VIP 到期时间。
- 未到期时，以当前最大有效 ends_at 为基础叠加天数；已到期/没有有效 VIP 时从当前时间起算。
- 卡密状态更新、激活记录 INSERT、审计 INSERT 通过 userBatch() 同批提交，并带有卡密仍为 unused 的断言。
- 激活后重新读取 vipStatus() 返回状态。

正向实现：同一张卡密的重复核销有状态断言和条件 UPDATE，业务写入与审计在同一批次中执行。

待验证：不同卡密同时核销同一账号时，续费基准是在批次外预先读取的；并发请求可能使用同一个旧 until 计算 ends_at，不能据此保证两张卡的时长串行叠加。

### 2.4 APP 卡密到期失活与恢复

当前实现：
- VIP 宽限期常量为 3 天。
- `vipExpiredOverGrace()` 查询该管理员全部激活记录的 MAX(ends_at)，再判断是否已超过 3 天。
- `vipActiveNow()` 判断该管理员是否存在 ends_at > now 的记录。
- 失活只处理 status='normal'、manual_disabled=0、activated_at IS NULL、used_at IS NULL、expires_at 未到期的 APP 卡密。
- 失活时写 status='inactive'、inactive_reason='admin_vip_expired'。
- 恢复只处理 status='inactive' 且 inactive_reason='admin_vip_expired'、未人工停用、未激活/使用、卡密自身未过期的记录。
- 恢复时清空 inactive_reason 并写 restored_at。
- 已激活/已使用、人工停用、卡密自身已过期的记录不会被自动恢复。
- APP 卡密生成接口要求有效 VIP 管理权限；有效体验 VIP 目前也会通过统一有效 VIP 门禁。

正向实现：自动恢复明确限定 inactive_reason='admin_vip_expired'，不会把所有 inactive 卡密一律恢复。

## 3. P0/P1 风险

### P1-19-01｜Cron 没有同步来源时跳过全部生命周期维护

**源码路径：** Worker scheduled()。

当前顺序：
1. 查询已分配、启用且审核通过的订阅来源；
2. 若 sources.length === 0，直接 return；
3. 只有存在来源时才创建 cronCtx 并执行：
   - runVipCardMaintenance()
   - runNodeLifecycle()
   - runEntitlementMaintenance()
   - runSync()

因此，系统没有任何可同步来源时：
- APP 卡密不会按管理员 VIP 到期三天规则自动失活；
- 管理员 VIP 恢复后的 APP 卡密不会自动恢复；
- APP entitlement 维护不会执行；
- 节点生命周期维护也不会执行。

这把会员/授权维护错误地依赖于“是否存在节点同步来源”。

**建议修复：**
- 将 cronCtx 初始化和独立维护任务移到来源数量判断之前。
- VIP 卡密、APP entitlement、节点生命周期等任务应按各自需要独立运行；只有节点同步步骤可以在无来源时跳过。
- 为每项任务写入开始/完成/失败/耗时/影响数量的运行记录。
- 任一维护任务失败不得静默吞掉；应记录错误编号并触发诊断告警，但不能把敏感卡密或 Token 写入日志。

### P1-19-02｜体验 VIP 发放失败被静默吞掉，接口仍宣称赠送成功

**源码路径：** `/api/auth/register`、`/api/super/users`、`grantTrial()`。

账号创建与 trial 激活记录分两步执行；第二步失败被 catch 忽略。接口仍返回 trial_days=7，前端可能显示用户已获得体验 VIP，但实际 vipStatus() 没有激活记录。

**影响：**
- 新用户注册成功却没有体验 VIP；
- 用户看到“已赠送 7 天”但管理操作返回 VIP_REQUIRED；
- 无明确待补发状态或失败审计；
- 后续排查难以区分用户主动没有体验资格与发放失败。

**建议修复：**
1. 在账号创建流程中使用原子批次写入用户、体验激活记录与审计；若需分步，必须有可靠补偿任务。
2. 不允许 catch 后仍返回赠送成功。
3. 返回实际发放结果和状态；失败时明确提示“账号已创建，体验权益待补发/暂不可用”，并生成可追踪任务。
4. 对体验发放失败做可靠重试和幂等补发。
5. 体验卡池尚未接入时，不得伪称已从超管体验卡池扣卡发放；当前 grantTrial() 是直接写激活记录，不是卡池核销。

### P1-19-03｜不同正式卡密并发续费可能丢失时长

当前请求先在事务外读取 `vipStatus()`，然后依据 cur.until 生成 INSERT ends_at，之后才把卡密核销、激活记录和审计放进 userBatch()。

两个不同卡密并发时可能发生：
- 请求 A、B 都读到同一个到期时间 T；
- A 插入 T + A 天；
- B 插入 T + B 天；
- 最终 MAX(ends_at) 可能只体现较长的一张，而不是 T + A 天 + B 天；
- 两张卡密都可能已经变为 used。

**建议修复：**
- 将同一用户 VIP 续费串行化，使用数据库内原子更新/锁定或可证明无竞态的 D1 事务设计。
- 续费基准必须在实际写入事务中重新计算，不得依赖事务外读取的旧状态。
- 卡密状态变化、激活记录、续费累计和审计必须原子提交。
- 并发测试必须使用两张不同卡密，同时对同一用户核销；最终到期时间应等于原有效到期时间加两张卡密天数之和。
- 同一张卡密并发核销仍必须只有一个请求成功。

## 4. P2 风险与待确认规则

### P2-19-04｜体验 VIP 创建的 APP 卡密是否享有三天宽限尚未确认

功能基线明确列出“体验 VIP 管理员创建的未激活卡密是否也采用独立 3 天宽限期”为待确认项。

但当前代码：
- userAppCardsRoute() 对体验 VIP 和正式 VIP 使用相同有效 VIP 门禁；
- vipExpiredOverGrace() 只取所有激活记录的 MAX(ends_at)，没有限定 kind='formal'；
- 因此体验 VIP 到期后，体验期间创建的未激活 APP 卡密也可能进入三天宽限后失活。

**处理原则：** 不得自行将其认定为正确业务规则。实施前需由用户明确：体验 VIP 创建的 APP 卡密，是采用三天宽限、立即失活，还是不允许体验 VIP 生成 APP 卡密。

### P2-19-05｜宽限期依据 MAX(ends_at)，没有显式限定最后一段有效 VIP 的类型

vipExpiredOverGrace() 和 vipActiveNow() 均按用户全部激活记录判断，没有把 trial/formal 的生命周期分开。

当用户曾有体验 VIP、后来正式 VIP、或历史激活记录存在异常重叠时，维护结果只按 MAX(ends_at) 计算，无法从状态字段直接解释“哪一种身份到期触发了卡密失活”。

建议：明确会员身份状态计算口径，至少区分当前有效体验、当前有效正式、历史体验、历史正式；APP 卡密宽限规则按已确认身份类型单独判断。

### P2-19-06｜VIP 历史记录与卡密生命周期的可追溯界面不足

当前 `GET /api/user/vip` 返回汇总状态；本批检查的 HTML 用户管理区域未确认有完整激活历史时间线，包括：
- 体验发放时间、到期时间、发放来源；
- 正式卡密核销记录与续费前后时间；
- 管理员 VIP 到期时间；
- APP 卡密三天宽限开始/结束；
- 每张 APP 卡密失活/恢复原因、操作者和时间。

建议增加用户会员时间线与卡密状态事件查询；卡密原文只在必要的受控场景展示，事件日志不得暴露明文卡密。

### P2-19-07｜VIP 卡密管理目前缺少撤销/作废 API 证据

本批检查的 `superVipRoute()` 提供卡密分页查询和生成；在该处理函数范围内未发现单张未使用 VIP 卡密的撤销/作废路由。

建议：如果产品需要超管作废误发或泄露的未使用卡密，应提供仅针对 unused 卡密的原子作废动作和审计；已经核销的卡密不能通过简单删除卡密行来撤销会员历史。正式 VIP 撤销应设计独立状态事件与授权影响规则。

### P2-19-08｜维护任务异常被吞掉，缺少任务级健康状态

scheduled() 对 runVipCardMaintenance、runNodeLifecycle、runEntitlementMaintenance 使用 catch(() => {})；runVipCardMaintenance() 的审计写入也有 catch 忽略。

建议：记录每个维护子任务的成功/失败/重试状态；不能因某个子任务失败而阻断其他独立维护，但必须能在后台查看失败、告警和重试结果。

### P2-19-09｜会员状态汇总字段名称可能产生误读

`vipStatus()` 中：
- is_formal 代表历史上存在 formal 记录，不一定代表当前正式 VIP 有效；
- active_formal 才表示当前存在有效 formal 记录；
- has_trial 代表历史上存在 trial 记录，不代表当前体验有效。

建议：前端展示当前身份时使用明确的 active_trial / active_formal / historical_formal 等语义；避免把历史正式会员直接显示为“当前正式 VIP”。

## 5. 与已确认规则对照

| 已确认规则 | 当前候选实现 | 核查结论 |
|---|---|---|
| 新注册用户获 7 天体验 VIP | 直接写 trial 激活记录 | 有实现，但失败被吞掉且非原子 |
| 体验与正式 VIP 有效期内核心管理权限相同 | 统一 requireActiveVipForManagement() | 基本符合，仍需全路由实测 |

| 手动停用/超管撤销/卡密自身过期不得自动恢复 | restore SQL 限定原因和状态 | 基本符合；需验证所有人工状态路径 |
| 管理员恢复 VIP 后恢复 admin_vip_expired 卡密 | restoreCardsForAdmin() | 有实现，但 Cron 可能跳过 |
| 体验 VIP 创建的 APP 卡密三天宽限 | 基线待确认 | 当前代码默认套用，属于未经确认的实现选择 |
| 体验卡来自超管体验卡池 | grantTrial() 直接插入激活记录 | 当前代码未体现卡池扣减闭环 |

## 6. 修复顺序与数据库影响

本批不实施代码修改。建议按以下顺序准备修复：

1. **先修 Cron 调度结构：** 独立运行 VIP/APP entitlement 维护，来源为空时仅跳过节点同步。
2. **修体验 VIP 发放一致性：** 用户创建、trial 激活、审计采用原子流程或可靠补偿任务；明确体验卡池扣减规则。
3. **修正式 VIP 续费并发：** 将累计基准放入可证明原子性的写事务。
4. **冻结体验 VIP 的 APP 卡密规则：** 由产品确认是否允许生成及到期宽限策略。
5. **增加会员与卡密生命周期时间线：** 展示发放、核销、续费、到期、宽限、失活、恢复的状态事件。
6. **补任务级运行记录与告警：** 让后台可以看见每次维护是否执行及失败原因。
7. **只读核实真实 D1：** 检查 admin_vip_activations、admin_vip_cards、app_cards 的字段、唯一约束、索引、外键和现存状态分布，再设计兼容迁移。

数据库影响预判：
- Cron 调度修复本身不一定需要新增表字段。
- 体验发放幂等可能需要唯一约束或发放任务账本，但必须先读取真实 D1 schema。
- 续费原子性修复可能只需调整 SQL/事务顺序，也可能需要用户级续费锁/账本；不可在未核实 D1 前决定。
- 生命周期时间线可能复用现有 admin_vip_activations、app_card_events、审计表；先核对现有结构，不重复建表。
- 不执行任何生产 D1 SQL，不改 Secrets，不部署 Worker。

## 7. 必须补充的验收测试

| 场景 | 预期 |
|---|---|
| 注册成功且体验激活写入成功 | 用户实际获得 7 天体验 VIP，响应与数据库一致 |
| 注册成功但体验激活写入失败 | 不得显示赠送成功；有可追踪补发任务 |
| 同一用户并发触发体验发放 | 最多一条有效 trial，不重复赠送 |
| 已有正式 VIP 历史的用户重新走发放流程 | 不重复赠送体验 VIP |
| 一张正式卡密核销成功 | 卡密只使用一次，激活记录和审计一致 |
| 同一正式卡密并发核销 | 只有一个请求成功 |
| 两张不同正式卡密并发续费 | 最终到期时间累计两张卡密全部天数 |
| VIP 已到期后核销正式卡密 | 从本次服务器时间起算 |
| VIP 未到期时核销正式卡密 | 从原有效到期时间叠加 |
| 管理员正式 VIP 到期未满三天 | 未激活且正常的 APP 卡密仍在宽限期 |
| 正式 VIP 到期满三天 | 符合条件的未激活 APP 卡密失活 |
| 已激活 APP 卡密遇管理员 VIP 到期 | 不因管理员 VIP 到期自动失效 |
| 人工停用卡密后管理员续费 | 不自动恢复人工停用卡密 |
| 超管撤销/作废卡密后管理员续费 | 不自动恢复超管撤销/作废卡密 |
| 卡密自身过期后管理员续费 | 不自动恢复已过期卡密 |
| 管理员续费后 | 只恢复 inactive_reason=admin_vip_expired 的未激活卡密 |
| 没有任何可同步来源时触发 Cron | VIP/APP entitlement 维护仍执行 |
| 某一维护子任务失败 | 其他独立任务继续；失败被记录并可告警 |
| 体验 VIP 到期时的 APP 卡密 | 按用户确认的独立规则执行 |
| VIP 状态查询异常 | 管理写操作 fail-closed，不误授 VIP 权限 |

## 8. 本批边界与结论
