# V2.5.0 RC1 APP 多卡密分组聚合差距复核

- 日期：2026-11-28
- 分支：`release/v2.5.0-rc1-converge`
- 核验对象：`backend/worker/V2.5-DEV-B1-CORE-AUTH-49/Worker.js`
- 方法：静态源码路径检查；未执行生产 D1、真实并发或 APK 联调。

## 1. 已确认的现状

### 1.1 卡密兑换模型
`POST /api/app/redeem` 每次兑换会创建一条 `app_entitlements`，记录 `admin_user_id / device_id / card_id / starts_at / expires_at / purge_at / status`，并写入该设备对应管理员的 `app_free_grants`。

这意味着数据层已保存卡密与授权的关联线索，但读取层尚未按设备聚合全部有效授权。

### 1.2 节点接口
`GET /api/app/nodes` 按 `device_id` 查询有效授权，使用 `ORDER BY created_at DESC LIMIT 1` 只选最新一条，再仅返回该条授权管理员名下来源节点。若同一设备存在同一管理员或不同管理员的多张有效卡密，其余授权不会在本接口合并。

### 1.3 分组接口
`GET /api/app/groups` 同样只取最新一条有效 entitlement；有有效 entitlement 时只查询该管理员的组。
没有有效 entitlement 时，按设备读取所有 `app_free_grants`，逐个管理员读取免费组并直接追加到输出，没有看到按管理员去重或按分组名称冲突生成卡密序列号后缀的逻辑。

### 1.4 入口链接接口
`GET /api/app/links` 同样只取最新有效 entitlement，因此多个管理员授权的链接也不会聚合。是否应跨管理员合并入口链接，需要按产品权限边界单独确认，不得从节点分组规则自动推导。

## 2. 与已确认业务规则的差距

1. 同一设备使用同一 VIP 管理员的多张有效卡密，应取得这些卡密分别配置的卡密分组；当前只读取最新 entitlement。
2. 同一管理员的免费分组只应出现一份；当前无有效 entitlement 分支按 grants 逐行追加，未显式去重。
3. 同一设备绑定多个管理员时，各管理员的卡密分组应按各自授权隔离；免费组按每个管理员只保留一份，不得因为多张卡密重复。
4. 卡密分组重名时，应显示卡密序列号后缀以区分来源；当前输出未包含卡密序列号，也没有同名组后缀处理。
5. 多卡密聚合必须先验证请求 token 对应设备，再从服务端授权记录枚举该设备有效授权；不得仅凭客户端提交的 device_id 聚合其他授权。
6. 设备授权过期后，保留免费组的规则应独立于卡密分组授权；不能因一张卡密过期而错误删除同管理员其他仍有效卡密对应的分组。

## 3. 建议的数据读取模型

- 先以有效 token 定位并验证一个 entitlement，确认其 device_id 与请求设备一致。
- 查询该 device_id 全部有效 entitlement，按 `admin_user_id + card_id` 保留授权来源。
- 卡密分组以 entitlement/card 关联为准，不能仅以设备成员关系或管理员最新授权代替卡密关联。
- 免费组以 `device_id + admin_user_id` 去重，每位管理员最多输出一份。
- 组名冲突展示必须使用稳定且不泄露完整卡密的序列号/短标识；展示规则要与后台卡密列表可对应。
- 不同管理员的授权、卡密组、免费组保持来源边界；相同名称不得覆盖或误合并不同来源节点。
- 对删除、禁用、过期、恢复等状态变化建立确定的聚合过滤规则，并纳入 tombstone/generation 与客户端 cleanup ACK 设计。

## 4. 测试矩阵

至少覆盖：
- 同一管理员 1 张、2 张、3 张有效卡密；
- 同一管理员多张卡密包含同名组；
- 多张卡密的分组名称不同；
- 两个管理员各有卡密，且免费组同名/不同名；
- 同一管理员多张卡密但免费组仅出现一份；
- 一张卡密过期、另一张仍有效；
- 一张卡密被手动禁用/撤销，不影响其他有效卡密；
- 无有效卡密但存在历史免费 grant；
- 错误 token、跨设备 token、伪造 device_id；
- 删除分组或取消来源后 generation/tombstone 和客户端清理 ACK；
- 重复请求、并发兑换与并发撤销。

## 5. 上线结论

APP 多卡密聚合、免费组去重、同名卡组序列号展示和节点删除同步仍未实现或未验证，属于 APP 功能上线阻断项。本报告是静态审计，不代表已完成实现。需先解决接口授权边界报告中的 token 验证缺口，再进行聚合实现和兼容性测试。
