## 2. 当前已存在的转换历史管理接口

从 Worker 静态路由可见：
- 超管转换历史列表：`GET /api/super/convert-links`，支持分页和 group 筛选。
- 超管修改单条转换记录分组：`PATCH /api/super/convert-links/:id/group`。
- 超管批量重命名分组：`POST /api/super/convert-groups/rename`。
- 超管查看来源：`GET /api/super/convert-links/:id/sources`，默认遮罩；`reveal=1` 返回完整来源 URL。
- 超管撤销短链：`POST /api/super/convert-links/:id/revoke`。
- 普通用户/匿名访客另有按 owner_key 查询、改分组和撤销短链的公开转换路由。

超管路由在进入管理分支前检查 super 身份，并拒绝处于协助他人状态的会话访问总后台；但仍需按真实 Worker 路由测试确认所有路径都经过同一守卫。

## 3. P1-43：超管查看完整订阅 URL 时，敏感查看审计失败会被静默吞掉

证据：
- `GET /api/super/convert-links/:id/sources?reveal=1` 将完整 URL 返回给超管。
- 返回前调用 `auditStmt(... action: "convert.sources.reveal" ...).run().catch(() => {})`。
- 审计写入失败不会阻止完整 URL 返回，也没有在该 catch 中留下独立告警。

影响：
- 当 D1 审计写入失败或审计表/触发器异常时，完整订阅凭证仍然被读取并返回。
- 事后可能无法证明是谁、何时、因何原因查看了完整订阅 URL。
- 这类 URL 可能含用户名、密码、Token 或长期订阅凭证，敏感程度高于普通转换元数据。

修复要求：
1. 完整 URL reveal 必须先完成强制审计，再返回敏感数据；审计失败时 fail closed，返回 503/明确错误。
2. reveal 操作要求填写原因，记录 actor、request_id、目标转换记录、来源数量、时间和审批/工单引用（如有）。
3. 默认永远返回遮罩 URL；完整值只允许按需、短时、单次展示。
4. 日志不得打印完整 URL；审计只记录记录 ID 和来源数量，不写凭证本身。
5. 增加对 reveal 的频率限制与异常告警。

## 4. P2-22：超管转换历史接口尚未覆盖“编辑保留快照”和“永久清理”能力

用户已确认的业务目标包括：
- 超管按用户名、用户 ID、URL、批次、时间、保存模式筛选转换记录。
- 查看、复制、编辑，并保留编辑前快照历史。
- 清理转换记录；敏感操作必须审计。

当前静态路由只看到：
- 列表支持 group 筛选和分页。
- 修改单条记录的 group_name。
- 批量重命名 group_name。
- 查看来源 URL（默认遮罩，可 reveal）。
- 撤销短链。

当前未看到：
- 按用户名、用户 ID、来源 URL、批次 ID、时间范围、保存模式的完整筛选能力。
- 读取并复制指定格式的转换内容的超管专用接口（公开短链可取配置，但不等于受控管理接口）。
- 编辑转换内容并保存旧 payload 快照/版本历史的接口。
- 删除/回收站/永久清理接口及恢复流程。
- local_only/save_mode 字段及相应筛选的持久化证据。

结论：这部分不是“已经实现，只差前端按钮”，而是 Worker 静态路由目前未呈现完整闭环。需要在实施计划中新增 API、D1 版本表/审计结构和权限测试。

修复设计建议：
1. 转换记录主表保留稳定 ID；每次编辑先写不可变快照（旧 payload hash、版本号、操作者、时间、变更原因），再更新当前版本。
2. 不允许直接覆盖且无法恢复的编辑。
3. 清理采用回收站状态与 purge_after；超管可恢复，达到保留期限后才由维护任务物理删除。
4. 对删除、恢复、永久清理分别设置 manage 权限、二次确认和审计。
5. 用户查询默认只返回自己的记录；超管跨用户查询必须有明确超管权限并记录查询审计。
6. 来源 URL 搜索应避免将明文凭证写入普通索引；建议使用规范化/脱敏字段或受控哈希检索，完整 reveal 单独授权。

## 5. P2-23：超管转换历史列表筛选能力与用户要求不匹配

当前列表只支持 group 参数，查询列包含 owner_user_id、hits、创建/最后使用/过期/撤销时间等基本信息。未看到用户名 join，也未看到 URL、时间区间、批次、保存模式筛选。

修复要求：
- 支持 username/user_id、record_id、created_at 范围、group、status、source fingerprint 等筛选。
- URL 搜索不得直接把明文订阅 URL 作为普通日志或可公开索引。
- 分页排序需稳定，避免时间相同导致翻页重复/遗漏。
- 对大表增加复合索引，先用脱敏测试数据验证查询计划。

## 6. P2-24：转换记录分组修改没有版本快照，且超管批量改名的审计不在同一业务批次

证据：
- 单条分组修改调用 userBatch，将 UPDATE 和 auditStmt 放入同一个 batch，方向较好。
- 批量分组改名先独立执行 UPDATE，再在 changed > 0 时另行调用 userBatch 写审计。

影响：
- 批量 UPDATE 成功而后续审计失败时，业务已改变但没有对应审计事件。
- 当前分组修改只更新 group_name，没有看到版本快照；如果用户把“编辑”理解为转换内容编辑，当前实现不满足。
- 批量改名没有记录每条转换记录变更明细，仅记录 from/to/数量。

修复要求：
1. 批量 UPDATE 与审计 INSERT 放入同一个 D1 batch。
2. 对真正的转换内容编辑建立独立快照表；分组更名可作为元数据变更审计，不必复制整份 payload。
3. 对批量操作记录操作前后条件、影响条数和操作者；必要时记录目标 ID 清单或可重建的批次标识。

## 8. 测试矩阵

1. 非超管访问 /api/super/convert-links：必须拒绝。
2. 超管处于协助会话时访问总后台：必须拒绝。
3. 默认来源查看：用户名、密码、Token、查询参数不得泄露。
4. reveal 缺少原因：拒绝；审计表故障：不得返回明文 URL。
5. reveal 成功：审计必须存在 actor/request_id/record_id/time。
6. 批量分组改名：业务和审计要么同时成功，要么同时失败。
7. 编辑转换内容：旧版本可查看、恢复，版本号严格递增。
8. 回收站删除：普通列表隐藏或标记删除；授权超管可恢复。
9. 永久清理：必须二次确认、记录审计并按保留策略执行。
10. 按用户、批次、时间、来源指纹筛选：结果稳定且不跨用户泄露。

## 9. 禁止事项

- 不得在审计日志、HTML 或普通接口响应中泄露完整订阅 URL。
- 不得把“撤销短链”冒充“删除历史数据”。
- 不得把修改 group_name 冒充编辑转换内容。

- 未经明确审批不得对真实转换记录执行 reveal、撤销、编辑或清理。
