## 2. 新确认问题

### P1-28：APP 分组节点查询缺少来源所有权二次校验

证据位置：`groupNodeList(db, groupId)`。

当前查询连接：
- `app_group_sources gs`
- `subscription_sources s`
- `node_records n`

当前过滤条件包括：
- `gs.group_id = ?`
- `s.enabled = 1`
- `n.enabled = 1`
- 不存在非 approved 的来源审批记录

但该查询没有连接或校验 `source_ownership`，也没有验证 `source_ownership.user_id = app_groups.admin_user_id`。

影响：
- 来源所有权被超管转移后，旧管理员的历史 APP 分组来源关联仍可能保留。
- 只要来源仍启用、节点仍启用且审批条件通过，旧分组的节点查询可能继续返回该来源节点。
- 与 `/api/app/nodes` 使用来源所有权约束的行为不一致。
- 来源重新启用时，历史关联可能再次暴露节点。

修复要求：
1. 分组节点查询必须同时验证来源当前所有权与分组管理员身份一致。
2. 来源转移时，旧管理员分组关联必须进入撤销/待确认状态；不能静默继承给新管理员。
3. 新管理员必须重新确认来源与分组关系。
4. 对来源转移、撤销、重新启用产生审计事件，并使 APP 客户端收到新的授权/分组版本。
5. 测试覆盖：A 管理员创建分组并关联来源；超管将来源转给 B；A 不得继续读取；B 不得自动继承 A 的分组/卡密/设备授权。

### P1-29：APP 分组节点查询未过滤 stale 生命周期节点

证据位置：
- `runNodeLifecycle(db, ctx)`：将满足条件的节点生命周期状态标记为 stale。
- `groupNodeList(db, groupId)`：没有连接 `node_lifecycle`，也没有过滤 stale 状态。

影响：
- 生命周期任务标记为 stale 的节点，只要 `node_records.enabled = 1`，仍可能通过 APP 分组接口下发。
- “只标记、不删行”本身可以保留历史数据，但 APP 读取层必须明确排除已撤销/失效节点。
- 不能将 stale 状态等同于已完成设备端清理。

修复要求：
1. 明确生命周期状态机中哪些状态可下发；至少 stale 不得继续进入新下发结果。
2. 节点从可用变为不可用时，产生单调递增的来源/分组版本或撤销墓碑。
3. APP 同步接口必须返回版本变化和撤销节点 ID，客户端确认清理后回传 cleanup acknowledgement。
4. 历史记录保留，不以物理删除作为撤销方案。
5. 测试覆盖：节点 stale 后新设备不得获取；已有设备下次同步必须删除本地缓存；设备离线后恢复联网也不得重新获得已撤销节点。

### P1-30：缺失节点停用行为依赖环境开关，不能视为默认清理

证据位置：`syncSource()` 中的 `disableMissing` 计算与 `commitTask()`。

当前行为：
- 只有 `env.SYNC_DISABLE_MISSING === "1"` 且未触发 suspicious shrink 时，才会在提交阶段把本次同步缺失的节点设为 `enabled = 0`。
- 默认配置未开启时，缺失节点可能继续保持 enabled。
- 即使节点被设为 disabled，也不能证明 APP 已收到撤销事件或清除本地缓存。

修复要求：
1. 对该环境开关建立明确的配置清单、默认值、部署核查与告警。
2. 订阅异常缩减时应进入待确认/保护状态，不得把“未停用”误判为节点仍有效。
3. 节点停用与 APP 撤销通知、客户端清理确认必须分开记录。
4. 上线前在 staging 使用受控数据验证，不直接对生产执行批量停用。

## 3. 已确认的相关现状

### 3.1 多管理员 entitlement

`appGroupsForDevice()` 查询有效 entitlement 时使用：
`ORDER BY created_at DESC LIMIT 1`

因此同一设备存在多个管理员有效授权时，当前接口只选取最新的一条；这与“多管理员授权集合”的业务设计尚不兼容。必须明确允许多管理员并存还是拒绝并存，并让 APP 数据按管理员身份隔离。

### 3.2 APP status 与 nodes 的授权差异

- `/api/app/status` 按 device_id 查询最近一条 entitlement，并通过子查询计算是否存在任意有效 entitlement；未见 Token 验证。
- `/api/app/nodes` 会选择最近一条有效 entitlement，并调用 `verifyEntToken()` 验证 Token。
- `/api/app/groups` 在有 entitlement 时也验证 Token；无 entitlement 时走历史 free grant 分支，该分支以 device_id 对应的 grant 列表读取免费分组，需单独定义撤销和多管理员边界。

这些接口的身份选择、授权集合与 Token 验证口径必须统一。

## 4. V2.5 必须实现的 APP 撤销闭环

推荐统一数据流：

1. Worker 检测来源转移、节点撤销、分组删除/改型、授权到期或管理员权限失效。
2. Worker 写入不可覆盖的版本事件/撤销墓碑，记录管理员、来源、分组、节点、版本、原因和时间。
3. APP 以管理员身份和设备授权拉取增量变更。
4. APP 按管理员命名空间删除对应本地节点/分组缓存，不得误删其他管理员的数据。
5. APP 回传设备、管理员、版本和清理结果。
6. Worker 记录 cleanup acknowledgement；未确认设备持续显示待清理，设备重新上线必须先应用撤销版本，再允许拉取新数据。
7. 24 小时本地保留策略只能作为明确的到期兜底，不能代替服务端撤销和客户端确认。

## 5. 测试矩阵（实施前必须补齐）

| 场景 | Worker 预期 | APK 预期 |
|---|---|---|
| 来源从 A 转给 B | A 的旧分组不再返回该来源；B 不继承旧授权 | A 缓存撤销；B 需重新授权/关联 |
| 节点进入 stale | 新下发排除该节点并产生撤销版本 | 下次同步删除本地节点 |
| 同步缺失节点且开关关闭 | 不得宣称已撤销；记录待处理状态 | 不得把旧缓存当成服务端仍授权 |
| 分组删除或改型 | 产生版本和撤销清单，保留审计历史 | 只清理对应管理员命名空间 |
| 两个管理员同时授权同设备 | 按明确规则返回授权集合或拒绝并存 | 分管理员隔离节点、分组、缓存 |
| 设备离线超过 24 小时后恢复 | 先下发撤销状态，再允许拉取新内容 | 先执行清理，再更新内容 |
| Token 失效/管理员 VIP 到期 | 按授权规则拒绝新读取并返回明确状态 | 停止更新，按业务保留规则处理历史缓存 |

## 6. 禁止事项与实施门槛

- 不得以删除历史节点行代替撤销。
- 不得把 device_id 当作设备身份凭证。
- 不得把 `/api/app/status` 的状态查询结果当作读取节点的授权证明。
- 不得仅凭 Worker 返回 403 就假设 APK 已清理本地缓存。
- 不得在没有 APK 源码审计和联测证据时宣称 24 小时清理闭环已完成。
- 不得未经审批执行生产 D1 迁移、批量停用、删除、Worker 部署或密钥修改。
