- 批次：第三十七批

- 日期：2026-11-27
- 状态：静态路由盘点与 UX 优化方案；未修改 HTML/Worker；未执行 D1；不可部署
- 基线：`星跃模拟后台 1.4.61.html`（blob `d046f71caa5af96b0c0978013771cb0a8f101739`）
- 关联：第三十四批 APP 化交互规范、第三十五批首页/主导航差距、第三十六批统一导航与角色权限映射
- 本批新增原则：同一业务功能只有一个权威页面和一个明确归属；其他位置仅提供指向该页面的快捷入口，不复制第二套页面或重复操作流程。

## 1. 对用户关于“重复页面/功能”的明确回应

用户特别指出：桌面菜单现有独立“APP 管理”分组，若页面或功能重复必须优化，不能让用户困惑。

本批明确：
- **桌面端保留“APP 管理”分组**。这是合理的业务分组，不应为了五项手机底栏而删除。
- **手机端“APP”一级入口对应同一个 APP 工作台**，点击后进入 APP 概览，再由工作台进入卡密、用户、设备、授权分享等子页面。
- APP 管理分组中的每个子页面仍只有一个主归属。手机底栏、首页快捷卡片、右侧快捷工具、收藏菜单都只能链接到该主页面，不得各自实现一套同名功能。
- “APP 授权分享”应归入 APP 管理业务域；“外部订阅分享”仍归入分享管理/订阅分享业务域。分享记录应按分享类型过滤展示，避免 APP 分享记录和普通外链记录混在一起。
- 卡密不再单独占据手机底部一级入口；它是 APP 工作台的子模块。手机用户从“APP → 激活卡密”进入。
- 任何调整必须保留旧 URL/route alias 和用户已有书签，迁移完成前不能直接删除旧 route。

## 2. 源码盘点结果

重新读取 1.4.61 HTML，静态提取到：
- `registerPage()` 共 55 次注册，55 个唯一页面 route。
- 桌面 `MENU` 有 7 个业务分组：工作台、节点转换、订阅与节点、分享管理、APP 管理、数据统计、系统管理。
- `PAGE_META`、`MENU_MAP`、`PAGE_RENDERERS` 分别承担页面元数据、桌面菜单映射、页面渲染注册；目前不是统一导航注册表。
- 手机 `renderBottomNav()` 独立硬编码两套数组：访客 4 项；已登录 5 项。已登录的第五项中有“卡密”，没有“APP 工作台”。
- `renderRightSidebar()` 又独立维护一套快捷入口，其中包含节点转换、转换批次、分组、订阅源、转换历史、节点、APP 卡密、APP 授权分享、系统设置。
- 侧栏收藏和最近访问也会重复显示主导航已有页面；这是快捷入口的重复展示，不是重复页面本身，应该保留但让用户能识别为“快捷方式”。

本批提取结果仅用于静态结构分析，不等于运行时所有页面都能正常渲染，也不证明后端接口存在。

## 4. 必须治理的重复与冲突

### P0-1：手机“卡密”入口与桌面“APP 管理”分组不一致

现状：桌面用户先看到“APP 管理”，手机用户却直接看到“卡密”，导致用户误以为 APP 管理就是卡密管理。

决定：
- 手机底栏第五项改为“APP”，route 指向 `app` 工作台。
- 卡密从一级导航移入 APP 工作台子菜单。
- 桌面保留“APP 管理”分组与其子页面。
- 桌面分组标题和手机入口名称不同可以接受，但业务归属必须一致。

### P0-2：APP 授权分享被放在普通“分享管理”分组

现状：`app-shares` 与 `shares` 同组，用户不易理解 APP 专用分享与普通外链分享的差异。

决定：
- `app-shares` 主归属迁入 APP 管理。
- `shares` 保留普通外部订阅分享。
- APP 免费分组、卡密分组仍使用专门 APP 对接分享链接，不允许普通网页链接替代。
- 分享记录保留统一查询页，但必须提供清晰类型筛选和来源标识；从 APP 页面进入时自动带入 APP 类型筛选。

### P0-3：两个首页 route 并存

现状：`dashboard` 和 `v1-overview` 都注册为页面；桌面菜单首页指向 `dashboard`，手机底栏首页指向 `v1-overview`。

决定：
- 目标只保留一个权威首页 route：`home`（实际实施前需决定最终 canonical ID）。
- `dashboard`、`v1-overview` 暂时作为旧 route alias，重定向到权威首页。
- 必须先对比两个 renderer 的功能、角色差异和数据来源，再合并内容；不能简单丢弃其中一个页面。
- 访客首页应作为同一首页的角色视图，而不是另一个完全割裂的首页体系。

### P0-4：转换入口存在两套 route

现状：桌面 `convert`，手机底栏 `v1-converter`，另有 `conv-tasks`、`conv-history`、`conv-plans`、`conv-groups` 等页面。

决定：
- 手机和桌面转换一级入口最终指向同一转换工作台。
- `convert` 与 `v1-converter` 必须对比操作流程、访客能力和 VIP 能力后确定 canonical route。
- 若是同一功能，保留一套实现，另一 route 做兼容 alias；若功能确实不同，必须改名并说明场景，禁止同名并列。
- 访客基础转换仍保留，不得因为合并 route 而开放 VIP 管理能力。

### P1-5：右侧快捷工具与主导航重复

决定：
- 右侧面板定位为“上下文快捷工具”，不再复制完整菜单。
- 根据当前页面动态显示相关动作。例如在 APP 卡密页显示“返回 APP 概览、APP 用户、授权分享”；在节点页显示“订阅源、分组、同步记录”。
- 不在每个页面重复列出全部常用入口。
- 收藏/最近访问可以跨业务域，但必须标注“快捷入口”，不创建重复页面。

### P1-6：统计页与业务页重复展示数据

决定：
- 业务页可以显示少量与当前任务直接相关的摘要。
- 完整统计、趋势、筛选、导出统一进入数据统计中心。
- 业务摘要卡片点击后打开对应统计页并带筛选条件，不在业务页另造一套统计页面。
- 未接真实 API 的统计必须明确标为演示/未连接，不得显示看似实时的假数字。

## 5. 桌面与手机最终信息架构

### 桌面侧栏（保留分组）

1. 工作台：首页、快捷操作（可并入首页）、最近访问（可并入首页）。
2. 转换：转换工作区、任务、历史、方案、过滤规则、分组、模板。
3. 节点：订阅源、节点、节点分组、同步记录。
4. 分享：普通外部订阅分享、分享记录（可筛选普通/APP）。
5. **APP 管理：APP 概览、APP 授权分享、激活卡密、APP 用户、设备管理。**
6. 数据统计：用户、激活、设备、节点、转换统计。
7. 系统管理：管理员、后台 VIP、权限、总后台、日志、任务、诊断、系统设置、主题；APP 版本与更新配置仅超管可见。

注：如果 APP 管理授权未授予，普通 VIP 不显示 APP 管理写操作；公开 APP 下载信息可以放在注册用户可见的“我的/帮助”中，但不能因此开放 APP 管理。

### 手机底部五项

- 首页：工作台。
- 转换：转换工作区。
- 节点：节点工作区。
- APP：APP 工作台。
- 我的：个人账号与权益。

手机侧滑菜单承载低频菜单、统计和系统管理。底部五项不承担全部页面目录。

访客模式保留基础转换、默认分组、本人批次、注册/登录、帮助；不为了视觉对称而塞入没有意义的第五项。访客可沿用五项布局时，第五项显示“我的/注册”，但不能显示 APP 管理。

## 6. 可合并、可折叠、不可合并的边界

| 类型 | 处理 |
|---|---|
| 同一业务的两个入口、同一操作流程 | 合并为一个页面，旧 route 做 alias |
| 同一页面在底栏/侧栏/首页快捷卡重复出现 | 保留一个主页面，其他仅作为链接 |
| 同一业务的不同任务步骤 | 可合并为一个工作区内的 Tab/步骤，不必拆成多个菜单 |
| 需要不同权限、不同数据范围或不同生命周期的功能 | 不强行合并，保持独立页面并明确名称 |
| APP 分享与普通外部订阅分享 | 不合并操作模型；可统一记录查询但类型隔离 |
| APP 用户与后台管理员 | 不合并；身份、资源与权限不同 |
| VIP 管理与 APP entitlement | 不合并；生命周期不同 |
| 统计摘要与统计中心 | 摘要保留，完整分析统一到统计中心 |

## 7. 页面体验约束：让用户不困惑

- 菜单名称用任务语言，不使用只有开发人员理解的内部术语。
- 每个页面顶部明确“你现在在哪个业务模块”，避免同名页面造成迷失。
- 每个页面只设置一个主操作按钮；次要操作放在菜单或次级区域。
- 同一操作不能在不同页面出现不同名称或不同确认流程。
- 从快捷入口进入时保留来源上下文；返回应回到原页面和筛选位置。
- 有风险的删除、撤销、发卡、发布操作统一确认规范，明确影响对象和后果。
- 受限用户不显示不可用的写操作；若只读可用，明确标识“只读”。
- 不能把“入口隐藏”当作 Worker 授权；每个 API 仍需服务端校验。

## 8. 实施拆分与验收门禁

### 第一阶段：路由收敛（不改业务数据）
- 建立 canonical route + alias map。
- 对比 `dashboard/v1-overview`、`convert/v1-converter` 两组 renderer。
- 统一底栏、桌面侧栏、首页快捷入口使用相同 route ID。
- APP 底栏指向 APP 工作台；卡密成为 APP 子页面。
- APP 授权分享移动到 APP 管理主归属。
- 右侧面板改为上下文快捷工具。

### 第二阶段：页面归并与工作台
- 首页/转换/节点/APP/我的分别形成明确工作台。
- 同一工作流的子页面可用 Tab 或步骤导航。
- 统计摘要跳转统一统计中心。
- 保留原页面功能，不在本阶段删除任何功能。

### 第三阶段：清理旧入口
- 只有当 canonical 页面覆盖旧页面全部有效功能，且 alias/书签/最近访问测试通过后，才移除旧 UI 入口。
- 旧 route 至少跨一个稳定版本保持兼容。
- 清理前生成路由迁移表和回滚方案。

### 必测视口和角色
- 视口：360×800、390×844、430×932、768×1024、1366×768。
- 身份：访客、普通注册、有效 VIP、体验 VIP、VIP 到期、超管本人、超管协助会话。
- 验收：同一功能不会出现两套不同页面；从不同快捷入口进入最终落到同一页面；页面标题/面包屑/底栏高亮一致；无权限用户不能通过直接输入旧 route 绕过前端门禁；Worker 端权限独立验证。

## 9. 本批结论与状态

本批将用户提出的“桌面 APP 管理分组要保留，同时消除重复页面/功能造成的困惑”落实为信息架构规则。

关键决定：
1. 桌面 APP 管理分组保留。
2. 手机 APP 一级入口进入同一个 APP 工作台；卡密不再占用底栏。
3. APP 授权分享归入 APP 管理；普通外部订阅分享独立保留。
4. 两个首页 route、两个转换 route 必须对比后收敛，旧 route 先做兼容映射。
5. 右侧快捷面板改为上下文快捷工具，不复制全量菜单。
6. 任何合并都以用户操作路径、权限边界和数据生命周期为依据，不为减少菜单数量而牺牲功能。

**本批仅完成静态路由盘点与改造方案；未修改 HTML/Worker，未连接生产 D1，未运行浏览器/Android 设备测试，不能作为部署包。**

下一批建议：第三十八批对 `dashboard` 与 `v1-overview`、`convert` 与 `v1-converter` 的页面渲染函数做逐项功能对照，确定 canonical 页面和兼容跳转方案，再开始第一处最小 HTML 改造。
