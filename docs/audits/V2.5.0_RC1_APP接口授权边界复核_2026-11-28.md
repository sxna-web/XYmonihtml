# V2.5.0 RC1 APP 接口授权边界复核

- 日期：2026-11-28
- 分支：`release/v2.5.0-rc1-converge`
- Worker：`backend/worker/V2.5-DEV-B1-CORE-AUTH-49/Worker.js`
- 范围：静态代码路径复核；未执行线上请求、生产 D1 查询或 APK 联调。

## 1. 结论

APP 各读取接口的鉴权边界不一致。当前 `/api/app/nodes` 与存在有效 entitlement 时的 `/api/app/groups`、`/api/app/links` 会验证 token；但 `/api/app/status` 仅凭请求参数中的 device_id 返回授权记录摘要，`/api/app/groups` 在没有有效 entitlement 时也会仅凭 device_id 查询免费授权并返回分组节点。

这不是多卡密功能的实现问题，而是独立的接口授权边界问题。应在多卡密聚合改造前一并设计，否则可能把未经认证的 device_id 当作设备身份凭据。

## 2. 代码核验

### 2.1 `GET /api/app/status`

路由读取 `device_id` 后直接查询 `app_entitlements`，返回最近一条授权的 `id / expires_at / purge_at / status / active`。该路径没有读取或验证 entitlement token。

### 2.2 `GET /api/app/groups`

先查询该 device_id 最新有效 entitlement：
- 找到 entitlement 时验证其 token，然后只返回该 entitlement 对应管理员的组。
- 找不到有效 entitlement 时，直接读取 `app_free_grants`，再返回对应管理员启用的免费组；该分支没有 token 校验。

因此，设备标识本身不能被视为可信的设备持有证明。即使免费组被设计为可公开获取，也应明确这是“公开分享”还是“已绑定设备的永久免费授权”，两者不能混用。

### 2.3 对照接口

- `GET /api/app/nodes`：验证有效 entitlement token 后才下发节点。
- `GET /api/app/links`：验证有效 entitlement token 后才返回入口链接。
- `GET /api/app/free`：通过管理员 ID 或分享编号获取公开免费节点；属于另一种公开分享语义，应与设备授权接口明确隔离。
- `POST /api/app/redeem`：兑换卡密后生成 entitlement token；需要继续保留卡密状态、有效期和设备绑定约束。

## 3. 修复设计要求

1. 明确设备凭据模型：不能仅凭客户端可任意提交的 `device_id` 证明设备身份。
2. `/api/app/status` 应验证 token 对应的有效 entitlement，并对无效、过期、撤销授权统一 fail-closed；返回字段只限客户端实际需要的状态。
3. `/api/app/groups` 的永久免费组读取必须区分两种模式：
   - 已激活卡密后保留的设备免费资格：必须通过有效设备凭据验证；
   - 管理员公开分享的免费组：只能走独立公开分享接口，且不得泄露设备授权记录。
4. 多卡密聚合时，验证传入 token 对应的 entitlement 属于该设备，再聚合该设备全部有效卡密；不可因知道 device_id 就列举该设备其他管理员的免费授权或卡密组。
5. 迁移时保留旧 APK 兼容窗口：先确认客户端请求实际携带的 token、参数位置及失败处理，再调整协议；不得直接假设旧版兼容。
6. 增加无 token、错误 token、过期 token、伪造 device_id、跨设备 token、多个有效 entitlement、免费授权残留等测试。

## 4. 上线判断

该项属于 APP 授权安全阻断项。当前报告仅记录静态源码证据和修复要求，不代表接口已经修复，也不构成真实 D1 或 APK 验证。未完成客户端协议核对和自动化回归前，不应将 APP 授权相关功能标记为正式可上线。
